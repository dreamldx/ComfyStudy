## 2. 背景与概念

**MSVC 工具链。** 微软的 C++ 工具链由几个程序组成：

| 程序 | 作用 |
|---|---|
| `cl.exe` | 编译器：把一个 `.cpp` 编译成目标文件 `.obj` |
| `lib.exe` | 打包器：把若干 `.obj` 打包成静态库 `.lib` |
| `link.exe` | 链接器：把 `.obj` 和库链接成可执行文件 `.exe` 或动态库 `.dll` |
| `rc.exe`、`mt.exe` | 资源编译器和清单工具，链接后期用来嵌入资源与清单 |

**为什么要用“x64 Native Tools”命令提示符。** 在普通终端里输入 `cl`，会提示找不到命令。`cl.exe` 并不在系统的 `PATH` 里，而且编译器还需要知道标准库头文件和系统库在哪。Visual Studio 自带一个脚本 `vcvars64.bat`，它会为当前终端设置四个环境变量：

| 变量 | 作用 |
|---|---|
| `PATH` | 加入 `cl.exe`、`link.exe` 等工具所在目录 |
| `INCLUDE` | 编译器查找头文件（标准库、Windows SDK）的目录 |
| `LIB` | 链接器查找库文件（`.lib`）的目录 |
| `LIBPATH` | 查找 .NET 与 Windows 元数据的目录 |

开始菜单里 Visual Studio 文件夹下的 “x64 Native Tools Command Prompt”（或 “Developer PowerShell”）就是运行完这个脚本的终端。**本教程所有命令都在这样的终端里运行。**

**CMake 与 Ninja。** CMake 本身不编译代码，它是一个**构建系统生成器**：读取 `CMakeLists.txt`，生成真正执行构建的文件。我们让它生成给 Ninja 用的文件。Ninja 是一个很小、很快的构建执行器，只做一件事：按依赖关系运行编译命令，并且只重做必要的部分。整个流程分三步：

1. **配置（configure）**：CMake 读取 `CMakeLists.txt`，探测编译器，把结果记在缓存里。
2. **生成（generate）**：CMake 写出 `build.ninja`。
3. **构建（build）**：Ninja 读取 `build.ninja`，运行 `cl`、`lib`、`link`。

`cmake --preset windows-debug` 完成前两步，`cmake --build --preset windows-debug` 完成第三步。

**从源码到可执行文件。** 一个 `.cpp` 文件和它包含的所有头文件合起来叫一个**翻译单元**。编译器把每个翻译单元独立编译成一个 `.obj`，再由链接器把所有 `.obj` 和库合成最终程序。这就是为什么你修改一个源文件，只需要重新编译它一个。

**Ninja 怎么知道改了什么。** 改了一个头文件，所有包含它的源文件都要重编，但这个依赖关系不是我们手写的。`cl` 有一个选项 `/showIncludes`：每编译一个源文件，它就把这个文件**实际包含了哪些头文件**（包括间接包含的）打印出来。Ninja 读取这些信息，存进构建目录里的 `.ninja_deps`。下次构建时，Ninja 比较这些头文件和目标文件的修改时间，哪个头文件比目标文件新，就重编依赖它的源文件。所以依赖关系永远由编译器告诉 Ninja，不会漏，也不需要维护。后面“验证”一节会亲手试一遍。

## 4. 关键代码讲解

**源码。** 程序分成三个小文件。`version.h` 只放版本号宏：

<!-- src: src/version.h#L1-L3 -->
```cpp
#pragma once

#define COMFYSTUDY_VERSION "0.1"
```

`greeting.h` 声明一个函数，`greeting.cpp` 实现它：

<!-- src: src/greeting.h#L1-L6 -->
```cpp
#pragma once

#include <string>

// Returns the program name followed by its version, e.g. "ComfyStudy 0.1".
std::string Greeting();
```

<!-- src: src/greeting.cpp#L1-L5 -->
```cpp
#include "greeting.h"

#include "version.h"

std::string Greeting() { return "ComfyStudy " COMFYSTUDY_VERSION; }
```

`main.cpp` 调用它。注意它只包含 `greeting.h`，**不包含** `version.h`；本章的“验证”会利用这一点观察“改一个头文件到底重编哪些文件”：

<!-- src: src/main.cpp#L1-L8 -->
```cpp
#include <iostream>

#include "greeting.h"

int main() {
  std::cout << Greeting() << '\n';
  return 0;
}
```

**`CMakePresets.json`：配置预设。** 预设把“怎么配置”写成文件，这样你和任何读者敲的命令都一样。预设也按系统分文件：`CMakePresets.json` 只写格式版本和最低的 CMake 版本，再用 `include` 引入当前系统的预设文件（路径相对于 `CMakePresets.json` 所在的目录）；生成器、vcpkg 的路径、Visual Studio 预设都是 Windows 专属的，所以写在 `cmake/presets/windows.json` 里。别的系统的分支加上自己的预设文件，再改这一行 `include`：

<!-- src: CMakePresets.json#L1-L5 -->
```json
{
  "version": 6,
  "cmakeMinimumRequired": { "major": 3, "minor": 25, "patch": 0 },
  "include": [ "cmake/presets/windows.json" ]
}
```

`cmake/presets/windows.json`：

<!-- src: cmake/presets/windows.json#L1-L36 -->
```json
{
  "version": 6,
  "configurePresets": [
    {
      "name": "windows-base",
      "hidden": true,
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/build/${presetName}",
      "cacheVariables": {
        "CMAKE_EXPORT_COMPILE_COMMANDS": "ON"
      }
    },
    {
      "name": "windows-debug",
      "inherits": "windows-base",
      "cacheVariables": { "CMAKE_BUILD_TYPE": "Debug" }
    },
    {
      "name": "windows-release",
      "inherits": "windows-base",
      "cacheVariables": { "CMAKE_BUILD_TYPE": "Release" }
    },
    {
      "name": "windows-vs",
      "generator": "Visual Studio 18 2026",
      "architecture": { "value": "x64", "strategy": "set" },
      "binaryDir": "${sourceDir}/build/windows-vs"
    }
  ],
  "buildPresets": [
    { "name": "windows-debug", "configurePreset": "windows-debug" },
    { "name": "windows-release", "configurePreset": "windows-release" },
    { "name": "windows-vs-debug", "configurePreset": "windows-vs", "configuration": "Debug" },
    { "name": "windows-vs-release", "configurePreset": "windows-vs", "configuration": "Release" }
  ]
}
```

- `"version": 6` 是预设文件格式的版本，需要 CMake 3.25 及以上。
- `windows-base` 是一个隐藏的预设，放公共设置：生成器用 `Ninja`；构建目录是 `build/<预设名>`，所以 Debug 和 Release 各有自己的目录，互不干扰；`CMAKE_EXPORT_COMPILE_COMMANDS` 让 CMake 额外写一个 `compile_commands.json`，列出每个文件的编译命令，编辑器和代码分析工具会读取它。
- `windows-debug` 和 `windows-release` 继承 `windows-base`，只有 `CMAKE_BUILD_TYPE` 不同。这个变量决定使用哪一组默认编译选项。
- `windows-vs` 是给 Visual Studio 用的预设（生成器换成 `Visual Studio 18 2026`），本章后面单独讲。
- `buildPresets` 把“构建”和“配置”对应起来，这样 `cmake --build --preset windows-debug` 就知道去哪个目录构建。

**`CMakeLists.txt`：项目本身。** 开头声明 CMake 的最低版本和项目名称。`LANGUAGES CXX` 表示只用 C++：

<!-- src: CMakeLists.txt#L1-L3 -->
```cmake
cmake_minimum_required(VERSION 3.25)

project(ComfyStudy VERSION 0.1.0 LANGUAGES CXX)
```

语言标准。`CMAKE_CXX_STANDARD` 要求 C++20，`CMAKE_CXX_STANDARD_REQUIRED` 表示达不到就报错，`CMAKE_CXX_EXTENSIONS OFF` 表示不用编译器私有扩展：

<!-- src: CMakeLists.txt#L5-L7 -->
```cmake
set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)
```

**按系统分文件。** 构建文件从一开始就按系统拆开：和操作系统有关的设置，包括编译器选项、C 运行库、以后第三方库的查找方式、只在 Windows 上存在的源文件和目标，都放在 `cmake/platform/<系统名>.cmake` 里；顶层 `CMakeLists.txt` 只写与系统无关的部分。`CMAKE_SYSTEM_NAME` 在 Windows 上是 `Windows`，转成小写就是文件名里的 `windows`。找不到对应的文件时，CMake 直接报错并说明缺哪个文件。主线只实现 Windows，所以只有 `windows.cmake`；别的系统的实现放在支线（platform 方向）里，不进主线：

<!-- src: CMakeLists.txt#L9-L18 -->
```cmake
# Everything that depends on the operating system lives in cmake/platform/<system>.cmake: the
# compiler options, how the third-party libraries are found, and sources and targets that exist on
# that system only. This branch has windows.cmake only.
string(TOLOWER "${CMAKE_SYSTEM_NAME}" comfystudy_platform)
set(comfystudy_platform_file "${CMAKE_SOURCE_DIR}/cmake/platform/${comfystudy_platform}.cmake")
if(NOT EXISTS "${comfystudy_platform_file}")
  message(FATAL_ERROR "No build support for ${CMAKE_SYSTEM_NAME} on this branch "
                      "(missing ${comfystudy_platform_file})")
endif()
include("${comfystudy_platform_file}")
```

平台文件 `windows.cmake` 先检查编译器：项目只支持 MSVC，不是 MSVC 就直接报错：

<!-- src: cmake/platform/windows.cmake#L3-L5 -->
```cmake
if(NOT MSVC)
  message(FATAL_ERROR "ComfyStudy is built with MSVC on Windows (run from an x64 Native Tools prompt).")
endif()
```

C 运行库。`MultiThreaded$<$<CONFIG:Debug>:Debug>DLL` 是一个生成器表达式：Debug 配置展开成 `MultiThreadedDebugDLL`（编译选项 `/MDd`），其它配置展开成 `MultiThreadedDLL`（`/MD`）。这两个都是**动态**链接 C 运行库：

<!-- src: cmake/platform/windows.cmake#L7-L8 -->
```cmake
# Dynamic CRT: /MD in Release, /MDd in Debug.
set(CMAKE_MSVC_RUNTIME_LIBRARY "MultiThreaded$<$<CONFIG:Debug>:Debug>DLL")
```

编译选项也写在平台文件里，是一个列表，每个选项的含义见第 5 节：

<!-- src: cmake/platform/windows.cmake#L10-L12 -->
```cmake
# Compiler options for every target.
set(COMFYSTUDY_COMPILE_OPTIONS
  /W4 /WX /permissive- /utf-8 /Zc:__cplusplus /external:anglebrackets /external:W0)
```

回到顶层 `CMakeLists.txt`。可执行文件统一放进 `build/<预设>/bin`：

<!-- src: CMakeLists.txt#L20-L21 -->
```cmake
# Executables (and, later, the shared libraries they need) end up in build/<preset>/bin.
set(CMAKE_RUNTIME_OUTPUT_DIRECTORY "${CMAKE_BINARY_DIR}/bin")
```

公共编译选项。`INTERFACE` 库不编译任何代码，只是一个“选项包”：谁链接它，谁就带上这些选项。选项的内容来自平台文件设置的 `COMFYSTUDY_COMPILE_OPTIONS`：

<!-- src: CMakeLists.txt#L23-L25 -->
```cmake
# Compiler options shared by every target (the platform file chooses them).
add_library(comfystudy_options INTERFACE)
target_compile_options(comfystudy_options INTERFACE ${COMFYSTUDY_COMPILE_OPTIONS})
```

两个目标。除了 `main()` 之外的代码放进静态库 `comfystudy_core`，可执行文件 `comfystudy` 只有 `main.cpp` 并链接这个库。这样以后测试程序也能直接链接同一个库。`PUBLIC` 表示“我自己用，链接我的目标也要用”，`PRIVATE` 表示“只有我自己用”：

<!-- src: CMakeLists.txt#L27-L33 -->
```cmake
# Everything except main() lives in a static library, so tests can link it too.
add_library(comfystudy_core STATIC src/greeting.cpp)
target_include_directories(comfystudy_core PUBLIC src)
target_link_libraries(comfystudy_core PUBLIC comfystudy_options)

add_executable(comfystudy src/main.cpp)
target_link_libraries(comfystudy PRIVATE comfystudy_core)
```

最后一行调用平台文件里的函数 `comfystudy_platform_targets()`：只存在于某个系统的目标要等程序目标建好之后才能定义，所以顶层在这里回调一次。现在它只设置 Visual Studio 的启动项目（本章后面讲）；0.5 会往里加 DLL 管理的目标：

<!-- src: CMakeLists.txt#L35-L36 -->
```cmake
# Targets that exist on one system only (defined by the platform file, now that the program exists).
comfystudy_platform_targets()
```

**编译命令（`cl.exe`）的参数：**

| 参数 | 含义 |
|---|---|
| `/nologo` | 不打印版权横幅 |
| `/TP` | 把输入当作 C++ 源文件（CMake 按扩展名自动加上） |
| `-I<项目>\src` | 头文件搜索目录，来自 `target_include_directories(... PUBLIC src)` |
| `/DWIN32 /D_WINDOWS` | 定义宏 `WIN32` 和 `_WINDOWS`，CMake 对 Windows 程序的默认定义 |
| `/EHsc` | 异常处理模型：只处理 C++ 异常，并假定 `extern "C"` 函数不会抛异常 |
| `/Ob0` | 不做内联展开（Debug 里便于调试）；Release 里是 `/Ob2`，允许内联 |
| `/Od` | 关闭优化（Debug）；Release 里是 `/O2`，按速度优化 |
| `/RTC1` | 运行时检查（栈帧、未初始化变量），只在 Debug 里有 |
| `-std:c++20` | 使用 C++20，来自 `CMAKE_CXX_STANDARD` |
| `-MDd` | 链接**动态**调试版 C 运行库；Release 里是 `-MD`（动态发布版） |
| `-Zi` | 生成调试信息，放在单独的 `.pdb` 文件里 |
| `/W4` | 警告级别 4，几乎所有有用的警告 |
| `/WX` | 把警告当作错误，保证代码里没有警告 |
| `/permissive-` | 严格遵守 C++ 标准，禁用微软的宽松扩展 |
| `/utf-8` | 源文件与执行字符集都按 UTF-8 处理 |
| `/Zc:__cplusplus` | 让预定义宏 `__cplusplus` 报告真实的语言版本，而不是旧值 199711 |
| `/external:anglebrackets` | 用尖括号 `<...>` 包含的头文件视为“外部头文件” |
| `/external:W0` | 外部头文件不报警告，免得第三方头文件的警告被 `/WX` 当成错误 |
| `/showIncludes` | 打印包含了哪些头文件，Ninja 靠它知道每个文件依赖哪些头文件（见“验证”里的依赖追踪） |
| `/Fo<文件>` | 目标文件 `.obj` 的输出路径 |
| `/Fd<文件>` | 编译器写调试信息的 `.pdb` 路径 |
| `/FS` | 强制同步写 `.pdb`，允许多个编译进程安全地共用一个 |
| `-c` | 只编译，不链接 |

**打包命令（`lib.exe`）：** `/machine:x64` 指定目标架构，`/out:` 指定输出的静态库，后面是要打包的 `.obj`。

**链接命令（`link.exe`）：** CMake 用 `cmake -E vs_link_exe` 包了一层：先运行链接器，再用 `rc` 和 `mt` 处理清单（manifest，嵌在可执行文件里的一小段 XML）。真正的链接器参数是：

| 参数 | 含义 |
|---|---|
| `/out:bin\comfystudy.exe` | 输出的可执行文件 |
| `/implib:comfystudy.lib` | 导入库的名字（可执行文件如果导出符号才用得到） |
| `/pdb:bin\comfystudy.pdb` | 调试信息文件的位置 |
| `/version:0.0` | 写进文件头的映像版本号 |
| `/machine:x64` | 目标架构 |
| `/debug` | 生成调试信息（Debug） |
| `/INCREMENTAL` | 增量链接（Debug）；Release 里是 `/INCREMENTAL:NO` |
| `/subsystem:console` | 控制台程序 |
| `comfystudy_core.lib` | 我们的静态库 |
| `kernel32.lib user32.lib …` | CMake 默认附带的一组 Windows 系统库 |

**Release 版。**

```text
cmake --preset windows-release
cmake --build --preset windows-release --verbose
```

编译命令里 Debug 专属的 `/Ob0 /Od /RTC1 -MDd -Zi` 换成了 `/O2 /Ob2 /DNDEBUG -MD`，链接命令里 `/debug /INCREMENTAL` 换成了 `/INCREMENTAL:NO`，其余相同。`/DNDEBUG` 定义宏 `NDEBUG`，标准库里的 `assert` 在它存在时被关掉。

**在 Visual Studio Community 里打开项目。** 命令行不是唯一的方式。你可以让 CMake 生成传统的**解决方案（solution）和项目（project）文件**，再用 Visual Studio 编辑、构建和调试。生成的文件放在 `build/` 里，不会弄脏源码目录。

前提：安装 Visual Studio Community（本教程用 Visual Studio 18，即 Visual Studio 2026）时勾选了“使用 C++ 的桌面开发”工作负载。它包含 MSVC 编译器和 Windows SDK。可以在 Visual Studio Installer 里点“修改”确认已经勾选。

*（下面菜单和按钮的名称以你的 Visual Studio 中文界面为准，不同小版本之间位置可能略有差别。）*

### 生成解决方案（solution）和项目（project）文件

`cmake/presets/windows.json` 里的 `windows-vs` 预设就是为此准备的，它和 `windows-debug`、`windows-release` 的区别是：

- 生成器是 `Visual Studio 18 2026`，不是 Ninja；
- `architecture` 设为 x64；
- 构建目录是 `build/windows-vs`；
- Visual Studio 生成器是**多配置**的：一份工程里同时包含 Debug 和 Release，配置到构建时才选，所以 `buildPresets` 里的 `windows-vs-debug` 和 `windows-vs-release` 多了一个 `configuration`。

平台文件里的函数 `comfystudy_platform_targets()` 设置了一个只对 Visual Studio 生效的属性，让 `comfystudy` 成为解决方案的启动项目，这样 F5 直接运行我们的程序，而不是运行汇总项目：

<!-- src: cmake/platform/windows.cmake#L14-L18 -->
```cmake
# Called by the top-level CMakeLists.txt once the targets exist.
function(comfystudy_platform_targets)
  # Visual Studio only: make the program the startup project, so F5 runs it.
  set_property(DIRECTORY ${CMAKE_SOURCE_DIR} PROPERTY VS_STARTUP_PROJECT comfystudy)
endfunction()
```

**使用生成的文件时：**

- 它们是**生成物**，放在 `build/` 里，**不要提交进 Git**（原因见第 8 节），也不要手工修改：下次生成会被覆盖。想改工程结构（比如增加源文件），修改 `CMakeLists.txt`，然后重新运行 `cmake --preset windows-vs`；在 Visual Studio 里直接“生成”时，`ZERO_CHECK` 也会替你重新生成并提示重新加载。
- 这个解决方案和命令行的 `windows-debug`、`windows-release` 用的是不同的构建目录（`build/windows-vs` 与 `build/windows-debug`、`build/windows-release`），可以并存。

> **备注：不生成解决方案，直接“打开文件夹”。** Visual Studio 原生支持 CMake 项目，也可以直接读取 `CMakeLists.txt` 和 `CMakePresets.json`，完全不需要上面的解决方案文件。前提是安装了“适用于 Windows 的 C++ CMake 工具”组件（它随“使用 C++ 的桌面开发”工作负载一起安装，自带 CMake 和 Ninja）：
>
> 1. 启动 Visual Studio，在起始窗口选择“打开本地文件夹”（或者菜单 文件 → 打开 → 文件夹），选中项目根目录，也就是包含 `CMakeLists.txt` 的那个目录。
> 2. Visual Studio 识别出 `CMakePresets.json` 后，工具栏上会出现配置预设的下拉框。选择 `windows-debug`（不要选 `windows-vs`）。它会自动运行一次“配置”，进度显示在“输出”窗口的 CMake 页签里。
> 3. 菜单 生成 → 全部生成，快捷键 Ctrl+Shift+B。
> 4. 在启动项下拉框里选 `comfystudy.exe`，按 F5 调试运行，或者 Ctrl+F5 不调试直接运行。
>
> 这种方式使用 Visual Studio 自带的 CMake 和 Ninja，并且会自动设置好 MSVC 环境，所以不需要开发者命令提示符；构建目录就是 `build/windows-debug`，和命令行用的是同一个。

## 6. 验证

**第二次构建什么也不做：**

```text
cmake --build --preset windows-debug
```

```text
ninja: no work to do.
```

**改一个头文件，重编哪些文件。** 在 `src/version.h` 末尾加一个空格，再构建：

```text
[1/3] Building CXX object CMakeFiles\comfystudy_core.dir\src\greeting.cpp.obj
[2/3] Linking CXX static library comfystudy_core.lib
[3/3] Linking CXX executable bin\comfystudy.exe
```

只重编了 `greeting.cpp`，**没有** `main.cpp`：因为只有 `greeting.cpp` 包含了 `version.h`。改回去再构建一次，然后在 `src/greeting.h` 末尾加一个空格再构建：

```text
[1/4] Building CXX object CMakeFiles\comfystudy_core.dir\src\greeting.cpp.obj
[2/4] Linking CXX static library comfystudy_core.lib
[3/4] Building CXX object CMakeFiles\comfystudy.dir\src\main.cpp.obj
[4/4] Linking CXX executable bin\comfystudy.exe
```

两个源文件都包含了 `greeting.h`，所以两个都重编。可以直接看 Ninja 记住了什么：在 `build\windows-debug` 目录里运行 `ninja -t deps <目标文件>`，输出的就是从 `/showIncludes` 记下的依赖：

```text
CMakeFiles/comfystudy_core.dir/src/greeting.cpp.obj: #deps 2, deps mtime ... (VALID)
    ../../src/greeting.h
    ../../src/version.h
CMakeFiles/comfystudy.dir/src/main.cpp.obj: #deps 1, deps mtime ... (VALID)
    ../../src/greeting.h
```

这两份列表和上面的实验完全吻合。

**Debug 与 Release 的运行库不同。** 用 `dumpbin /dependents` 查看可执行文件依赖哪些 DLL：

```text
dumpbin /dependents build\windows-debug\bin\comfystudy.exe
```

Debug 版依赖的是带 `D` 的调试运行库：

```text
MSVCP140D.dll
VCRUNTIME140_1D.dll
VCRUNTIME140D.dll
ucrtbased.dll
KERNEL32.dll
```

Release 版依赖的是发布运行库：

```text
MSVCP140.dll
VCRUNTIME140.dll
VCRUNTIME140_1.dll
api-ms-win-crt-runtime-l1-1-0.dll
api-ms-win-crt-math-l1-1-0.dll
api-ms-win-crt-stdio-l1-1-0.dll
api-ms-win-crt-locale-l1-1-0.dll
api-ms-win-crt-heap-l1-1-0.dll
KERNEL32.dll
```

这正是 `/MDd` 和 `/MD` 的区别：前者链接调试版 C/C++ 运行库（带额外检查，只能在装了 Visual Studio 的机器上运行），后者链接发布版。第 0.5 章会回到这些 DLL。

**调试信息文件。** Debug 构建会在 `bin` 里生成 `comfystudy.pdb`（还有增量链接用的 `comfystudy.ilk`），Release 构建没有 `.pdb`：

```text
build\windows-debug\bin
  comfystudy.exe
  comfystudy.ilk
  comfystudy.pdb
```

**两种构建互不干扰：** `build\windows-debug` 和 `build\windows-release` 是两个独立的目录，构建 Release 不会碰 Debug 的任何文件。

## 7. 技术资料

- MSVC `cl` 19.51.36256（Visual Studio 18，工具集 14.51.36231）；CMake 4.3.1（项目最低要求 3.25）；Ninja 1.13.2。
- `CMakePresets.json` 的 `"version": 6` 需要 CMake 3.25 或更高。
- Visual Studio 生成器：`Visual Studio 18 2026`（MSBuild 18.9.1，自动选用的 Windows SDK 为 10.0.28000.0）；它生成的解决方案是 `.slnx` 格式。
- 设计取舍：
  - **生成器选 Ninja。** 它比 Visual Studio 生成器启动快，增量构建只重做必要的部分，并且天然适合命令行。
  - **用静态库放业务代码。** 以后测试程序和主程序都链接同一个 `comfystudy_core`，代码只编译一次。
  - **C 运行库选动态（`/MD`）。** 后面要用的 libtorch 等库也是动态运行库，必须一致。
  - **被否决：** GNU make / nmake 手写规则。每个库都要自己写包含路径和链接选项；而 CMake 对后面要接入的 vcpkg、libtorch、ggml、ONNX Runtime 都有现成的支持。
- 只支持 MSVC，是为了先把一件事做好；`cmake/platform/windows.cmake` 里直接对非 MSVC 报错。
  - **构建文件按系统分文件。** 新增一个系统只需要加一个 `cmake/platform/<系统名>.cmake`，不用改顶层 `CMakeLists.txt`。C++ 源码里和系统有关的地方也一样，在 0.4 起用 `#if defined(_WIN32)` 包起来，别的系统走 `#else` 分支并给出 `#error`。

## 8. 常见问题与坑

- **`'cl' 不是内部或外部命令`，或者 CMake 找不到编译器。** 没有在开发者命令提示符里运行。换成开始菜单里的 x64 Native Tools 命令提示符。
- **Git 自带的 `link.exe` 抢先了。** 如果 `PATH` 里有 Git 的 `usr\bin` 目录，里面有一个同名的 `link` 命令（创建硬链接的小工具）。开发者命令提示符把 MSVC 的目录放在最前面所以没问题，但在别的终端里手敲 `link` 可能会运行错的那个。
- **换了生成器之后报错。** `build/windows-debug` 里的缓存记住了第一次用的生成器。如果之后想换成别的生成器，要先删掉整个 `build/windows-debug` 目录再重新配置。
- **`cmake --preset windows-debug` 说找不到预设。** 必须在包含 `CMakePresets.json` 的项目根目录运行。
- **备注里的“打开文件夹”看不到 CMake 的任何东西。** 通常是安装时没有勾选“适用于 Windows 的 C++ CMake 工具”。到 Visual Studio Installer 里修改安装，勾上后重启 Visual Studio。
- **同一个构建目录不能换生成器。** `build/windows-vs` 用的是 Visual Studio 生成器，`build/windows-debug` 用的是 Ninja，不要把一个预设的 `binaryDir` 指向另一个预设的目录。换生成器要换目录，或者先删掉旧的构建目录。
- **不要把生成的解决方案和项目文件提交进 Git。** 这几十个文件是 CMake 按你这台机器的情况生成的：一个只有两个源文件的项目，仅 `comfystudy.vcxproj` 就有约 58 KB，里面有约 60 处本机的绝对路径（项目放在哪个盘哪个目录）、几百处对本机 CMake 安装位置的引用、写死的 Windows SDK 版本（例如 10.0.28000.0）。换一台机器、换一个目录，甚至换一个 CMake 版本，这些内容都要变，提交进去的文件在别人那里要么打不开、要么每次生成后都是一堆无关的改动。更重要的是它们和 `CMakeLists.txt` 是**同一份信息的两个副本**：在 Visual Studio 里改了工程设置，下次重新生成就丢了；改了 `CMakeLists.txt` 忘了重新生成，两边就不一致。正确做法是只提交 `CMakeLists.txt` 和 `CMakePresets.json`，每个人自己运行 `cmake --preset windows-vs`。
- **较旧的 Visual Studio 可能打不开 `.slnx`。** 它是新格式，据我所知旧版本不一定支持；遇到时用对应版本的生成器名字（例如 `Visual Studio 17 2022`）生成传统的 `.sln`。
- **F5 找不到可执行文件或运行了别的项目。** 用解决方案时确认启动项目是 `comfystudy`（不是 `ALL_BUILD`）；打开文件夹时确认启动项下拉框选的是 `comfystudy.exe`。
- **改了头文件却没重编。** 极少见，通常是系统时间不对，或者文件的修改时间被改乱；运行 `cmake --build --preset windows-debug --target clean` 后再构建，可以排除。
- **警告变成了错误。** `/WX` 把任何警告都当成错误。读报错信息，修掉警告，不要关掉 `/WX`。
