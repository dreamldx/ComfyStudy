## 2. 背景与概念

**为什么需要包管理器。** 后面要用的库很多：解析 JSON、发 HTTP 请求、测试框架……每个库都自己下载、编译、配置包含路径和链接选项，既费事又容易出错。**vcpkg** 是微软做的 C/C++ 包管理器：你说“我要 curl”，它负责下载源码、用当前编译器编译好，放到固定的目录里。

**manifest 模式。** vcpkg 有两种用法：经典模式把库装在全局，所有项目共用；**manifest 模式**则在项目根目录放一个 `vcpkg.json`，列出这个项目需要哪些库，库装在项目自己的目录里。依赖写在项目里，克隆下来就能重现同样的环境，所以本教程用 manifest 模式。

**baseline（基线）。** vcpkg 的“库目录”是一个 Git 仓库，每个提交对应一套库的版本。`vcpkg.json` 里的 `builtin-baseline` 写的就是一个提交号，意思是“版本以这一刻的目录为准”。有了它，同一个 `vcpkg.json` 在不同的时间、不同的机器上装出的版本是一样的。

**triplet（三元组）。** triplet 描述“为什么平台编译”：CPU 架构、操作系统、库是静态还是动态。我们用 `x64-windows`：64 位 Windows，**库是动态库（DLL），C 运行库也是动态的（`/MD`）**。这和第 0.1 章 `CMakeLists.txt` 里选的运行库一致，混用不同的运行库会出现难以排查的错误。

**toolchain file（工具链文件）。** CMake 支持在配置时读一个“工具链文件”，用来改变它找编译器和库的方式。vcpkg 提供了 `vcpkg.cmake`，把它指给 CMake 之后：

1. 每次配置时，它先运行 `vcpkg install`，按 `vcpkg.json` 把缺的库装好；
2. 它让 CMake 的 `find_package` 去 vcpkg 装好的目录里找库；
3. 它在每个可执行文件构建完成后，把需要的 DLL 复制到可执行文件旁边（“app-local” 部署）。

**find_package 与导入目标。** 库装好之后，`find_package(CURL CONFIG REQUIRED)` 让 CMake 读取库自带的配置文件，得到一个**导入目标** `CURL::libcurl`。把它写进 `target_link_libraries`，CMake 就自动处理：头文件路径、要链接的 `.lib`，而且 Debug 与 Release 会自动选对应版本的库文件。我们不需要手写任何路径。

**日志库 spdlog。** 程序越来越大，到处用 `std::cout` 打印就不够用了：没有级别（哪些是普通信息，哪些是警告和错误）、没有统一的格式、没法按需关掉。spdlog 是 C++ 里使用最广的日志库之一：用 `{}` 格式化（`spdlog::info("加载了 {} 个变量", 3)`）；有 trace、debug、info、warn、error、critical 几个级别，可以设一个阈值，低于阈值的日志直接丢掉；日志写到哪里由 **sink（输出目标）** 决定，可以是控制台、文件，也可以是一个字符串流（测试里很有用）。它依赖格式化库 fmt，vcpkg 会自动一起装好。

**CLI11。** 程序要接受命令行参数（`--verbose`、`--config 文件` 这类），自己写循环判断很快会写乱：缺少参数值怎么办、拼错了选项怎么提示、`--help` 的文字谁来写。CLI11 是 C++ 里最常用的命令行解析库之一：先声明有哪些选项，它负责解析、类型转换、报错和生成帮助信息；它还能读配置文件（INI 或 TOML 语法），并且让命令行的值优先于配置文件的值。下一章我们就用它一次解决命令行和配置文件。vcpkg 里它是一个小的静态库，**不需要 DLL**，我们的代码链接它之后，它就编进了可执行文件里。

**GoogleTest。** 上一章的测试宏只是原理演示。GoogleTest 是 C++ 里使用最广的测试框架，提供 `TEST(套件, 名字)` 来定义测试，`EXPECT_*` 和 `ASSERT_*` 来检查：

| 宏 | 失败时 |
|---|---|
| `EXPECT_EQ(a, b)` | 记录失败，**继续**运行这个测试 |
| `ASSERT_EQ(a, b)` | 记录失败，**立即结束**这个测试 |

一般用 `EXPECT_*`；当后面的检查依赖前面的结果（比如先要确认指针非空才能解引用）时用 `ASSERT_*`。

## 4. 关键代码讲解

**依赖清单 `vcpkg.json`。** 项目名、版本、依赖列表和基线：

<!-- src: vcpkg.json#L1-L12 -->
```json
{
  "name": "comfystudy",
  "version-string": "0.0.0",
  "dependencies": [
    "nlohmann-json",
    "curl",
    "gtest",
    "spdlog",
    "cli11"
  ],
  "builtin-baseline": "93ad765c7b66ab9ce97469ec23a90b15c3a14ee5"
}
```

`builtin-baseline` 不用手写：运行 `vcpkg x-update-baseline --add-initial-baseline`，它会把当前库目录的提交号填进去。

**预设里接入 vcpkg。** 新增一个隐藏预设 `windows-vcpkg`，指定工具链文件、triplet 和安装目录，然后让 `windows-base`（Debug、Release 共用）和 `windows-vs` 都继承它：

<!-- src: cmake/presets/windows.json#L4-L22 -->
```json
    {
      "name": "windows-vcpkg",
      "hidden": true,
      "toolchainFile": "$env{VCPKG_ROOT}/scripts/buildsystems/vcpkg.cmake",
      "cacheVariables": {
        "VCPKG_TARGET_TRIPLET": "x64-windows",
        "VCPKG_INSTALLED_DIR": "${sourceDir}/vcpkg_installed"
      }
    },
    {
      "name": "windows-base",
      "hidden": true,
      "inherits": "windows-vcpkg",
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/build/${presetName}",
      "cacheVariables": {
        "CMAKE_EXPORT_COMPILE_COMMANDS": "ON"
      }
    },
```

`$env{VCPKG_ROOT}` 读的是环境变量 `VCPKG_ROOT`，即 vcpkg 的安装目录，所以路径不写死。`VCPKG_INSTALLED_DIR` 把库装到项目下的 `vcpkg_installed` 目录，**所有预设共用这一份**（里面 Debug 与 Release 的库并存，见后面“验证”）。

**CMake 里找库并链接。** 怎么找库和系统有关，所以 `find_package` 写在平台文件 `cmake/platform/windows.cmake` 里：在 Windows 上库由 vcpkg 提供，用 `CONFIG` 模式找它安装的配置文件。顶层 `CMakeLists.txt` 只负责把导入目标链接到核心库。用 `PUBLIC`，因为 `net_probe` 的头文件和使用它的代码都会用到这些库，依赖要传递给链接 `comfystudy_core` 的程序和测试：

<!-- src: cmake/platform/windows.cmake#L14-L18 -->
```cmake
# Third-party libraries come from vcpkg (see vcpkg.json); the preset points CMake at its toolchain file.
find_package(nlohmann_json CONFIG REQUIRED)
find_package(CURL CONFIG REQUIRED)
find_package(spdlog CONFIG REQUIRED)
find_package(CLI11 CONFIG REQUIRED)
```

<!-- src: CMakeLists.txt#L27-L31 -->
```cmake
# Everything except main() lives in a static library, so tests can link it too.
add_library(comfystudy_core STATIC src/greeting.cpp src/net_probe.cpp)
target_include_directories(comfystudy_core PUBLIC src)
target_link_libraries(comfystudy_core PUBLIC comfystudy_options
  nlohmann_json::nlohmann_json CURL::libcurl spdlog::spdlog CLI11::CLI11)
```

CLI11 的 CMake 包名是 `CLI11`，导入目标是 `CLI11::CLI11`。vcpkg 把它编译成一个静态库（`CLI11.lib`），链接时由这个导入目标自动带上；它用到了 Windows 的 `CommandLineToArgvW`，所以可执行文件会多依赖系统的 `SHELL32.dll`，这是 Windows 自带的，不用管。

**用到三个库的代码。** `net_probe` 只有三个函数：返回 libcurl 的版本，把一段 JSON 文本解析后再用紧凑格式输出，以及用 CLI11 从一串命令行参数里取出 `--name` 的值：

<!-- src: src/net_probe.h#L1-L16 -->
```cpp
#pragma once

#include <string>
#include <vector>

// Version string of the linked libcurl, e.g. "libcurl/8.23.0 ...".
std::string CurlVersion();

// Parses `text` as JSON and returns it re-serialized in compact form.
// Throws nlohmann::json::parse_error when `text` is not valid JSON.
std::string JsonRoundTrip(const std::string& text);

// Parses `args` (the command-line arguments after the program name) with CLI11 and returns the
// value of "--name", or "" when it is not given.
// Throws CLI::ParseError when an argument is not recognized.
std::string NameFromArgs(const std::vector<std::string>& args);
```

<!-- src: src/net_probe.cpp#L1-L21 -->
```cpp
#include "net_probe.h"

#include <curl/curl.h>

#include <CLI/CLI.hpp>
#include <nlohmann/json.hpp>

std::string CurlVersion() { return curl_version(); }

std::string JsonRoundTrip(const std::string& text) {
  return nlohmann::json::parse(text).dump();
}

std::string NameFromArgs(const std::vector<std::string>& args) {
  CLI::App app;
  std::string name;
  app.add_option("--name", name);
  std::vector<std::string> reversed(args.rbegin(), args.rend());  // CLI11 wants them reversed
  app.parse(reversed);
  return name;
}
```

CLI11 的用法分三步：建一个 `CLI::App`；用 `add_option("--name", name)` **声明**有一个叫 `--name` 的选项，解析结果会写进变量 `name`；最后 `parse`。参数不认识（比如 `--bogus`）或者缺少值时，`parse` 抛出 `CLI::ParseError`。有一个容易踩的地方：`parse` 接收 `std::vector<std::string>` 时要求参数是**倒过来**排的（最后一个参数在最前面），所以我们先反转一次；如果直接把 `main` 的 `argc`、`argv` 交给它（`app.parse(argc, argv)`），就不用反转。

注意头文件 `net_probe.h` 里**没有**包含 curl 或 nlohmann 的头文件，只用标准库的 `std::string`。这样使用它的代码不会被第三方头文件拖慢编译，也不会被它们污染。

新的测试 `test_deps.cpp` 检查三个库真的能用：

<!-- src: tests/test_deps.cpp#L1-L23 -->
```cpp
#include <string>

#include <CLI/CLI.hpp>
#include <gtest/gtest.h>

#include "net_probe.h"

TEST(Deps, CurlReportsItsVersion) {
  EXPECT_EQ(CurlVersion().rfind("libcurl/", 0), 0u);
}

TEST(Deps, JsonRoundTripIsCompact) {
  EXPECT_EQ(JsonRoundTrip("{ \"a\" : [1, 2] }"), std::string("{\"a\":[1,2]}"));
}

TEST(Deps, CliParsesAnOption) {
  EXPECT_EQ(NameFromArgs({"--name", "Ada"}), "Ada");
  EXPECT_EQ(NameFromArgs({}), "");
}

TEST(Deps, CliRejectsAnUnknownOption) {
  EXPECT_THROW(NameFromArgs({"--bogus"}), CLI::ParseError);
}
```

`rfind("libcurl/", 0) == 0` 是“以 `libcurl/` 开头”的惯用写法；`0u` 的 `u` 让右边是无符号数，和 `rfind` 返回的 `size_t` 类型一致，比较的两边类型相同。

**日志的测试。** `test_logging.cpp` 检查 spdlog 的两个基本行为：`{}` 格式化，以及低于阈值的日志被丢掉。它不让日志写到控制台，而是自己建一个 logger，把输出目标（sink）接到一个字符串流上，再用 `[%l] %v`（只输出级别和消息）这个格式，这样就能在测试里检查日志的内容：

<!-- src: tests/test_logging.cpp#L1-L36 -->
```cpp
#include <memory>
#include <sstream>
#include <string>

#include <gtest/gtest.h>
#include <spdlog/sinks/ostream_sink.h>
#include <spdlog/spdlog.h>

namespace {

// A logger that writes into a string, with a pattern that prints only the level and the message.
std::shared_ptr<spdlog::logger> MakeStringLogger(std::ostringstream& out) {
  auto sink = std::make_shared<spdlog::sinks::ostream_sink_mt>(out);
  auto logger = std::make_shared<spdlog::logger>("test", sink);
  logger->set_pattern("[%l] %v");
  return logger;
}

}  // namespace

TEST(Logging, FormatsWithBraces) {
  std::ostringstream out;
  auto logger = MakeStringLogger(out);
  logger->info("loaded {} variables from {}", 3, "a.env");
  EXPECT_NE(out.str().find("[info] loaded 3 variables from a.env"), std::string::npos);
}

TEST(Logging, LevelsBelowTheThresholdAreDropped) {
  std::ostringstream out;
  auto logger = MakeStringLogger(out);
  logger->set_level(spdlog::level::warn);
  logger->info("hidden");
  logger->warn("shown");
  EXPECT_EQ(out.str().find("hidden"), std::string::npos);
  EXPECT_NE(out.str().find("[warning] shown"), std::string::npos);
}
```

注意警告级别在输出里的名字是 `warning`，而不是 `warn`。

**登记测试。** `tests/CMakeLists.txt` 现在链接 `GTest::gtest_main`（它提供 `main` 函数，所以测试文件里不用再写），并用 `gtest_discover_tests` 让 CTest 发现程序里的**每一个 `TEST`**：

<!-- src: tests/CMakeLists.txt#L1-L14 -->
```cmake
find_package(GTest CONFIG REQUIRED)
include(GoogleTest)

# Builds tests/<name>.cpp into a program that links the core library and GoogleTest, and
# registers every TEST in it with CTest (one CTest entry per TEST).
function(add_comfystudy_test name)
  add_executable(${name} ${name}.cpp)
  target_link_libraries(${name} PRIVATE comfystudy_core GTest::gtest_main)
  gtest_discover_tests(${name})
endfunction()

add_comfystudy_test(test_greeting)
add_comfystudy_test(test_deps)
add_comfystudy_test(test_logging)
```

`gtest_discover_tests` 是在**构建之后**运行一次测试程序（`--gtest_list_tests`）来列出有哪些测试，所以新加 `TEST` 只需重新构建，不用改 CMake。

**库装在哪里。** 项目下多了一个 `vcpkg_installed` 目录（它是生成的，不提交进 Git）：

```text
vcpkg_installed\x64-windows
  bin        发布版的 DLL
  debug      调试版：debug\bin（DLL）、debug\lib（.lib）
  include    头文件（Debug 和 Release 共用）
  lib        发布版的 .lib
  share      CMake 配置文件等
  tools
```

Debug 与 Release 的库**并存**，而且文件名不同：

```text
lib\libcurl.lib             debug\lib\libcurl-d.lib
bin\libcurl.dll             debug\bin\libcurl-d.dll
```

调试版带 `-d` 后缀。我们没有写过任何一个库文件名，CMake 通过导入目标 `CURL::libcurl` 根据当前配置自动选择。

**DLL 自动复制到可执行文件旁边。** 构建时 vcpkg 的工具链文件（`VCPKG_APPLOCAL_DEPS` 默认开启）会把运行需要的 DLL 复制过去：

```text
build\windows-debug\bin\
  comfystudy.exe  test_greeting.exe  test_deps.exe  test_logging.exe
  libcurl-d.dll   libzd.dll   spdlogd.dll   fmtd.dll   gtest.dll   gtest_main.dll
```

Release 目录里的则是 `libcurl.dll`、`libz.dll`、`spdlog.dll`、`fmt.dll`、`gtest.dll`、`gtest_main.dll`。CLI11 没有 DLL（它是静态库，已经编进了可执行文件）。用 `dumpbin /dependents` 看 `comfystudy.exe` 依赖什么，Debug 版多了 `libcurl-d.dll`，Release 版多了 `libcurl.dll`：

```text
Debug:    libcurl-d.dll  SHELL32.dll  KERNEL32.dll  MSVCP140D.dll  VCRUNTIME140_1D.dll  VCRUNTIME140D.dll  ucrtbased.dll
Release:  libcurl.dll  KERNEL32.dll  MSVCP140.dll  VCRUNTIME140.dll  VCRUNTIME140_1.dll  api-ms-win-crt-*.dll
```

`comfystudy.exe` 不依赖 GoogleTest，**也还不依赖 spdlog**：现在主程序没有用到它，下一章用上之后，它的依赖里才会多出 spdlog 的 DLL。zlib 是 libcurl 自己的依赖，fmt 是 spdlog 的依赖，所以它们出现在 `bin` 里，但不在 exe 的依赖列表里（它们是间接依赖）。

`SHELL32.dll` 是 Windows 自带的，CLI11 取命令行参数时用到它；Release 版的链接器丢掉了没人调用的 CLI11 代码，所以列表里看不到它。

**CMake 记住了什么。** 查看 `build\windows-debug\CMakeCache.txt`，里面有预设写入的这些变量：

```text
CMAKE_TOOLCHAIN_FILE:FILEPATH=<VCPKG_ROOT>/scripts/buildsystems/vcpkg.cmake
VCPKG_TARGET_TRIPLET:STRING=x64-windows
VCPKG_INSTALLED_DIR:PATH=<项目>/vcpkg_installed
VCPKG_APPLOCAL_DEPS:BOOL=ON
```

**每次配置都会运行 `vcpkg install`。** 再运行一次 `cmake --preset windows-debug`，会再看到 `Running vcpkg install`，但因为什么都不缺，几百微秒就结束了。往 `vcpkg.json` 里加一个依赖，下次配置才会真的去安装它（见练习）。

## 7. 技术资料

- vcpkg（版本 2026-10-29）；库目录基线 `93ad765c7b66ab9ce97469ec23a90b15c3a14ee5`。装出的版本：nlohmann-json 3.12.0（port 版本 2）、curl 8.23.0（特性 `core,sspi,ssl`，用 Schannel）、GoogleTest 1.18.0、spdlog 1.17.0（依赖 fmt 12.2.1）、CLI11 2.7.2、zlib 1.4。
- triplet `x64-windows`：动态库、动态 C 运行库。要全静态的话是 `x64-windows-static`，这需要把 `CMAKE_MSVC_RUNTIME_LIBRARY` 也改成静态；本项目后面要用的 libtorch 等是动态库，所以保持动态。
- 设计取舍：
  - **manifest 模式，不用经典模式。** 依赖写在项目里，可重现；经典模式的全局安装会让不同项目互相影响。
  - **用基线固定版本。** 不写基线的话，会随你机器上 vcpkg 目录的状态变化，别人克隆之后可能装出不同的版本。
  - **所有预设共用一个 `vcpkg_installed`。** Debug 与 Release 的库本来就并存，共用可以避免装两遍；代价是 `build/windows-vs`（Visual Studio 生成器）也用同一份。
  - **测试框架选 GoogleTest。** 使用最广、资料最多，自带 GoogleMock（后面要模拟 LLM 的 HTTP 响应时会用到），Visual Studio 的 Test Explorer 能识别它。
  - **日志库选 spdlog。** 使用最广、用 `{}` 格式化（和 C++20 的 `std::format` 写法接近）、线程安全，并且有异步日志和多种输出目标；通过 vcpkg 一行就能装好。vcpkg 给出了两个 CMake 目标：`spdlog::spdlog`（编译成库，需要 DLL）和 `spdlog::spdlog_header_only`（纯头文件，不需要 DLL）。我们用前者，因为每个源文件只需要包含声明，编译更快。
  - **命令行与配置文件解析选 CLI11。** 接口直观，错误信息和 `--help` 现成，并且自带配置文件支持（INI 和 TOML，优先级也由它保证：命令行高于配置文件）。它在 vcpkg 里是一个小的静态库，不增加 DLL。备选有 cxxopts（更轻，但没有配置文件支持）、Boost.Program_options（成熟，但要多装三十多个 Boost 包和一个 DLL）。
  - **被否决：** 手工下载库放进项目目录（版本和编译选项没有保证，还要自己管理 Debug/Release 两套）；用 Git 子模块（每个库要自己写构建规则）。
- 第 0.5 章会回头处理 DLL：现在 vcpkg 的 app-local 步骤替我们复制了，到时我们要**验证**复制得对不对，并保证程序只加载自己目录里的 DLL。

## 8. 常见问题与坑

- **CMake 报 `Could not find a package configuration file provided by "nlohmann_json"`。** 通常是 CMake 没有用 vcpkg 的工具链文件：构建目录是在接入 vcpkg **之前**配置的，缓存里没有工具链文件，而 CMake 不会在已有的缓存上改工具链。给配置命令加 `--fresh`（`cmake --preset windows-debug --fresh`），或者删掉整个 `build\windows-debug` 目录再配置。
- **`VCPKG_ROOT` 没有设置。** 预设里的 `$env{VCPKG_ROOT}` 会变成空，CMake 找不到工具链文件。x64 Native Tools 命令提示符会设置 `VCPKG_ROOT`，指向 Visual Studio 自带的 vcpkg；也可以自己设一个环境变量，指向你单独安装的 vcpkg。两者都行，只要 `vcpkg.json` 里的基线在该 vcpkg 的库目录里能找到。
- **第一次配置像卡住了。** 它在编译 curl 等库，几分钟没有输出是正常的。联网是必须的；网络不好时 vcpkg 下载源码会失败，重试即可。
- **`vcpkg.json` 里的名字写错。** 包名是 `nlohmann-json`（连字符），而 CMake 里的包名是 `nlohmann_json`（下划线）；curl 的 CMake 包名是 `CURL`。两套名字不一样，以 vcpkg 配置输出末尾打印的用法提示为准。
- **链接时找不到库，或者运行时找不到 DLL。** 前者一般是漏了 `target_link_libraries`；后者看可执行文件旁边有没有 DLL（vcpkg 的复制发生在构建的最后一步），或者重新构建一次。
- **`CHECK_EQ` 之类的老写法编译不过。** 本章起测试都用 GoogleTest 的 `TEST` 和 `EXPECT_*`，`tests/check.h` 已经删除。
- **新加的 `TEST` 没出现在 `ctest -N` 里。** `gtest_discover_tests` 是在构建之后才列出测试的，先重新构建。
