- 一句话目标：设计并实现上下文的组装：一个纯函数把工具、系统提示词（几节）、历史对话、状态块、最新用户消息和本回合已产生的消息按固定的顺序拼成发给模型的内容（与具体协议无关，同样的输入得到逐字节相同的输出）；有 token 预算，放不下时整个回合地丢最老的历史，工具调用与结果永远成对；历史按频道放在 `History` 接口后面；`--show-context` 打印每一部分占多少 token，并与服务实际数的对比；把不变的开头标出来（Anthropic 的缓存标记）并读出三种回答里的缓存读数，让提示缓存真的命中

## 1. 本章目标与成果

到 1.5 为止，发给模型的内容是循环里顺手拼出来的：系统提示词是一个字符串，历史是 `messages`，工具是 `options.tools`，Skill 目录混在一个工具的说明里。对话一长，没人知道请求里到底有什么、每一部分占多少，也没有“放不下怎么办”的答案。这一章把它做成一个明确的步骤：每次请求前，用一个纯函数按固定的顺序把几个来源的内容组装起来，并且知道每一部分的大小。做完后你会得到：

- **`BuildContext`：** 纯函数，输入各个来源的内容，输出一个与协议无关的 `Context`。顺序固定：工具定义，系统提示词，历史，状态块，最新用户消息，本回合已经产生的消息。同样的输入得到逐字节相同的输出，不读时钟，不读随机数。
- **系统提示词由几节拼成：** 你的 `--system`、几句规则、Skill 目录，各是一节，标题写在方括号里。
- **状态块：** 会话当下的情况（频道、今天的日期和星期、已加载的 Skill、这一回合最多几步），放在最新用户消息的前面，不写进历史。以后图像节点的句柄、记忆检索的结果也往这里加节。
- **日期：** 模型没有时钟，也没有日历；不告诉它，它只能按训练时的印象猜今天几号。状态里有一行 `date: 2026-11-27 Friday (UTC-08:00)`，由调用者读时钟、传进来，所以 `BuildContext` 仍然是纯函数。
- **`History` 接口：** 每个频道一份历史，先做内存实现。聊天在每个回合前读它，只有以回答结束的回合才写回去；`/reset` 清空当前频道。
- **token 预算：** 默认是窗口减去回答的空间再减一成，也可以用 `context_budget_tokens` 设定。放不下时，从最老的回合开始整个丢，工具调用和结果永远成对；丢光历史还放不下，就在发请求之前报错，写明各部分的大小。
- **估算：** 没有分词器，用一个很粗的启发式；真实请求对照后，误差写在第 6 节。
- **`--show-context`：** 每个请求前打印一张各部分的表，回答后打印服务实际数的 `input_tokens`，用来对照。
- **Skill 目录搬了家：** 目录从 `load_skill` 的说明移到系统提示词，“已加载”移到状态块；两个 Skill 工具的说明从此固定不变。
- **提示缓存：** 把请求里不变的开头标出来，让服务留着它，下一个请求直接读，不再重新算，价钱也低得多。Anthropic 要在请求里写标记，这一章写在系统提示词的末尾、历史的末尾和最新的用户消息上；OpenAI 的两种接口是自动的。三种回答里的缓存读数（读了多少、写了多少）都读出来，`--show-context` 会打印。设置 `prompt_cache` 可以关掉。
- 新设置 `context_budget_tokens` 和 `prompt_cache`，新选项 `--show-context`。73 个新测试，现在一共 372 个，其中三份黄金文件。

## 2. 背景与概念

**为什么要组装。** 一个请求由几类内容构成，来源各不相同：工具来自运行时，系统提示词来自配置和 Skill，历史来自存储，状态来自会话，最新消息来自用户。如果各处自己往一个对象里塞，顺序、重复、大小就没人管。把它们交给一个函数：来源只管把自己的内容交上来，顺序和预算由这个函数定。

**顺序：稳定的在前，变化的在后。** 工具、系统提示词、历史，每个请求之间几乎一样，放前面；状态每一步都可能变，最新的用户消息每个回合都变，放后面。服务的缓存只认“从开头起完全相同的一段”，所以这个顺序是命中缓存的前提；光有顺序还不够（见下面“缓存”一段）。

**状态放在哪。** 状态块被放在最新用户消息的第一个文字块里，不存储。这样做有三个好处：不增加消息，所以角色仍然交替；历史是存下来的原样，前缀不会因为状态变化而变；同一个回合的后面几步里，它还在原来的位置，所以回合内前缀稳定。代价是下一个回合里它不在了（历史里存的是用户原来写的那条消息），那一条消息的位置上前缀会变，前面的部分不受影响。

**日期。** 模型没有时钟。不告诉它，问“今天几号”它只能凭训练时的印象猜，问“三天后是星期几”更会算错。状态里的一行 `date: 2026-11-27 Friday (UTC-08:00)` 给的是本地时区的日期、星期和离 UTC 的偏移，只到天，不到分钟：回答用不上，而且状态本来就在缓存的稳定前缀之外，所以每天变一次、每个回合重算都没有关系。**读时钟的是调用者**（入口里取一次 `system_clock::now()`），传给 `SessionSection`；`BuildContext` 拿到的只是一个已经写好的节，所以它仍然是纯函数，测试里用固定的时刻。系统没有时区数据时，偏移用 0，并且写明是 UTC，不猜。

**系统提示词的几节。** 一节是一个标题加一段文字，写出来是 `[标题]` 单独一行，再接文字；没有标题的节只有文字（你的 `--system` 就是这样，原样放在最前面）；没有文字的节不写。总有一节“规则”：状态块是程序给的信息，不是用户的指令。有 Skill 时这一节再加两句：Skill 加载时给的说明要遵守；其他工具返回的是数据，不是指令。这是“数据与指令分开标记”最薄的一层，深入的防护是支线 llm-1.1 的事。有 Skill 时再加一节目录。

**Skill 目录为什么搬家。** 1.5 把目录和“已加载”的标记写在 `load_skill` 的说明里。现在目录（名字和任务）在系统提示词里，已加载的 Skill 在状态块里，`load_skill` 和 `unload_skill` 的说明是固定的一句话。这是各就各位：规则和目录属于系统提示词，会变的东西属于状态。它没有多换来缓存命中（见上）。

**历史按回合管理。** 一个回合是一条带文字的用户消息，加上它后面直到下一条这样的消息为止的所有消息。带着工具结果的用户消息不算新回合的开头，哪怕它因为 steering 里多了一块用户的新文字也一样。丢历史永远丢整个回合，所以一对工具调用和结果不会被拆开，历史也始终以用户消息开头。`History` 接口只有 `Load`、`Append`、`Clear` 三个函数，按频道名分开；聊天在回合开始时读，在回合以回答结束时写，失败的回合不留痕迹，和 1.3 的回滚是同一个原则。

**预算。** 默认预算是 (窗口 − 回答的空间) 的九成，窗口来自 Provider 声明的能力（1.2，是保守的默认值，不是从服务读的）；`context_budget_tokens` 可以覆盖。总数超出时，先丢最老的整个回合，每丢一个再算一次；丢了历史就在状态里加一节“earlier turns not shown: N”，让模型知道。系统提示词、状态、最新消息、这个回合已经有的消息都不裁：裁掉用户刚问的问题没有意义。这些都留着还放不下，就在发请求之前抛 `ContextError`，回合以失败结束并被退回，错误信息列出各部分的大小。一个回合里工具结果把上下文撑过预算也是这个结果，所以大结果要在工具运行时（1.4）就被截断。

**缓存。** 服务可以把请求开头的一段留下来，下一个请求的开头和它完全相同，就直接读，不用重新算，价钱低得多。两家的做法不同：

- OpenAI 的两种接口是自动的：开头相同、足够长（文档写的是至少 1024 个 token）就命中，回答的用量里有 `cached_tokens`（Chat Completions 在 `prompt_tokens_details` 里，Responses 在 `input_tokens_details` 里）。我们只需要把不变的东西放在前面，并且把这个数读出来。
- Anthropic 要你自己标出“到这里为止可以留着”：在块上写 `cache_control`，一个请求最多四个标记。缓存按“工具，系统提示词，消息”的顺序算前缀，标记之前的所有东西都被留下。回答的用量里分成三个数：`cache_creation_input_tokens`（这次写进去的）、`cache_read_input_tokens`（读出来的），和 `input_tokens`（标记之后没缓存的部分），**总数是三个相加**。写缓存比普通输入贵（文档里 5 分钟的缓存是 1.25 倍），读便宜很多（Sonnet 5.5 是 0.05 倍），缓存默认 5 分钟，每次用到会续期；开头短于一个下限（Sonnet 5.5 是 512 个 token）就不缓存，也不报错。

标记放哪里，是这一章的组装能帮上忙的地方。`Context` 里有一个 `cache_points`：历史的最后一条消息，和最新的用户消息。Anthropic 的请求另外在系统提示词的末尾放一个（没有系统提示词就放在最后一个工具上），所以一个请求最多三四个标记。为什么是这几处：

- 系统提示词的末尾，覆盖工具和系统提示词，这是最大、最稳定的一段，每个回合、每一步都读它。
- 历史的末尾，覆盖已经存下的所有回合：下一个回合的历史就是它加上这个回合的消息，开头相同。
- 最新的用户消息（含状态块）：同一个回合的下一步，请求就是它加上模型的回答和工具结果。

这也是状态块不存进历史的又一个理由：历史里存的是用户原来写的那条消息，下一个回合的前缀才和这一次的历史末尾对得上。状态块在“最新消息”里，只会让这一条消息的位置之后不命中，前面的都命中。

两件事缓存管不了：一是缓存要求前缀逐字节相同，工具定义变了，从工具往后的一切都要重新写，所以加载或卸载一个 Skill，整个请求只好重新缓存一次（下面第 6 节有真实的数）；二是缓存只在有人重复用的时候才划算：第一次写缓存比不缓存贵，一个只问一次的聊天是净亏损，`prompt_cache = off` 就是为这个。

**估算。** 没有本地分词器，估算很粗：每四个字母、数字、空白算一个 token，每个标点算一个，每个非 ASCII 字符算一个。它和服务数的不会一样：不同服务的分词器不同，服务自己加的东西（角色标记之类）在请求里看不见。所以它只用来看哪一部分占地方，和让请求离窗口远一点；偏差见第 6 节的对照。计数函数可以替换，测试里用“一个字节一个 token”，让裁剪的测试确定。

**不做的事。** 真正的分词器和摘要压缩（支线 llm-1.4）；记忆和检索的内容（支线 llm-2.x，这一章只留下“往状态里加一节”的插槽）；一小时的缓存和预热、OpenAI 新版本模型的显式缓存断点（这一章用默认的）；图片（1.8）、发言者格式（1.7）；SQLite 的实现（1.9）；提示注入的防护（llm-1.1）。

## 4. 关键代码讲解

**输入和输出。** 来源只管交内容：`system` 和 `state` 是节的列表，`history` 是已经存下的回合，`latest` 是用户这次的消息，`turn` 是这个回合到现在为止产生的消息。`count` 是计数函数，空的时候用估算。

```cpp
// A titled piece of text. In the system prompt and in the state, a section is written as "[title]" on a
// line of its own and then the text; a section without a title is the text alone; a section without text
// is left out.
struct Section {
  std::string title;
  std::string text;
};

// How many tokens a text takes. The default is EstimateTokens; tests pass an exact one.
using TokenCounter = std::function<std::size_t(const std::string&)>;

struct ContextInputs {
  std::vector<llm::ToolDefinition> tools;
  std::vector<Section> system;        // joined with blank lines into Conversation::system
  std::vector<llm::Message> history;  // the turns that are stored, before this one
  std::vector<Section> state;         // changes from request to request: put in front of `latest`
  llm::Message latest;                // the user's message that started this turn (role kUser)
  std::vector<llm::Message> turn;     // what this turn has produced so far (the model's calls, the results)
  std::size_t budget_tokens = 0;      // 0: no limit
  TokenCounter count;                 // empty: EstimateTokens
  std::size_t per_message_tokens = 4;  // what a message costs besides its content (roles, separators)
};
```

```cpp
// A user message that starts a turn: one without tool results (a message with results continues the turn
// of the call it answers, even when it also carries a new message of the user's).
bool StartsTurn(const llm::Message& message) {
  if (message.role != llm::Role::kUser) return false;
```

```cpp
std::size_t EstimateTokens(const std::string& text) {
  std::size_t plain = 0;  // letters, digits and white space: about four to a token
  std::size_t marks = 0;  // ASCII punctuation: about one token each (JSON, code and tool definitions are full of it)
  std::size_t others = 0;  // every other character (Chinese, accents, symbols): about one token each
  for (const char c : text) {
    const auto byte = static_cast<unsigned char>(c);
    if (byte >= 0x80) {
      if ((byte & 0xC0u) != 0x80u) ++others;  // the first byte of a character
    } else if (std::isalnum(byte) != 0 || std::isspace(byte) != 0) {
      ++plain;
    } else {
      ++marks;
    }
  }
  return (plain + 3) / 4 + marks + others;
```

```cpp
std::string FormatDate(std::chrono::system_clock::time_point now, std::chrono::minutes utc_offset) {
  using namespace std::chrono;
  static const char* const kWeekdays[] = {"Sunday", "Monday", "Tuesday", "Wednesday", "Thursday", "Friday", "Saturday"};
  const sys_days day = floor<days>(now + utc_offset);
  const year_month_day date{day};
  const unsigned weekday_index = weekday{day}.c_encoding();  // 0 is Sunday
  const auto two = [](unsigned n) { return (n < 10 ? "0" : "") + std::to_string(n); };
  const long long offset_minutes = utc_offset.count();
  const long long magnitude = offset_minutes < 0 ? -offset_minutes : offset_minutes;
  return std::to_string(static_cast<int>(date.year())) + "-" + two(static_cast<unsigned>(date.month())) + "-" +
         two(static_cast<unsigned>(date.day())) + " " + kWeekdays[weekday_index] + " (UTC" + (offset_minutes < 0 ? "-" : "+") +
         two(static_cast<unsigned>(magnitude / 60)) + ":" + two(static_cast<unsigned>(magnitude % 60)) + ")";
}

std::chrono::minutes LocalUtcOffset(std::chrono::system_clock::time_point now) {
  try {
    return std::chrono::duration_cast<std::chrono::minutes>(std::chrono::current_zone()->get_info(std::chrono::floor<std::chrono::seconds>(now)).offset);
  } catch (const std::exception&) {
    return std::chrono::minutes(0);  // no time zone data on this system: say UTC rather than guess
  }
}

Section SessionSection(const SessionInfo& info, std::chrono::system_clock::time_point now, std::chrono::minutes utc_offset) {
  std::string text = "channel: " + info.channel + "\ndate: " + FormatDate(now, utc_offset);
  if (info.has_skills) {
    std::string loaded;
    for (const std::string& name : info.loaded_skills) loaded += (loaded.empty() ? "" : ", ") + name;
    text += "\nloaded skills: " + (loaded.empty() ? std::string("none") : loaded);
  }
  if (info.max_steps > 0) text += "\nsteps: at most " + std::to_string(info.max_steps) + " model calls for one answer";
  return {"session state", text};
}
```

```cpp
  EXPECT_EQ(first.conversation.system, second.conversation.system);
  ASSERT_EQ(first.tools.size(), second.tools.size());
  // everything up to the message that carried the state of the first request is the same
  const std::size_t shared = before.history.size();
  ASSERT_GE(second.conversation.messages.size(), shared);
  for (std::size_t i = 0; i < shared; ++i) {
    EXPECT_EQ(Flat(first.conversation.messages[i]), Flat(second.conversation.messages[i])) << "message " << i;
  }
  // the state of the first request is not in the second one's history
  for (const llm::Message& message : second.conversation.messages) {
    for (const llm::Block& block : message.blocks) {
      if (const auto* text = std::get_if<llm::TextBlock>(&block)) EXPECT_FALSE(Contains(text->text, "step 1"));
    }
  }
}
```

**裁剪。** 用“一个字节一个 token”的计数：丢整个回合，不拆开调用和结果，历史以用户消息开头；带着结果和 steering 文字的用户消息不算回合的开头；状态里写着丢了几个回合；没有预算就一个也不丢；放不下时抛 `ContextError`，信息里有预算和各部分的大小；这个回合已经产生的消息不裁。

**估算。** `EstimateTokens` 的已知值（空文本、ASCII、汉字、混合、标点、空格），文本变长从不变短；`DefaultBudget` 是窗口减去回答的空间再减一成，回答比窗口还大时是 1，不是 0（0 的意思是不限制）；`context_budget_tokens` 不是整数时的错误指出设置的名字。

**历史。** `tests/test_history.cpp`：没写过的频道是空的，追加的内容按顺序读回，频道互不影响，`Clear` 只清一个频道，`Load` 返回的是拷贝。

**循环里。** 原有的循环测试一个没改，全部通过（没有计划）。有计划时：请求里有各节系统提示词，状态块在用户消息前面，对话里存的消息不含状态；每一步都重新问节，所以变化在下一个请求里可见；小预算时旧回合不在请求里，却还在对话里；放不下的上下文在发请求之前让回合失败，传输里没有任何请求，对话被退回；钩子收到 `ContextBuilt`，没有计划时不会收到。和 Skill 一起：第一步里 `load_skill`，第二步的状态里写着 `loaded skills: calc`，系统提示词里的目录两步相同。

**聊天里。** 只有以回答结束的回合进历史，失败的回合什么也没留下；每个回合从存下的历史开始；`/reset` 只清当前频道；系统各节和状态在请求里；预算小时旧回合不在请求里、却还在历史里；没有设置预算时用 Provider 的窗口。

**缓存。** `tests/test_llm_cache.cpp`：开着缓存时系统提示词变成带标记的块，关着时完全没有变化（即使有缓存点）；没有系统提示词时标记在最后一个工具上，有系统提示词时在系统提示词上，不在工具上；缓存点上的消息，标记在它的最后一个块，不在第一个块；工具结果也能带标记；被略掉的消息把标记一起带走，其余的位置不变；一个请求里标记不超过四个；另外两种接口的请求没有任何变化；三种回答里缓存读数的解析（Anthropic 的总数是三个数相加，没有缓存字段时不变；Chat Completions 和 Responses 的 `cached_tokens`；回答里没有的数不编出来）。组装里：缓存点是历史的最后一条和最新的一条，丢了旧回合后下标跟着变，`FormatContext` 把它们写出来。循环里：开着缓存时请求里标记在系统提示词、历史末尾和用户的文字上（不在状态块上），关着时没有标记。设置：`prompt_cache` 默认开，`off` 关，别的值是指出设置名字的错误。

**日期。** `FormatDate`：已知的日期和星期（1970-01-01 是星期四，一个闰日 2028-02-29 是星期二），偏移把日期推过午夜（东八区把 11 月 28 日 20 点推到 29 日，西八区把 3 点拉回 27 日，半小时偏移的时区也对，跨年也对）；同一个时刻两次得到同一段文字。`LocalUtcOffset` 的结果在时区的范围里。`SessionSection`：只有频道和日期；开着 Skill 时有已加载的 Skill 和步数上限；只有日期这一行取决于时钟，换一天其余完全不变。

**改动检验。** 把下面八处各临时改坏一次，对应的测试都会失败，然后改回：

- 状态块放到用户文字的后面：`TheOrderIsToolsSystemHistoryStateLatestAndTheTurn`、`TheStateIsInFrontOfTheLatestMessage...` 和两份黄金文件失败。
- 裁剪每次只丢一条消息：`WhenItDoesNotFitTheOldestTurnsAreLeftOutWhole`、`AUserMessageThatCarriesResultsDoesNotStartATurn`、`TheStateSaysHowManyTurnsAreNotShown` 和裁剪后的黄金文件失败。
- 带着工具结果的用户消息也算回合的开头：`AUserMessageThatCarriesResultsDoesNotStartATurn` 和裁剪相关的测试失败。

- 消息上不写标记：`AnthropicCache.TheLastBlockOfEachMessageAtACachePointCarriesAMarker`、`AToolResultCanCarryTheMarker`、`NeverMoreThanFourMarkers` 和循环里的 `TurnContext.WithCachingOnTheRequest...` 失败。
- Anthropic 的总数不加上缓存读的和写的：`AnthropicCache.TheTokensReadFromAndWrittenToTheCacheAreInTheTotal` 失败。
- 历史的末尾不算缓存点：`BuildContext.TheCachePointsAreTheLastMessageOfTheHistoryAndTheLatestMessage`、`TheFormatNamesTheCachePoints`、两份黄金文件和循环里的缓存标记测试失败。

- 日期不加上偏移：`FormatDate.TheOffsetMovesTheDateAcrossMidnightInBothDirections` 失败。
- 状态里不写日期：`SessionSection` 的三个测试失败。

**构建。** 清理后重建，`/W4 /WX` 下 0 个警告。

**真实运行：估算和服务数的对比。** 同一个问题（有 Skill 的聊天，一句“只回答 ok”），一个请求，三种请求格式：

| | 估算 | 服务数的 input_tokens |
|---|---|---|
| anthropic | 472 | 831 |
| openai-chat | 472 | 618 |
| openai-responses | 472 | 618 |

估算都比服务数的少，Anthropic 少 359，OpenAI 兼容的模型少 146。一部分是服务自己加的东西：只发这一句问题（没有工具、没有系统提示词、没有状态）时，Anthropic 数 18，OpenAI 兼容的模型数 38，这是角色标记之类。其余的差距我没有查它具体是什么。这些都是请求里看不见的开销，估算管不了它。

要看估算本身准不准，要拿没有这些干扰的文本比。我取了五段文字（一段英文许可证、一段中文、一段中英混合的 README、一段 JSON、一段 C++ 头文件的注释和代码），各放进系统提示词，用服务数的 token 数减去没有这段文字时的数，得到这段文字的净数，再和最终的估算比：

| 文字 | 估算 | OpenAI 兼容模型 | Claude |
|---|---|---|---|
| 英文（1065 字节） | 293 | 240 | 494 |
| 中文（107 个非 ASCII 字符） | 136 | 101 | 165 |
| 中英混合 | 531 | 390 | 654 |
| JSON（301 字节） | 124 | 123 | 146 |
| C++（1500 字节） | 465 | 367 | 462 |

对 OpenAI 兼容的模型，估算高出两成多到三成半（JSON 几乎一样）；对 Claude，估算低一成五到四成（C++ 几乎一样）。第一版估算把标点也按四个字符一个 token 算，JSON 那一段只有服务数的六成多，这对工具定义（全是 JSON）尤其不利，所以改成标点各算一个，JSON 就对上了。**但这只是五段文字、一天里、每种协议一个模型的结果**，不是服务的规格。预算里的一成余量和可设置的预算，是给这个误差留的。

**真实运行：缓存（Anthropic）。** 一段 6000 字节的系统提示词，三个回合，每个只要一个词的回答；开着缓存和关着缓存各一次，数是同一个请求的不同读法：

| 回合 | 服务数的总数 | 读自缓存 | 新写进缓存 | 关着缓存时的总数 |
|---|---|---|---|---|
| 1 | 2430 | 0 | 2426 | 2430 |
| 2 | 2677 | 2381 | 292 | 2815 |
| 3 | 2900 | 2626 | 270 | 3103 |

第一个回合两边的总数相同，后两个回合不完全一样：两次运行里模型的回答（和它的思考块）不同，进了历史的东西就不同。缓存不改变请求，只改变怎么算钱。按文档里的倍数（写 1.25，读 0.05，都是对普通输入的倍数；Sonnet 5.5 的读是 0.05）算，三个回合折合普通输入的 4000 个 token 左右，关着缓存是 8350 个，不到一半；第一个回合本身更贵（约 3040 对 2430），回本是在第二个回合。这是按文档算的，我没有看账单。

**真实运行：缓存（OpenAI 的两种接口）。** 同样的系统提示词，同样的三个回合（这两个服务是 `config.ini` 里配置的，不一定是 OpenAI 自己的）：

| 接口 | 回合 1 | 回合 2 | 回合 3 |
|---|---|---|---|
| openai-chat（总数，读自缓存） | 1803，0 | 1816，0 | 1830，1664 |
| openai-responses（总数，读自缓存） | 1802，1152 | 1816，1792 | 1830，1792 |

两个服务都在报 `cached_tokens`，数是 128 的整数倍（1664 是 13 个 128）。Chat 的前两个回合没有命中，第三个才命中；Responses 的第一个回合就读到了 1152：同样的系统提示词几分钟前刚用过，缓存还在。缓存是尽力而为的，不是保证。这两个服务要多少个 token 才开始缓存、缓存多久，我没有去量。

**真实运行：加载一个 Skill 会让缓存重写一次。** 同一段系统提示词，带 `--tools`，前两个回合各问一个词的问题，第三个回合让模型加载 `calculator` 再算 2+3，之后再问两个回合（Anthropic）：

| 请求 | 总数 | 读自缓存 | 新写进缓存 |
|---|---|---|---|
| 回合 1 | 3186 | 0 | 3182 |
| 回合 2 | 3204 | 3044 | 156 |
| 回合 3，第 1 步 | 3234 | 3130 | 100 |
| 回合 3，第 2 步（`load_skill` 之后，工具列表多了 `add`） | 3499 | 0 | 3336 |
| 回合 3，第 3 步 | 3571 | 3336 | 0 |
| 回合 4 | 3595 | 3252 | 339 |
| 回合 5 | 3614 | 3521 | 89 |

第 2 步一个字也没有读到：工具列表变了，缓存按“工具，系统提示词，消息”的顺序算前缀，工具变了，后面全都对不上，3336 个 token 重新写了一遍。下一步（第 3 步）就又读到了。回合 2 只读到 3044，不是 3182：缓存里留着的是上一个回合的“工具加系统提示词”和“带状态块的最新消息”，下一个回合里那条消息已经没有状态块了（状态块不进历史，新的状态块也不一样），前缀在那里断开，之前的（工具加系统提示词）仍然命中。这就是设计时让状态块不进历史的原因。

**真实运行：推理块。** 历史里带着思考块的回答，估算怎么算是个问题。上面“先看效果”里第二个请求，历史里只有一问一答，估算算了 735 个 token（回答带着的思考块按整个内容、包括很长的签名算了），服务数的整个请求才 511 个，高估了。更早的一次运行里，我只按思考块里能读到的文字算，估算只有服务数的三到五成，低估了很多，服务那几次显然数了思考块。我没能弄清服务什么时候数多少，所以估算选择安全的一边：按整个内容算，宁可多丢一个回合，也不要请求放不下。

**真实运行：日期。** 命令行里问“今天几号、星期几”，状态里有日期这一行，模型答对了；这台机器的时区是 UTC-08:00，答案是本地的日期：

```text
> [context] step 1: about 72 tokens (budget 179079)
  system: rules             1 items,     25 tokens
  state                     1 items,     24 tokens
Today is Friday, November 27, 2026.
[context] the service counted 83 input tokens (about 72 were estimated); 0 read from the cache; 0 written to it
```

没有这一行时，模型没有办法知道这个日期。

**真实运行：预算放不下。** 有工具时预算 700 个 token，第二个回合里模型加载了 Skill，上下文变成大约 717 个，放不下，回合在请求发出之前失败，信息里有各部分的大小，并且被退回；第三个回合照常，历史里还有第一个回合：

```text
> [tool] load_skill {"name":"calculator"}
[tool] load_skill -> The Skill "calculator" is loaded. Tools you can use now: add.
...
error: the context needs about 717 tokens, more than the budget of 700 even without the history (tools 364, system: rules 69, system: skills 79, history 0, state 55, input 19, turn 131)
> ...
Your name is Mei.
```

**真实运行：Skill 目录搬家以后，模型还选得对吗。** 对比 1.5 里的两个问题，各用三种格式问一次。“等 300 毫秒”：三种格式的模型都自己加载了 `timer` 再调用 `sleep`。“用 shutdown 工具”：`openai-responses` 这次加载了 `playground`，调用 `shutdown`，被拒绝，并解释说它被归类成危险工具（1.5 里它没有去加载）；`anthropic` 同样；`openai-chat` 里配置的那个模型仍然说“没有 shutdown 工具”，没有去加载。一次运行不能说明变好了，只能说明目录放在系统提示词里没有变坏；让模型选对 Skill 要靠目录里的说明写得清楚，那是支线 llm-4.3 的内容。

## 7. 技术资料

- 没有新的依赖。
- 提示缓存（Anthropic 的文档，2026-11-28 读的）：一个请求最多四个 `cache_control` 标记（类型只有 `ephemeral`，可以加 `ttl`），也有一个放在请求顶层、自动放在最后一个可缓存的块上的写法，这一章用的是显式的标记，因为我们的历史前面那条用户消息在下一个回合里少了状态块，按文档的规则推断，下一个回合什么也对不上（这种写法我没有实测）；每个标记最多往前查 20 个位置；开头的下限因模型而异（Sonnet 5.5 是 512 个 token，Sonnet 5 是 1024，一些别的模型 2048 或 4096）；默认缓存 5 分钟，每次用到免费续期；写 1.25 倍，读 0.1 倍（Opus 5.5 和 Sonnet 5.5 是 0.05 倍）；思考块不能直接带标记，但是传回去时一起缓存。工具、系统提示词、消息的顺序是前缀的顺序，改了前面的，后面的缓存都失效。
- 提示缓存（OpenAI 的文档，开发者站点的镜像页，一部分我没能逐字核对，下面只写页面里明确有的和我实测到的）：默认开着，不用写标记；前缀要完全相同才命中，工具的名字、说明、模式和顺序也要相同；新版本的模型下限是 1024 个可见 token，更早的模型下限随请求的设置而变；Responses 的 `usage.input_tokens_details.cached_tokens`，Chat Completions 里我实测是 `usage.prompt_tokens_details.cached_tokens`。
- 设计取舍：
  - **`RunTurn` 仍然在一个 `Conversation` 上工作，加一个可选的 `ContextPlan`。** 历史只在回合的两头用。被否决：让 `RunTurn` 直接读写 `History`（要改签名、二十多个循环测试和回滚，收益只是少拷贝一次）；把组装放进 Provider（协议无关的目标就落空了）。
  - **状态放在最新用户消息的第一个文字块。** 被否决：单独一条用户消息（连续的用户消息各个服务的处理不一致）；放进系统提示词（状态一变整个前缀都变）。
  - **按整个回合丢历史，丢光还放不下就报错。** 被否决：按条数丢（会拆开工具调用和结果）；用摘要代替（支线 llm-1.4）；也裁当前回合（模型会忘了用户刚问的问题）。
  - **估算用启发式，计数函数可以替换。** 被否决：把每个请求回报的 `input_tokens` 当校准（要保存状态，组装就不是纯函数了）；引入分词库（依赖大，换个模型就不准）。
  - **Anthropic 用显式的缓存标记，不用顶层的自动标记。** 自动标记放在请求的最后一个块，缓存的前缀里有带状态块的那条用户消息，它在下一个回合里没有状态块了，按文档的规则推断，下一个回合读不到东西（我没有实测）。显式的标记放在系统提示词末尾和历史末尾，前缀才对得上。被否决：自动标记（上面的原因）；每条消息都放标记（上限是四个，也没有意义）。
  - **缓存开关默认开。** 被否决：默认关（多数聊天会重复用同一段开头，该用上）。代价是只问一次的会话多付约 25% 的写入费，所以有一个 `prompt_cache` 设置。
  - **工具仍然放在请求的 `tools` 字段里，不把工具定义写成文字放进状态或历史。** 写成文字的好处只有一个：加载或卸载 Skill 时不改变前缀，缓存不用重写。代价是模型要通过一个通用的 `call_tool` 间接调用，调用的准确度可能下降（没有测过），服务端也不再按 Schema 约束参数；放在状态里还要每个回合重新为这些文字付写缓存的钱。而加载一个 Skill 只让缓存重写一次，下一步就又读到了。所以被否决；如果会话里要反复加载卸载很多 Skill，再回头做这个实验。
  - **规则一节总是有，两三句话；有 Skill 时多两句。** 状态块每个请求都有（至少有频道和日期），所以说明“状态是程序给的”的那一句也总要有。被否决：不加（“数据不是指令”的标记就没有落脚处）；加很长的行为准则（改变每个聊天的行为，不是这一章的事）。
  - **日期由调用者读时钟，不由 `BuildContext` 读。** 这样 `BuildContext` 仍然是纯函数，测试里用固定的时刻。被否决：在 `BuildContext` 里读时钟（同样的输入不再得到同样的输出，黄金文件没法写）；把时间也写进去（精确到分钟没有用处，只会让状态每分钟都不一样）。
  - **Skill 目录进系统提示词，“已加载”进状态。** 被否决：保持在 `load_skill` 的说明里（系统提示词只剩 `--system`，“多个来源组装”就很薄）。

## 8. 常见问题与坑

- **估算偏低或偏高都会出事。** 偏低，请求放不下窗口，服务报错，回合失败；偏高，多丢历史。预算里留一成，估算的误差看第 6 节。预算也可以直接设。
- **服务自己加的东西看不见。** 角色标记之类不在你的任何一部分里，也不在估算里（上面的对比里，服务数的总是更大）。比较两个请求的差，比看绝对数更有意义。
- **思考块要不要数。** 见第 6 节：偏高比偏低安全。
- **同一回合里状态每一步都被重新问。** 如果状态函数很慢或有副作用，每一步都会付出。它应该只是读几个变量。
- **工具结果把上下文撑过预算。** 回合会失败。大结果要在工具运行时里截断（1.4 的 `tool_result_max_bytes`），不能指望裁历史。
- **窗口来自 Provider 的保守默认值。** 不是从服务读的，所以默认预算很大，在普通对话里永远用不上；要看到裁剪，用 `context_budget_tokens` 设小。
- **开头太短就不缓存，而且不报错。** Sonnet 5.5 的下限是 512 个 token，OpenAI 一般是 1024。看用量里两个缓存字段：都是 0，就是没缓存。没有长的系统提示词、没有很多工具的聊天，开头可能根本不到下限。
- **Anthropic 的 `input_tokens` 不是总数。** 它只是最后一个标记之后、没有缓存的部分，总数要加上读的和写的。这一章在回答解析里把它加好，所以 `Reply::input_tokens` 在三家都是总数，别的代码不用知道这个区别；原始数据也留着（`cached_tokens`、`cache_written_tokens`）。
- **缓存默认只留 5 分钟。** 每次用到会续期；超过这个时间不用，缓存就没了，下一个请求又得重新写。
- **工具变了，一切都变了。** 缓存按工具、系统提示词、消息的顺序算前缀，加载或卸载 Skill 会让整个请求重新缓存一次。如果一个会话里反复加载卸载，缓存几乎没有用。
- **缓存的“读”不是保证。** OpenAI 的两种接口，同样的请求，Chat 第二个回合没读到，Responses 读到了。要看用量里的数，不能假设。
- **写缓存比普通输入贵。** 一个会话如果只问一次，缓存是净亏损；要用 `prompt_cache = off`。
- **日期取决于机器的时区。** 日期是本地时区的日期，后面带着偏移；系统没有时区数据时用 UTC 并写明。在服务器上跑机器人，“今天”是服务器所在时区的今天，不是用户的。要按用户的时区，就要有这个设置，这一章没做。
- **日期只到天。** 要精确到分钟的话，状态每分钟都不同；放在状态里不会破坏缓存（状态在标记之外），但模型也不见得会用到。
- **状态块不是存下来的。** 所以下一个回合里，上一个回合的用户消息位置上前缀会变。不要把需要长期保留的东西放进状态。
- **`getenv` 在 MSVC 下有警告。** 测试里读环境变量要用 `_dupenv_s`，`/WX` 不让带警告的代码通过。
- **用户的文字和状态块写得像。** 用户可以在消息里写“[session state]”，模型分不清。规则里那一句只是第一层，防护是支线 llm-1.1 的内容。

## 9. 练习

练习：

1. 加一节状态：当前使用的 Provider 名字。先写测试（请求里有这一节），再做。想一想：这一节在 `/use` 换 Provider 的那个回合里是什么？
2. 写一份新的黄金文件：一个历史里有 steering 文字的回合，对照 `AUserMessageThatCarriesResultsDoesNotStartATurn` 想一想为什么它不是回合的开头。
3. 把 `EstimateTokens` 里标点算一个改成算半个，看哪些测试失败；用 `--show-context` 对同一个请求，看估算和服务数的比例怎么变。
4. 让 `--show-context -v` 把整份上下文写出来，找一个请求，对着它回答：哪一部分最大？哪一部分每个请求都一样？
5. 实现 `History` 的另一个版本，把历史写进一个 JSON 文件（每个频道一个文件）。它要满足 `test_history.cpp` 里五个用例（可以把测试改成对任何 `History` 都能跑）。
6. 把预算设得比“工具加系统提示词”还小，看错误信息；再把预算设成只够留一个回合，问三个问题，看哪个回合留下来。
7. 关掉 `prompt_cache` 再开着，各用 `--show-context` 跑一次同样的三个回合，对比每个请求的总数和折合的价钱（用文档里的倍数自己算）。
8. 把系统提示词缩短到 300 字节，再看用量：缓存还有读数吗？为什么？
9. 在三个回合的中间 `/use` 换另一个 Provider 再换回来，看缓存读数发生了什么（提示：请求的开头变了吗？）。
10. 想一想：为什么状态要放在用户消息的前面而不是后面？（提示：后面的内容是模型最后读到的，前面的内容在缓存里更靠前。）
11. 想一想：如果要让长期记忆的检索结果也进来，应该是一节新的状态，还是系统提示词里的一节？它们各自对缓存意味着什么？
12. 在状态里再加一行现在的时间（小时和分钟），用 `--show-context` 看缓存读数变不变，想一想为什么。
13. 让机器人所在的服务器和用户在不同的时区（把机器的时区换一个），问“今天几号”，看答案；怎样让它按用户的时区回答？
