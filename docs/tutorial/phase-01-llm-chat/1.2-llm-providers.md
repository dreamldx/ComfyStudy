# 1.2 LLM 双协议与 Provider 抽象

- 状态：已打 tag ｜ 类型：主线 ｜ tag：`chapter-1.2-llm-providers` ｜ 上一 tag：`chapter-1.1-http-json`
- 所属阶段：[阶段 1：LLM 与对话通道](README.md)
- 一句话目标：命令行里能多轮对话，三种请求格式收在同一个入口后面；消息由文本块和推理块组成，推理块原样保存、原样回传，对话中途可以用 `/use` 换 Provider

## 1. 本章目标与成果

1.1 结束时，程序能问一句、答一句。三种请求格式（OpenAI Chat、OpenAI Responses、Anthropic）各有自己的函数，选哪一种靠配置，`Ask` 里有一个 `switch`。机器人要做的是对话：记住前面说过什么，一轮一轮接着聊，而且不同服务返回的东西不只是文字，还有思考过程留下的、带签名的内容。这一章把这些放进一个统一的模型里。做完后你会得到：

- 一个入口函数 `llm::Generate(transport, provider, conversation, options)`：给它一份配好的 `Provider` 和一段对话，它按 Provider 的协议编出请求、经 `Transport` 发出去、把回答读回来。三种格式不再由调用方挑。
- 内部的消息模型：消息是“角色加一串带类型的块”。本章有两种块：文本块和推理块。工具调用、图片以后各加一种块（1.3、1.8），模型不用改。
- 推理块的保存规则：服务在思考时产生的内容（Anthropic 的 `thinking`、`redacted_thinking`，OpenAI Responses 的 `reasoning` 项）可能带着签名或加密内容，只能由产生它的协议读懂。我们把它原样存下来，下一次请求原样发回，不改、不丢、不拼进正文。
- 命令行对话：`--chat` 读一行问一行，历史放在内存里；`/use <名字>` 在对话中途换 Provider，`/reset` 清空历史，`/exit` 结束，`/help` 列出命令。
- 先读 ai-sdk-cpp 的设计再决定的结果是自己写，理由在第 7 节。

做完以后，可以用同一段对话先跟 Anthropic 聊两句，换到 OpenAI 的 Responses 接着聊，再换回来，换回来时 Anthropic 留下的推理块又会原样发出去。

先看效果（配置文件里已经写好密钥和模型；回答由模型生成，每次不完全一样）。`--chat` 读一行问一行，历史放在内存里，第二问只有带着第一轮的历史才答得出来：

```text
build\windows-debug\bin\comfystudy.exe --chat --llm_provider openai --openai_api chat
> My name is Lin. Reply with one short sentence.
Nice to meet you, Lin.
[info] stopped because: stop; tokens in/out: 41/33
> What is my name? One short sentence.
Your name is Lin.
[info] stopped because: stop; tokens in/out: 61/43
> /exit
```

每个回答后面的 `[info]` 行是日志：模型为什么停下来，以及输入、输出各用了多少 token。第二问的输入 token 比第一问多，因为第二次请求带上了第一轮的整个对话。

再看一个中途换服务的：用 Anthropic 打开推理，问一道要想一想的题，用 `/use` 换到 OpenAI 的 Responses，再换回来：

```text
build\windows-debug\bin\comfystudy.exe --chat --llm_provider anthropic --llm_reasoning high
> Find all positive integers n such that n^2 + 2n + 2 divides n^3 + 5n + 7. Think it through before answering; give the final answer in one sentence.
There are no such positive integers n. (……推导和一张检查 n = 1 到 6 的表……)
> /use openai-responses
now using openai-responses
1 reasoning block(s) in the history come from another protocol and will not be sent
> In one short sentence: what was the question about?
It asked for all positive integers \(n\) such that \(n^2+2n+2\) divides \(n^3+5n+7\).
> /use anthropic
now using anthropic
1 reasoning block(s) in the history come from another protocol and will not be sent
> In one short sentence: what was the answer?
There are no such positive integers n.
> /exit
```

`/use` 之后的两行提示是说：对话里有一个推理块来自另一个协议，这一次请求不会发给它；它还留在历史里，换回原来的协议，又会原样发出去。第 5 节有这个会话的详细说明和三种格式的请求体、响应体。

## 2. 背景与概念

### 2.1 五个概念和它们的关系

这一章反复出现五个词，它们的关系如下：

| 概念 | 回答什么问题 | 是什么 | 在哪里定的 |
|---|---|---|---|
| `Transport` | 字节怎么送出去 | 接口：发一个 POST，拿回状态码和正文。它不知道对面是不是大模型 | 1.1 |
| `Endpoint` | 送到哪里，凭什么 | 数据：`base_url` 和 `api_key` | 1.1 用到，本章挪到 `provider.h` |
| `Protocol` | 用哪种“方言”说话 | 枚举：`kOpenAIChat`、`kOpenAIResponses`、`kAnthropic`。它决定请求和响应的样子 | 1.1 用到，本章挪到 `protocol.h` |
| `Provider` | 一个配好的目标服务 | 数据：名字、`Protocol`、`Endpoint`、模型名、能力声明 | 本章 |
| `Conversation` | 说了什么 | 数据：一段指令加一串消息，消息是角色加一串块 | 本章 |

它们这样接起来，入口只有一个函数：

```text
Generate(transport, provider, conversation, options) -> Reply
  provider.protocol  决定请求怎么编、回答怎么读（llm_wire）
  provider.endpoint  给出地址和认证头
  transport.Post     把编好的请求真正发出去
```

要分清的一点：**公司、协议、Provider 不是一一对应的。** OpenAI 一家有两种协议（Chat Completions 和 Responses）；OpenRouter 这样的网关对外说 Chat Completions；同一种协议可以有好几个 Provider。所以 `Provider` 不是“某家公司”，而是“用哪种协议、连哪个地址、问哪个模型”的一份组合。本章的名字固定为三个：`openai-chat`、`openai-responses`、`anthropic`，它们的设置来自已有的 `openai_*` 和 `anthropic_*`（`openai-chat` 和 `openai-responses` 共用 `openai_*`），不加新的服务配置项。

`Provider` 只是数据，没有虚函数。要换掉的是 `Transport`：测试里让 `Provider` 指向一个按脚本回答的假 `Transport`，就能测整条路径，包括以后的 agent 循环。第 7 节讲为什么这样选。

### 2.2 消息是内容块

字符串装不下一条助手消息。同一次回答里可能先有一段思考，再有一段正文，以后还会有工具调用。所以消息不是字符串，而是**一串带类型的块**：

- `TextBlock`：一段文字。
- `ReasoningBlock`：服务在思考时产生的内容，见下一节。

三种协议在线上表示它们的方式不同：Chat 的 `content` 是一个字符串，Responses 的 `input` 是一串“项”，Anthropic 的 `content` 是一串带 `type` 的块。内部模型取并集，编码和解码时各自转换。第 4.4 节并排看这三种写法。

### 2.3 推理块为什么要原样保存

模型思考时产生的内容，各家的处理方式不一样：

- Anthropic 的 `thinking` 块有一个 `signature` 字段，服务在你把它发回去时校验。`redacted_thinking` 块只有一段加密的 `data`。
- OpenAI Responses 的 `reasoning` 项有 `id`、`summary`，在不让服务端保存对话（`store: false`）时还带加密的 `encrypted_content`。
- OpenAI Chat 的协议里没有推理项。

这些内容对我们是不透明的：我们读不懂，也不该改。所以 `ReasoningBlock` 存着服务给的那一项的原样 JSON（`payload`），外加它来自哪个协议（`origin`）和一段给人看的文字（`visible_text`，只用于显示和日志）。

为什么要保存它，分两种情况。**纯文本的多轮对话里，这些块不是必须的**：本章实测，把 Anthropic 的 thinking 块从第二轮请求里整个去掉，服务照样回答。官方文档说，在工具调用的那一轮，必须把 thinking 块和工具调用一起原样带回，本章没有工具，这一条留到 1.3 验证。所以本章的验证目标是三件事：块被原样存下来；下一次请求里它原样发出，没有被服务拒绝；换到别的协议时它不会被发出去。

### 2.4 换 Provider 时的规则

对话里的推理块只有产生它的协议能读懂。所以编码一次请求时：

- 来源协议和目标 Provider 的协议相同的推理块，原样放回请求里；
- 来源不同的推理块，**这一次请求不编进去**；
- 对话本身不改，那些块还在历史里：换回原来的协议，它们又会被发出去。

`/use` 换 Provider 时，会告诉你历史里有几个块属于别的协议、不会被发送。

### 2.5 能力声明

`Provider` 带一份 `Capabilities`：这个协议能不能保存推理块、一次回答最多多少个 token、上下文窗口多大。机器人以后要根据它选路径（比如不支持的就不要发图片），不在代码里写“如果是某某模型就……”。本章里数值是每种协议的保守默认值，**不是向服务查询来的**，真正用上它们的是后面的章节：1.2 只把位置留好，并用 `keeps_reasoning_blocks` 区分 Chat 和另外两种。

## 4. 关键代码讲解

### 4.1 对话由块组成

文本块和推理块。`ReasoningBlock::payload` 是服务给的那一项，原样存放：

<!-- src: src/conversation.h#L18-L33 -->
```cpp
struct TextBlock {
  std::string text;
};

// A block the service produced while it was thinking: Anthropic's "thinking" and
// "redacted_thinking" blocks, OpenAI Responses' "reasoning" items. It is opaque: it may carry a
// signature or encrypted content that the service checks when it comes back, so `payload` is
// stored exactly as received and sent back exactly as stored. Only the protocol it came from can
// read it.
struct ReasoningBlock {
  Protocol origin;
  json::Value payload;
  std::string visible_text;  // the readable part (if any), for display and logs only
};

using Block = std::variant<TextBlock, ReasoningBlock>;
```

消息是角色加一串块。指令（system prompt）不放在消息里，因为三种协议放它的位置不同：Chat 把它做成第一条消息，Responses 有单独的 `instructions` 字段，Anthropic 有顶层的 `system`。

<!-- src: src/conversation.h#L35-L47 -->
```cpp
enum class Role { kUser, kAssistant };

struct Message {
  Role role;
  std::vector<Block> blocks;
};

// The instruction ("system prompt") is not a message: the three protocols put it in different
// places.
struct Conversation {
  std::string system;  // may be empty
  std::vector<Message> messages;
};
```

回答 `Reply` 里带着助手消息 `message`，所以继续对话只要“追加这条消息，再追加下一条用户消息”。`Text()` 取出所有文本块。

<!-- src: src/conversation.h#L49-L67 -->
```cpp
// How much the model should think before it answers.
enum class Reasoning { kOff, kLow, kMedium, kHigh };

struct Options {
  int max_tokens = 1024;  // upper limit for the answer, counted in tokens
  Reasoning reasoning = Reasoning::kOff;
};

// An answer: the assistant's message (append it to the conversation to continue), why it stopped,
// and what it cost.
struct Reply {
  Message message;          // role kAssistant
  std::string stop_reason;  // in the protocol's own words
  std::optional<long> input_tokens;
  std::optional<long> output_tokens;

  // The generated text: all text blocks of the message, one after the other ("" if it has none).
  std::string Text() const;
};
```

### 4.2 `Provider` 和能力声明

`Endpoint`、`Capabilities`、`Provider` 都是只放数据的结构：

<!-- src: src/provider.h#L19-L36 -->
```cpp
// What a service can do, so that the program picks a path by asking instead of by checking names.
// The numbers are conservative defaults for each protocol (what any current model of that API
// accepts); they are not read from the service.
struct Capabilities {
  bool keeps_reasoning_blocks;  // does the protocol return reasoning blocks that can be sent back?
  int max_output_tokens;
  int context_window;  // in tokens
};

// A configured target: a protocol, an address, a model. Just data; what happens to a request is
// decided by Generate (llm_client.h), which takes a Provider as an argument.
struct Provider {
  std::string name;  // "openai-chat", "openai-responses" or "anthropic"
  Protocol protocol;
  Endpoint endpoint;
  std::string model;
  Capabilities capabilities;
};
```

`MakeProvider` 按名字从设置生成一个 Provider；缺设置时错误信息里写明是哪个设置、对应的环境变量和命令行选项叫什么（1.1 的行为，原样保留）。`Providers` 把三个名字各试一遍，设置不全的跳过。

<!-- src: src/provider.cpp#L39-L57 -->
```cpp
Provider MakeProvider(const config::Values& settings, const std::string& name) {
  Provider provider;
  provider.name = name;
  if (name == "openai-chat" || name == "openai-responses") {
    provider.protocol = name == "openai-chat" ? Protocol::kOpenAIChat : Protocol::kOpenAIResponses;
    provider.model = Required(settings, "openai_model");
    provider.endpoint.base_url = Required(settings, "openai_base_url");
    provider.endpoint.api_key = Required(settings, "openai_api_key");
  } else if (name == "anthropic") {
    provider.protocol = Protocol::kAnthropic;
    provider.model = Required(settings, "anthropic_model");
    provider.endpoint.base_url = Required(settings, "anthropic_base_url");
    provider.endpoint.api_key = Required(settings, "anthropic_api_key");
  } else {
    throw Error("unknown provider \"" + name + "\"; the names are openai-chat, openai-responses and anthropic");
  }
  provider.capabilities = DefaultCapabilities(provider.protocol);
  return provider;
}
```

默认用哪个 Provider，仍由 `llm_provider` 和 `openai_api` 两个设置决定，规则和 1.1 一样：OpenAI 默认用 Chat Completions，`openai_api = responses` 才用 Responses，`llm_provider = anthropic` 时不看 `openai_api`。

<!-- src: src/provider.cpp#L71-L81 -->
```cpp
std::string DefaultProviderName(const config::Values& settings) {
  const std::string& provider = Setting(settings, "llm_provider");
  if (provider == "anthropic") return "anthropic";
  if (provider != "openai") {
    throw Error("llm_provider must be \"openai\" or \"anthropic\", not \"" + provider + "\"");
  }
  const std::string& api = Setting(settings, "openai_api");
  if (api.empty() || api == "chat") return "openai-chat";  // Chat Completions is the default
  if (api == "responses") return "openai-responses";
  throw Error("openai_api must be \"chat\" or \"responses\", not \"" + api + "\"");
}
```

### 4.3 入口：`Generate`

`Generate` 先按协议挑出三个函数（编码、解码、取错误文字），再做 1.1 里 `Ask` 做的那几步：编请求、记日志、经 `Transport` 发出去、检查状态码、读回答。

<!-- src: src/llm_client.cpp#L11-L32 -->
```cpp
  HttpRequest (*build)(const Provider&, const Conversation&, const Options&) = nullptr;
  Reply (*parse)(const std::string&) = nullptr;
  std::string (*error_text)(const std::string&) = nullptr;
  switch (provider.protocol) {
    case Protocol::kOpenAIChat:
      build = openai_chat::BuildRequest;
      parse = openai_chat::ParseReply;
      error_text = openai_chat::ErrorText;
      break;
    case Protocol::kOpenAIResponses:
      build = openai_responses::BuildRequest;
      parse = openai_responses::ParseReply;
      error_text = openai_responses::ErrorText;
      break;
    case Protocol::kAnthropic:
      build = anthropic::BuildRequest;
      parse = anthropic::ParseReply;
      error_text = anthropic::ErrorText;
      break;
  }

  const HttpRequest http_request = build(provider, conversation, options);
```

日志里的请求头先过 `http::Redacted`，密钥不会进日志。状态码不是 2xx 时抛 `llm::Error`，信息里带着服务自己的错误文字；`401` 再加一句提示。传输层的失败（连不上、超时）是 `http::Error`，原样往上抛。

<!-- src: src/llm_client.cpp#L40-L52 -->
```cpp
  const http::Response response =
      co_await transport.Post({http_request.url, http_request.headers, http_request.body});
  spdlog::debug("HTTP {}", response.status);
  spdlog::debug("response body: {}", response.body);

  if (response.status < 200 || response.status >= 300) {
    std::string message = "the service answered HTTP " + std::to_string(response.status) + ": " +
                          error_text(response.body);
    if (response.status == 401) message += " (check the API key)";
    throw Error(message);
  }
  co_return parse(response.body);
}
```

`Generate` 不改传进来的对话，也不替调用方追加回答：要继续对话，调用方把 `reply.message` 和下一条用户消息自己追加进去。`Ask` 现在只是“建一个只有一条用户消息的对话，调用 `Generate`”，所以 1.1 的 `--prompt` 和它的测试都没有变。

### 4.4 三种协议怎么装一段对话

三个 `BuildRequest` 的任务相同：把整段对话编成一个请求。先看 Chat。它没有推理块的位置，只发文字：

<!-- src: src/llm_wire.cpp#L166-L183 -->
```cpp
HttpRequest BuildRequest(const Provider& provider, const Conversation& conversation, const Options& options) {
  json::Value messages = json::Array();
  // The instruction is a message of its own, in front of the others. ("developer" is the newer
  // name; "system" is accepted by every model and by most OpenAI-compatible servers.)
  if (!conversation.system.empty()) {
    json::Push(messages, {{"role", "system"}, {"content", Utf8(conversation.system)}});
  }
  // This format has no place for reasoning blocks: only the text goes out.
  for (const Message& message : conversation.messages) {
    const std::string text = TextOf(message);
    if (!text.empty()) json::Push(messages, {{"role", RoleName(message.role)}, {"content", text}});
  }

  json::Value body = {{"model", provider.model}, {"messages", messages}, {"max_completion_tokens", options.max_tokens}};
  if (options.reasoning != Reasoning::kOff) body["reasoning_effort"] = EffortName(options.reasoning);
  return HttpRequest{WithoutTrailingSlash(provider.endpoint.base_url) + "/chat/completions",
                     JsonHeaders({{"Authorization", "Bearer " + provider.endpoint.api_key}}), json::Dump(body)};
}
```

Responses 的 `input` 是一串“项”：消息是一项，推理也是一项，推理项放在它所属的那条消息前面，原样放回。`store: false` 表示不让服务端保存对话，这时推理项里的内容是加密的，我们自己保存；`include: ["reasoning.encrypted_content"]` 明确要求返回加密的内容（官方文档说不写也是这样，这个写法只是为了兼容保留着，写上没有坏处）。

<!-- src: src/llm_wire.cpp#L211-L238 -->
```cpp
HttpRequest BuildRequest(const Provider& provider, const Conversation& conversation, const Options& options) {
  json::Value input = json::Array();
  for (const Message& message : conversation.messages) {
    // A reasoning item goes in front of the message it belonged to, exactly as it was received.
    for (const Block& block : message.blocks) {
      if (const json::Value* payload = SendablePayload(block, Protocol::kOpenAIResponses)) json::Push(input, *payload);
    }
    const std::string text = TextOf(message);
    if (!text.empty()) json::Push(input, {{"role", RoleName(message.role)}, {"content", text}});
  }

  json::Value body = {{"model", provider.model},
               {"input", input},
               // the API does not accept fewer than 16 output tokens
               {"max_output_tokens", std::max(16, options.max_tokens)}};
  if (!conversation.system.empty()) body["instructions"] = Utf8(conversation.system);  // a field of its own
  if (options.reasoning != Reasoning::kOff) {
    body["reasoning"] = {{"effort", EffortName(options.reasoning)}};
    // Nothing is kept at the service, so the reasoning items come back with their content
    // encrypted, and we keep them ourselves. The documentation says that is the default when
    // nothing is stored and that "include" is only kept for compatibility; asking for it
```

```cpp
HttpRequest BuildRequest(const Provider& provider, const Conversation& conversation, const Options& options) {
  json::Value messages = json::Array();
  for (const Message& message : conversation.messages) {
    // The content is a list of typed blocks; a thinking block goes back exactly as it was received.
    json::Value content = json::Array();
    for (const Block& block : message.blocks) {
      if (const json::Value* payload = SendablePayload(block, Protocol::kAnthropic)) {
        json::Push(content, *payload);
      } else if (const auto* text = std::get_if<TextBlock>(&block)) {
        if (!text->text.empty()) json::Push(content, {{"type", "text"}, {"text", Utf8(text->text)}});
      }
    }
    if (!content.empty()) json::Push(messages, {{"role", RoleName(message.role)}, {"content", content}});
  }

  json::Value body = {{"model", provider.model},
               {"max_tokens", options.max_tokens},  // required here
               {"messages", messages}};
  if (!conversation.system.empty()) body["system"] = Utf8(conversation.system);  // top level, not a message
  if (options.reasoning != Reasoning::kOff) {
    // The models of today decide for themselves whether and how long to think; "effort" is the hint.
    // Without "display" the thinking text comes back empty (only the signature is there).
    body["thinking"] = {{"type", "adaptive"}, {"display", "summarized"}};
    body["output_config"] = {{"effort", EffortName(options.reasoning)}};
  }
  return HttpRequest{WithoutTrailingSlash(provider.endpoint.base_url) + "/v1/messages",
                     JsonHeaders({{"x-api-key", provider.endpoint.api_key}, {"anthropic-version", "2023-06-01"}}),
                     json::Dump(body)};
}
```

### 4.5 推理块的发送规则

编码时，一个块能不能发，只看它的来源协议是不是这次的目标协议：

<!-- src: src/llm_wire.cpp#L120-L124 -->
```cpp
// The payload of a reasoning block, when it can be sent to a service that speaks `protocol`.
const json::Value* SendablePayload(const Block& block, Protocol protocol) {
  const auto* reasoning = std::get_if<ReasoningBlock>(&block);
  return reasoning != nullptr && reasoning->origin == protocol ? &reasoning->payload : nullptr;
}
```

三个 `BuildRequest` 都用它。一条消息里所有能发的块都没有了（比如只有别家的推理块），这条消息就整条不编进请求。`CountForeignReasoning` 数的是反过来的那一类：历史里不会被发出去的块。`/use` 用它提示你。

<!-- src: src/conversation.cpp#L13-L22 -->
```cpp
std::size_t CountForeignReasoning(const Conversation& conversation, Protocol protocol) {
  std::size_t count = 0;
  for (const Message& message : conversation.messages) {
    for (const Block& block : message.blocks) {
      const auto* reasoning = std::get_if<ReasoningBlock>(&block);
      if (reasoning != nullptr && reasoning->origin != protocol) ++count;
    }
  }
  return count;
}
```

文字也要检查：不是合法 UTF-8 的文字在编码时就报 `llm::Error`，不会让坏字节混进请求体：Glaze 写出 JSON 时不检查 UTF-8，不合法的字节会原样发给服务，服务那边才报一个更难懂的错。里面有一个 NUL 字节的文字也报错：它在 UTF-8 里合法，但我们发的文字里不会有，出现就说明输入没有被正确读进来。Windows 控制台默认不是 UTF-8，读进来的中文字节会不合法，这些检查就是为它准备的（`UseUtf8Console` 负责在交互式控制台里把输入改成 UTF-8）。命令行参数（比如中文的 `--system`）同理：Windows 上 `main` 拿到的参数是 ANSI 编码，所以 `options::Arguments` 改从宽字符的命令行读出，转成 UTF-8。

<!-- src: src/llm_wire.cpp#L100-L109 -->
```cpp
const std::string& Utf8(const std::string& text) {
  // A NUL byte is valid UTF-8, but no text we send has one: it means the input was not read right.
  if (text.find('\0') != std::string::npos) {
    throw Error("the text contains a NUL byte (the console did not hand over the input correctly)");
  }
  if (!IsValidUtf8(text)) {
    throw Error("the text is not valid UTF-8 (on a Windows console, switch it to UTF-8 first)");
  }
  return text;
}
```

**中途换 Provider。** 用 Anthropic 打开推理，问一道要想一想的题，换到 OpenAI 的 Responses，再换回来。每一行 `>` 是程序等你输入的提示；回答由模型生成，每次不完全一样：

```text
build\windows-debug\bin\comfystudy.exe --chat --llm_provider anthropic --llm_reasoning high
> Find all positive integers n such that n^2 + 2n + 2 divides n^3 + 5n + 7. Think it through before answering; give the final answer in one sentence.
There are no such positive integers n. (……推导和一张检查 n = 1 到 6 的表……)
> /use openai-responses
now using openai-responses
1 reasoning block(s) in the history come from another protocol and will not be sent
> In one short sentence: what was the question about?
It asked for all positive integers \(n\) such that \(n^2+2n+2\) divides \(n^3+5n+7\).
> /use anthropic
now using anthropic
1 reasoning block(s) in the history come from another protocol and will not be sent
> In one short sentence: what was the answer?
There are no such positive integers n.
```

第一次 `/use` 提示的是 Anthropic 留下的那一个 thinking 块；第二次提示的是网关的 Responses 回答留下的推理项，它来自 Responses，不会发给 Anthropic。换回 Anthropic 以后，第一个 thinking 块又被原样发出去了（见第 6 节的核对）。

**命令。** 输入 `/help` 会列出它们；以 `/` 开头的行都不会发给模型：

```text
/reset       forget the history
/exit        end the chat
/help        show this list

> /foo

```

**出错时。** 故意用错误的设置和输入，看看错误信息（密钥是随便写的假值）。聊天里出错只打印错误，这一轮的提问不记入历史，可以接着问：

```text
> comfystudy --chat --openai_api_key sk-wrong
> hi
error: the service answered HTTP 401: Invalid API key: this is not an OpenRouter API key. ... (check the API key)

> comfystudy --chat --llm_provider anthropic --anthropic_api_key sk-ant-wrong
> hi
error: the service answered HTTP 401: authentication_error: invalid x-api-key (check the API key)

> comfystudy --chat --openai_base_url http://127.0.0.1:1/v1
> hi
error: request failed: Failed to connect to 127.0.0.1:1 after 0 ms: Could not connect to server

> comfystudy --chat --llm_reasoning loud

> comfystudy --chat --prompt hi
error: --chat and --prompt cannot be used together

> comfystudy --chat --openai_model ""
error: setting "openai_model" is not set (config file, environment variable OPENAI_MODEL or --openai_model)

> comfystudy --chat --openai_model "" --anthropic_model ""
error: no provider is configured: set openai_model, openai_api_key and openai_base_url, or anthropic_model, anthropic_api_key and anthropic_base_url
```

前三条是服务的答复和传输失败（和 1.1 一样，状态码不是 2xx 是答复，连不上是 `http::Error`）；后面四条是在发请求之前就检查出的配置问题。输入本身也会被检查：不是合法 UTF-8 的一行，报错以后不会发给模型，下一行照常处理。下面用 `printf` 送进去一个 Latin-1 的 é（字节 `\xe9`），再送一行 `hello`：

```text
printf 'caf\xe9\nhello\n/exit\n' | build\windows-debug\bin\comfystudy.exe --chat --llm_provider anthropic
> error: the text is not valid UTF-8 (on a Windows console, switch it to UTF-8 first)
> Hello! How can I help you today?
[info] stopped because: end_turn; tokens in/out: 10/13
> 
```

`-v` 的日志里，thinking 块的签名是一长串字符，那是服务要的，不是密钥。

**手动核对（要网络和密钥，不进 `ctest`）。** 下面是本章实际做过的，结果见括号：

1. 三个 Provider 各聊三轮（都正常；OpenAI 两种格式连的是兼容网关）。用中文提问得到中文回答（用 Git Bash 的管道输入：`printf '...' | comfystudy.exe --chat`；cmd 和 PowerShell 的管道各有各的编码，没有试）。中文的 `--system` 和 `--prompt` 参数也原样到达请求（`-v` 看请求体）。
2. `--llm_reasoning high`，问一道需要推导的题，`-v` 看第二轮请求：`messages[1]` 里的 thinking 块与第一轮回答里收到的那个逐字段相等，服务返回 200。
3. 上面第 5 节的 `/use` 来回：Anthropic 到 Responses 再回到 Anthropic，三个请求都是 200；发给 Responses 的请求里没有 thinking 块；换回 Anthropic 的请求里又有。
4. **签名实验。** 用一个临时脚本，拿第 2 步里真实的第二轮请求，做三种改动再发给服务：

| 做法 | 结果 |
|---|---|
| 原样发回 | 200 |
| thinking 块的 `signature` 改一个字符 | 400：`messages.1.content.0: Invalid signature in thinking block` |
| 只改 thinking 块里那段摘要文字，签名不变 | 200（这一次） |
| 整个 thinking 块去掉 | 200 |

结论：服务确实校验签名，所以块不能被我们改；纯文本对话里不带它也能回答，所以它真正的用处要等 1.3 的工具调用。只改摘要文字也通过了，但这只是一次的结果，不要据此推断服务从不检查那段文字；`visible_text` 只用来显示。

三项**没有核对**：在交互式的 Windows 控制台里直接键入中文（`UseUtf8Console` 管的就是这个，只用 Git Bash 的管道验证过 UTF-8 的路径，没有在真实控制台里键入试过；请你自己试一次，输入“你好”，看有没有报 UTF-8 或 NUL 的错）；GPT-5 系列在 Chat 协议上小的 `max_tokens` 会不会被隐藏推理用光（没有可用的模型，不当作结论写）；OpenAI Responses 的推理项在官方的 `api.openai.com` 上能不能原样回传（本章只对着 OpenRouter 试过，请求里的 `store` 和 `include` 按官方文档写，没有在官方服务上验证）。

## 7. 技术资料

- 三种协议的官方文档（字段以实测和文档为准）：Anthropic 的 [extended thinking](https://platform.claude.com/docs/en/build-with-claude/extended-thinking)；OpenAI 的[推理指南](https://developers.openai.com/api/docs/guides/reasoning)、[Responses](https://developers.openai.com/api/reference/resources/responses) 和 [Chat](https://developers.openai.com/api/reference/resources/chat) 的接口说明。
- 本章实测的模型：Anthropic 的 `claude-sonnet-5-5`（官方接口）；OpenAI 的两种格式连的是 OpenRouter 上的一个 DeepSeek 模型。结论里凡是“这个模型”，都只对它们成立。
- 设计取舍：
  - **Provider 只是数据，入口是函数。** 备选是三个类各自实现一个 `Provider` 接口，或者一个类加三套“编解码”。选函数加数据，是因为可以替换的东西已经有了：`Transport`。测试里换掉它，整条路径包括以后的 agent 循环都能测，不需要再造一个假 Provider；发请求、检查状态码、报错这些三种协议都一样的步骤，只写在 `Generate` 里一遍。代价是测试脚本要写成线上格式，所以有了 `ScriptedTransport` 的渲染函数。
  - **块只有两种。** 文本块和推理块。图片和工具各自在用到它们的章节加进来，现在没有真实服务能验证它们，预先做出来只会是未经检验的代码。
  - **推理块存原样的 JSON，不拆字段。** 它们对我们不透明，拆成字段就要跟着每家的改动走；存原样，只需要知道它来自哪个协议。
  - **换协议时在编码处丢弃，不改历史。** 在历史里删掉会让换回来时丢信息。
  - **推理的请求写法（Anthropic）。** `claude-sonnet-5-5` 拒绝旧的 `thinking: {type: enabled, budget_tokens}`（400，错误信息要求用 `adaptive` 和 `output_config.effort`）；官方文档说较新的模型都是这个写法，而 4.5 一代的模型只认旧写法，本章不支持它们。
  - **推理的请求写法（OpenAI Responses）。** `reasoning.effort`、`store: false` 加 `include: ["reasoning.encrypted_content"]`。官方文档说，不让服务端保存时，推理项默认带加密内容，`include` 只是为兼容保留；这里仍然写上，因为它没有坏处，也不依赖文档的这个说法。这一组写法只在 OpenRouter 上试过，没有对着 `api.openai.com` 验证。
  - **被否决：直接用现成的库。** 先读了两个都叫 ai-sdk-cpp 的项目的头文件和源码，没有编译试用：
    - ClickHouse 的 ai-sdk-cpp：同步阻塞的接口；HTTP 层是内部的类，没有可以注入的地方，绕过了 1.1 的 `Transport`（取消、错误分类、密钥脱敏）；OpenAI 只调 Chat Completions，没有 Responses；内容块只有文本、工具调用、工具结果三种，Anthropic 的解析只认 `text` 和 `tool_use`，`thinking` 块会被丢掉，签名也就丢了。
    - mhdimo 的 ai-sdk-cpp：用 Boost.Asio 的协程，有 `ReasoningPart`（带 `signature`），也有 Responses；但用的是自己的 `Task<>`，HTTP 走 Beast，JSON 用 `boost::json`，CI 配置里只看到 Ubuntu 和 macOS，没有看到 Windows；它还带了工具循环、MCP、记忆，这些正是 1.3 到 1.9 要自己写的内容。
    - 借鉴的有三点：消息是内容块的 `variant`；`signature` 和 `redacted_data` 这样的字段；把 HTTP 放到接口后面，让测试换成假的。
  - **名字固定为三个，设置沿用已有的。** 同一种协议同时只能配一个服务。同时配几个同协议的服务，留给 1.7 的组合根。
  - **没做：** 流式（支线 llm-1.4）、重试和降级（支线 llm-1.3）、上下文窗口的管理（1.6）、持久化（1.9）、图片和工具块。

## 8. 常见问题与坑

下面每一条都写明了核对到哪一步：没有注明的，是在真实服务上试过的；注明的，只在脚本测试里试过或没有试。

- **模型自己决定要不要思考。** 自适应模式下，`--llm_reasoning high` 只是提示。简单的问题得不到 thinking 块，回答里没有推理块是正常的；要看到它，问一个需要推导的题。
- **thinking 块的文字默认是空的。** 不带 `display: summarized` 时，`thinking` 字段是空字符串，只有签名。程序里加了这个字段，`visible_text` 才有内容；它只用于显示和日志，不要拿它当原文。
- **旧的 `budget_tokens` 写法会被直接拒绝。** 网上的示例大多是 `thinking: {type: enabled, budget_tokens: N}`，在 `claude-sonnet-5-5` 上返回 400。换成 `adaptive` 加 `output_config.effort`。
- **签名被校验，一个字符都不能错。** 改了 `signature` 的一个字符，请求就是 400。所以推理块只能整块原样存、原样发；也不要把它序列化再反序列化时顺手“规范化”。（改动摘要文字没有被拒绝，但别指望总是这样。）
- **别的协议的推理块不发。** 推理块只有产生它的协议认得，所以 `/use` 换协议后，别家的块这一次不会被编进请求，历史里它们还在。没有拿真实服务试过把它们发错协议会怎样，这里按设计不发。
- **OpenRouter 的 Chat 响应里有额外字段。** 兼容网关在 `message` 里加了 `reasoning` 和 `reasoning_details`（即使没打开推理），这不是 Chat Completions 的字段。本章不读它们：Chat 协议不产生推理块，所以用这种网关时，它们的“思考”不会被保存。1.3 的工具调用要用到思考时，要回头看这一点。
- **回答里可能一个文字块都没有。** 比如思考用光了 `max_tokens`，回答里只有推理块。`--chat` 会提示“no text”，并且不把这一轮记入历史。这条处理只在脚本测试里复现过，真实服务上没有触发过。
- **失败的那一问不要留在历史里。** 留着它，重发同一句话就是历史里两条连续的用户消息，对话也不再是真正得到过回答的问题的记录。`RunChat` 在失败时把它删掉（脚本测试覆盖了这一点；没有拿真实服务去试连续两条用户消息会怎样）。
- **Windows 控制台默认不是 UTF-8。** 键入的中文读进来不是合法的 UTF-8，编码时报 `the text is not valid UTF-8`。`--chat` 在交互式控制台里先把输入输出改成 UTF-8（`UseUtf8Console`）。Git Bash 的管道输入送来的本来就是 UTF-8，试过没有问题；cmd 和 PowerShell 的管道按各自的编码送字节，没有试。
- **协程的参数是引用时，对象要活到协程结束。** 和 1.1 一样：`Generate` 的参数都是引用，`RunChat` 里的 `conversation` 一直在，跑完一轮才改它。
