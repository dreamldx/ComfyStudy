# 1.3 Tool Calling 循环

- 一句话目标：模型自己决定调用工具，程序执行后把结果送回去，循环到模型不再调用为止；一个 Turn 由若干个 Step 组成，可以被 Ctrl+C 取消或超时，命令行的输出全部走 Agent 钩子

## 1. 本章目标与成果

1.2 结束时，程序能多轮对话，但模型只会说话。机器人要做事：模型自己决定什么时候调用工具，程序执行，把结果送回去，模型再接着答。这一章做这个循环，并把后面所有章节要挂上去的东西一次定好。做完后你会得到：

- **Turn 和 Step 两个概念（不翻译）。** Turn：从一条用户消息开始，到最终回答（或被停掉）为止。Step：Turn 里的一次模型调用，加上它要求的工具的执行。下面第一个例子是一个 Turn，三个 Step。
- **两种新的块：** 工具调用块和工具结果块，以及三种协议各自怎么写它们。一个 Step 里模型可以一次要求好几个调用。
- **循环 `RunTurn`：** 一个 Step 接一个 Step，直到模型的回答里没有调用；有步数上限和整个 Turn 的截止时间；Turn 没有正常结束时，历史回到这条用户消息之前。
- **Agent 钩子：** 循环不直接打印，在八个固定的位置调用钩子。命令行的打印就是一个钩子（`ConsoleHook`），以后 Discord、流式输出、调用记录各是一个钩子。本章的钩子只能看，不能改。
- **一个取消入口，两个触发器：** 一个 Turn 对外只有一个停法，命令行用 Ctrl+C，Discord 以后用 `/stop`；总的截止时间用同一种办法停掉同样的东西（在途的请求和正在执行的工具），只是结束的原因记成超时。
- **steering：** 一个 Turn 进行中收到的新消息，每个 Step 开始前取一次，放进上一个 Step 的工具结果后面。本章用脚本测试这个规则，命令行里没有并发输入，真正接上留到 1.7。
- **工具：** 手写的一张表，只有 `add(a, b)` 和 `sleep(ms)`。循环只通过两件事认识工具：“现在有哪些工具定义”和“执行这个调用”。1.4 把这张表换成真正的工具运行时，循环不用改。

做完以后，`--chat` 不加 `--tools` 时和 1.2 一样；加上 `--tools`，下面的会话就能跑起来。

先看效果（配置文件里已经写好密钥和模型；回答由模型生成，每次不完全一样）。加上 `--tools`，模型就能调用 `add` 和 `sleep`。下面这一次连的是 Anthropic，打开了推理；问题要三次加法，模型自己决定调用几次、先后顺序：

```text
build\windows-debug\bin\comfystudy.exe --chat --tools --llm_provider anthropic --llm_reasoning high
> Use the add tool to compute 17 + 25, then use the add tool again for 8 + 9, then use it once more to add the two results. Answer with just the final number.
[tool] add {"a":17,"b":25}
[tool] add -> 42
[tool] add {"a":8,"b":9}
[tool] add -> 17
[tool] add {"a":42,"b":17}
[tool] add -> 59
59
[info] stopped because: end_turn; tokens in/out: 2103/198
> /exit
```

`[tool]` 开头的行是工具的调用和结果，最后一行是日志：模型为什么停下来，以及三个 Step 的输入、输出各用了多少 token 加起来的总数。

再看一个会被停掉的：让模型调用 `sleep` 睡 5 秒，而整个回答只允许 2 秒（`--agent_turn_timeout_ms 2000`）。两秒一到，这一轮停下，什么也不留在历史里，接着问下一句照常回答：

```text
build\windows-debug\bin\comfystudy.exe --chat --tools --agent_turn_timeout_ms 2000 --llm_provider anthropic
> Call the sleep tool with 5000 milliseconds, and after it returns tell me what 2+3 is.
[tool] sleep {"ms":5000}
stopped: timed out after 2s
> Say hi in one word.
Hi!
[info] stopped because: end_turn; tokens in/out: 512/6
> /exit
```

按 Ctrl+C 的效果和超时一样，只是由你来决定什么时候停（Ctrl+C 这一条在真实控制台里没有按过，见第 6 节）。

## 2. 背景与概念

### 2.1 Turn 和 Step

一次提问到最终回答之间，模型可能被调用好几次：它先要求调用工具，拿到结果后再决定要不要继续。所以需要两个词：

- **Turn**：从一条用户消息开始，到最终回答（或被停掉）为止。有总的截止时间，可以被取消，结束时有一个原因。
- **Step**：Turn 里的一次模型调用，加上它要求的工具的执行。有步数上限。

“先看效果”里的第一个例子，一个 Turn 里有三个 Step：

```text
Turn（一条用户消息）
  Step 1  模型回答：要求调用 add(17,25) 和 add(8,9)   → 执行这两个工具，两个结果放进一条消息
  Step 2  模型回答：要求调用 add(42,17)               → 执行，结果放进一条消息
  Step 3  模型回答：59（没有调用）                       → Turn 完成
```

1.2 里写的“一轮”就是 Turn。

### 2.2 工具调用在三种协议里的样子

模型的回答里除了文字，还可以有“我要调用某个工具，参数是这些”。三种协议写法不同：

| | 请求里的工具 | 回答里的调用 | 结果怎么送回去 |
|---|---|---|---|
| Chat | `tools: [{type: function, function: {name, description, parameters}}]` | `message.tool_calls[{id, function: {name, arguments}}]`，`arguments` 是一段文字 | 每个结果一条 `role: tool` 的消息，带 `tool_call_id` |
| Responses | `tools: [{type: function, name, description, parameters}]`（不再包一层 `function`） | `output` 里的 `function_call` 项：`id`、`call_id`、`name`、`arguments`（文字） | `function_call_output` 项：`call_id`、`output` |
| Anthropic | `tools: [{name, description, input_schema}]` | `content` 里的 `tool_use` 块：`id`、`name`、`input`（对象） | 紧跟的用户消息里的 `tool_result` 块，一个 Step 的所有结果在同一条消息里，而且必须排在这条消息的任何文字前面 |

内部用同一种写法：`ToolCallBlock` 和 `ToolResultBlock`。调用和结果都是普通的数据，所以一段带工具调用的历史可以换一个协议重新编码。（编码有测试；换协议以后服务接不接受，没有用真实服务试过。Anthropic 对调用编号里的字符有限制，别的服务给的编号不一定符合。）

### 2.3 工具失败不是异常

模型可能给出不存在的工具名、缺参数、类型不对，或者参数干脆不是合法的 JSON（Chat 和 Responses 的 `arguments` 是一段文字，官方文档明说它不总是合法的 JSON）；工具自己也可能出错。这些都不该让整个对话崩掉，应该告诉模型出了什么错，让它自己改。所以工具的结果有一个“是不是错误”的标记，失败变成一个 `is_error` 的结果送回去，循环继续。只有取消是例外：它不是工具的失败，要一直往上传。

### 2.4 Turn 没有正常结束时，整个 Turn 作废

Turn 的结果有六种：完成（`kDone`）、步数上限（`kMaxSteps`）、被取消（`kCancelled`）、超时（`kTimedOut`）、出错（`kFailed`）、最后一个回答没有文字（`kNoText`）。除了完成，其余五种都回滚：`conversation` 回到这条用户消息之前，用户可以重新问。

为什么不保留已经完成的 Step？因为没有最终回答的 Turn，历史会以工具结果结尾，下一条用户消息接上去，对话不再是“问题加回答”的记录。

代价要说清：1.4 以后有副作用的工具（比如写文件）在被取消之前已经执行了，回滚以后模型不记得它做过。这一点要在 1.4 讲副作用分类时回头看。

### 2.5 Agent 钩子

循环要把正在发生的事告诉外面：开始了、模型回答了、工具开始了、结束了。最直接的做法是循环自己打印，但这样 Discord、流式输出、调用记录各要在循环里另写一套。所以循环只在固定的位置调用钩子，谁关心谁订阅。

| 位置 | 钩子方法 | 命令行的 `ConsoleHook` 做什么 | 以后的使用者 |
|---|---|---|---|
| Turn 开始 | `OnTurnStarted` | 无 | 记录调用（2.6） |
| Step 开始 | `OnStepStarted` | 无 | 记录调用 |
| 收到模型的回答 | `OnReplyReceived` | 打印回答的文字 | Discord（1.7）、流式（llm-1.2） |
| 工具开始 | `OnToolStarted` | 打印 `[tool] add {...}` | Discord、记录调用 |
| 工具结束 | `OnToolFinished` | 打印 `[tool] add -> 5` | Discord、记录调用 |
| Step 结束 | `OnStepFinished` | 无 | 记录调用 |
| Turn 结束 | `OnTurnFinished` | 打印停止的原因或 `[info]` 行 | Discord、记录调用 |
| 出错 | `OnError` | 打印 `error: ...` | Discord |

本章的钩子是**只读**的：每个位置的参数都是 `const&`，钩子看得到，改不了。但接口按“真钩子”设计：方法是协程（以后有的钩子要等，比如等用户批准）；可以注册多个，按注册的顺序一个个调用；钩子出错只记一条日志，Turn 继续。支线 llm-1.1 在它上面加“改写和中止”的能力和三个新位置（模型调用之前、围着模型调用、围着工具调用），再用它做脱敏、预算、重试与降级、权限确认。

### 2.6 取消：一个入口，两个触发器

一个 Turn 对外只有一个停法：`TurnControl::Cancel()`。谁来调用由前端决定：命令行在 Turn 运行期间监听 Ctrl+C；Discord 在 1.7 收到 `/stop` 命令时调用它。总的截止时间不经过 `Cancel()`，但停掉的是同样的东西：Step 循环和一个计时器并排运行，谁先结束就取消另一个；计时器先到，Step 循环被取消，结束的原因记成超时。

取消会打断两处：在途的模型请求（沿用 1.1 的 `Transport` 取消），以及正在执行的工具（比如 `sleep`）。取消以后 Turn 回滚，`OnTurnFinished` 仍然会调用。

### 2.7 steering

机器人在一个 Turn 进行中可能收到同一个频道的新消息：用户补充了一句，或者纠正了一句。这样的消息不该打断工具，也不该另起一个 Turn，应该在下一个 Step 开始前并进去。规则是：

- 每个 Step（从第二个起）开始前问一次“有没有新消息”；
- 新消息放进上一个 Step 的工具结果那条用户消息里，排在所有结果后面，每条前面有一段固定的标记文字，告诉模型“这是任务进行中收到的新消息”；
- 一个 Turn 最后一个 Step（没有调用的回答）进行时到的消息，不在这个 Turn 里消费，留给下一个 Turn。
- 已经取出来的新消息，如果这个 Turn 后来被取消、超时或出错，会随着回滚一起丢掉，不会还回收件箱。现在没有谁传入收件箱，所以没有影响；1.7 接上的时候要决定怎么办（比如回滚时把它们还回去）。

放进同一条消息是为了不出现连续两条用户消息；标记文字固定，是为了以后提示缓存能命中。命令行没有并发输入，所以本章只用脚本测试这条规则。

### 2.8 工具的接缝

循环不知道工具是怎么实现的，只通过两件事认识它们：现在有哪些工具定义，以及执行这个调用。1.3 用一张手写的表实现这两件事；1.4 的工具运行时是另一种实现（参数校验、每个工具自己的超时、并发策略、结果截断、副作用分类……），循环不用改。循环在**每一个 Step** 都重新问一次工具定义，不是只在开始时问一次：1.5 的 Skill 会在一个 Turn 中途加载新的工具。

## 4. 关键代码讲解

### 4.1 两种新的块

模型要求调用工具，就是回答里的一个 `ToolCallBlock`：调用的编号、工具名、参数。参数在 Chat 和 Responses 里是一段文字，不一定是合法的 JSON，所以块里有两份：解析好的 `arguments`（读不出来时是 null）和原样的 `arguments_text`。回放时用原样的那一份，因为 Responses 的文档警告，改动前面的输入会让服务丢掉后面的推理项。

<!-- src: src/conversation.h#L32-L51 -->
```cpp
// The model asks for a tool to be run.
struct ToolCallBlock {
  std::string id;  // pairs the call with its result (Chat: tool_call_id, Responses: call_id, Anthropic: tool_use id)
  std::string name;
  json::Value arguments;  // null when the text the model sent was not valid JSON
  // Chat and Responses send the arguments as text. It is kept exactly as received and sent back
  // as it is (the Responses documentation warns that changing earlier input makes the service
  // drop reasoning items); empty when the call came from Anthropic, which sends an object.
  std::string arguments_text;
  std::string item_id;  // Responses only: the "id" of the function_call item, which differs from the call id
};

// What running the tool gave, sent back to the model.
struct ToolResultBlock {
  std::string call_id;  // the id of the ToolCallBlock it answers
  std::string text;
  bool is_error = false;
};

using Block = std::variant<TextBlock, ReasoningBlock, ToolCallBlock, ToolResultBlock>;
```

工具的定义（名字、说明、参数的 JSON Schema）放在 `Options` 里，空表示不给模型任何工具：

<!-- src: src/conversation.h#L70-L81 -->
```cpp

struct ToolDefinition {
  std::string name;
  std::string description;
  json::Value parameters;
};

struct Options {
  int max_tokens = 1024;  // upper limit for the answer, counted in tokens
  Reasoning reasoning = Reasoning::kOff;
```

### 4.2 三种协议的映射

Chat 把每个结果做成一条 `role: tool` 的消息，助手的调用放进 `tool_calls`（这时 `content` 可以是 null）；结果后面如果还有文字（steering），是一条用户消息。

<!-- src: src/llm_wire.cpp#L195-L224 -->
```cpp
  // This format has no place for reasoning blocks: only the text and the tool calls go out. Every
  // result is a message of its own (role "tool"); the text after the results is a user message.
  for (const Message& message : conversation.messages) {
    const std::string text = TextOf(message);
    json::Value calls = json::Array();
    for (const Block& block : message.blocks) {
      if (const auto* result = std::get_if<ToolResultBlock>(&block)) {
        json::Push(messages, {{"role", "tool"}, {"tool_call_id", result->call_id}, {"content", Utf8(result->text)}});
      } else if (const auto* call = std::get_if<ToolCallBlock>(&block)) {
        json::Push(calls, {{"id", call->id},
                           {"type", "function"},
                           {"function", {{"name", call->name}, {"arguments", ArgumentsText(*call)}}}});
      }
    }
    if (!calls.get_array().empty()) {
      json::Push(messages, {{"role", "assistant"}, {"content", text.empty() ? json::Value{} : json::Value(text)}, {"tool_calls", calls}});
    } else if (!text.empty()) {
      json::Push(messages, {{"role", RoleName(message.role)}, {"content", text}});
    }
  }

  json::Value body = {{"model", provider.model}, {"messages", messages}, {"max_completion_tokens", options.max_tokens}};
  if (!options.tools.empty()) {

      json::Push(tools, {{"type", "function"},

    }
    body["tools"] = tools;
  }
```

`ToolTable` 是手写的实现。工具名不存在、参数不是合法 JSON、工具函数抛异常，都变成 `is_error` 的结果，只有取消继续往上传：

<!-- src: src/tool.cpp#L69-L91 -->
```cpp
boost::asio::awaitable<ToolResult> ToolTable::Run(const llm::ToolCallBlock& call) {
  const Entry* found = nullptr;
  std::string known;
  for (const Entry& entry : entries_) {
    if (entry.definition.name == call.name) found = &entry;
    known += (known.empty() ? "" : ", ") + entry.definition.name;
  }
  if (found == nullptr) co_return Error("there is no tool called \"" + call.name + "\"; the tools are: " + known);
  if (call.arguments.is_null()) {
    co_return Error("the arguments are not valid JSON: " + call.arguments_text);
  }

  ToolResult result;
  try {
    result = co_await found->function(call.arguments);
  } catch (const boost::system::system_error& e) {
    if (e.code() == boost::asio::error::operation_aborted) throw;  // the Turn was cancelled: not the tool's failure
    result = Error(std::string("the tool failed: ") + e.what());
  } catch (const std::exception& e) {
    result = Error(std::string("the tool failed: ") + e.what());
  }
  co_return result;
}
```

两个玩具工具里，`sleep` 有意思的地方在于它等的是一个可以被取消的计时器：取消到来时 `co_await` 抛出取消异常，直接穿过工具表一直传到循环。

```cpp
boost::asio::awaitable<ToolResult> Sleep(const json::Value& arguments) {
  const json::Value* ms = arguments.is_object() ? json::Find(arguments, "ms") : nullptr;
  if (ms == nullptr) co_return Error("sleep needs the whole number \"ms\"");
  const std::optional<std::int64_t> whole = json::AsInt64(*ms);
  if (!whole) co_return Error("\"ms\" must be a whole number of milliseconds");
  const std::int64_t wait = *whole;
  if (wait < 0 || wait > kMaxSleepMs) co_return Error("\"ms\" must be between 0 and " + std::to_string(kMaxSleepMs));
  boost::asio::steady_timer timer(co_await boost::asio::this_coro::executor, std::chrono::milliseconds(wait));
  co_await timer.async_wait(boost::asio::use_awaitable);  // a cancellation throws here and goes on up
  co_return ToolResult{"slept " + std::to_string(wait) + " ms", false};
}
```

### 4.6 循环：Turn 的开始和结束

`RunTurn` 记下回滚点（用户消息之前），通知钩子，运行 Step 循环；如果设了截止时间，Step 循环和一个计时器**谁先结束就停掉另一个**：Step 先结束，计时器被取消；计时器先到，Step 循环被取消，结束的原因记成超时。外部的取消（Ctrl+C、`/stop`）同样会打断它们，原因记成取消。

结束以后，不是 `kDone` 的 Turn 都把历史截回回滚点，再通知钩子。注意取消之后那一行 `reset_cancellation_state()`：取消到达时，这个协程的取消状态被设上了，之后任何新的 `co_await` 都会立刻被它打断，钩子就没法等了；调用这一行，表示取消已经处理完。

<!-- src: src/agent.cpp#L177-L226 -->
```cpp
  bool cancelled = false;
  try {
    co_await Notify(hooks, &AgentHook::OnTurnStarted, TurnStarted{conversation.messages.size()});
    if (limits.deadline.count() > 0) {
      // Whichever ends first stops the other: the Steps end the timer, or the timer stops the Steps.
      const auto finished = co_await (RunSteps(run) || Deadline(limits.deadline));
      if (finished.index() == 1) outcome.reason = Reason::kTimedOut;
    } else {
      co_await RunSteps(run);
    }
  } catch (const boost::system::system_error& e) {
    if (IsCancellation(e)) {
      cancelled = true;
    } else {
      outcome.reason = Reason::kFailed;
      outcome.error = e.what();
    }
  } catch (const boost::asio::multiple_exceptions& e) {
    // A cancellation from outside reaches the Steps and the timer next to them, and both end with an
    // abort: `||` then reports the two together. They are a cancellation as long as the first is one.
    try {
      std::rethrow_exception(e.first_exception());
    } catch (const boost::system::system_error& first) {
      if (IsCancellation(first)) {
        cancelled = true;
      } else {
        outcome.reason = Reason::kFailed;
        outcome.error = first.what();
      }
    } catch (const std::exception& first) {
      outcome.reason = Reason::kFailed;
      outcome.error = first.what();
    }
  } catch (const std::exception& e) {
    outcome.reason = Reason::kFailed;
    outcome.error = e.what();
  }
  if (cancelled) outcome.reason = Reason::kCancelled;

  // A cancellation has been dealt with. Without this, every co_await below would be cut short by it,
  // and the hooks could not wait for anything.
  co_await boost::asio::this_coro::reset_cancellation_state();

  if (outcome.reason != Reason::kDone) {
    conversation.messages.erase(conversation.messages.begin() + static_cast<std::ptrdiff_t>(rollback_to), conversation.messages.end());
  }
  if (!outcome.error.empty()) co_await Notify(hooks, &AgentHook::OnError, ErrorInfo{outcome.error});
  co_await Notify(hooks, &AgentHook::OnTurnFinished, TurnFinished{outcome});
  co_return outcome;
}
```

**手动核对（要网络和密钥，不进 `ctest`）。** 下面是本章实际做过的，结果见括号：

1. 三个 Provider 各做一次多步调用（都得到 59；三种协议的第一个 Step 里模型都一次给了两个调用）。
2. Responses：回放时 `function_call` 项带着 `id`、推理项原样放在前面，服务返回 200。
3. Anthropic 带 thinking 的多步调用：用一道需要推导的题，再让模型用 `add` 验算；两次里第一个响应都是 thinking 块加 `tool_use`。第二个请求里助手消息的 thinking 块与收到的逐字段相等（签名 1648 个字符），服务返回 200。
4. **实验：thinking 块和签名。** 拿第 3 步里真实的第二个请求，做两种改动再发给服务：

| 做法 | 结果 |
|---|---|
| 原样发回 | 200 |
| 整个 thinking 块去掉 | 200，模型的回答里又有了新的 thinking 块和 `tool_use` |
| thinking 块的 `signature` 改一个字符 | 400：`messages.1.content.0: Invalid signature in thinking block` |

结论：在这个模型的自适应模式下，服务并不要求把 thinking 块带回来，这一点和官方文档里“自适应模式没有这条要求”的说法一致，但文档仍然建议带回，本章也带回。签名是被校验的，改一个字符就是 400，所以块必须整块原样放回。

5. 超时：`--agent_turn_timeout_ms 2000`，让模型调 `sleep(5000)`，两秒后停下，下一个问题正常回答；一个 1500 毫秒的 `sleep` 在默认期限内正常结束，模型接着调用 `add`，回答里引用了两个结果。

**没有核对的**（这一章里没有验证，请不要当成结论）：
- 在真实的控制台里按下 Ctrl+C 键：测试里用 `raise(SIGINT)` 验证了处理函数和取消，但从键盘到 SIGINT 这一段是 C 运行库的事，这里没有交互式控制台可以试。请你自己试一次：让模型调用 `sleep(5000)`，两秒内按 Ctrl+C。
- steering 在真实的并发输入下的行为：只用脚本测试过。
- Responses 的 `function_call` 项不带 `id` 回放会不会被拒绝：这里一直带着 `id`。
- OpenRouter 的 Chat 响应里的 `reasoning`（以及可能有的 `reasoning_details`）在工具调用那一轮有没有作用：这次没有回放它们，任务也完成了，只能说明“不回放也能完成这一个任务”。

## 7. 技术资料

- 三种协议的官方文档（字段以实测和文档为准）：OpenAI 的[函数调用指南](https://developers.openai.com/api/docs/guides/function-calling)（Chat 和 Responses 的写法）和[推理指南](https://developers.openai.com/api/docs/guides/reasoning)（带调用的推理项要一起带回）；Anthropic 的[工具使用](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)、[处理工具调用](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)和[并行工具使用](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)。
- 本章实测的模型：Anthropic 的 `claude-sonnet-5-5`（官方接口）；OpenAI 的两种格式连的是 OpenRouter 上的一个 DeepSeek 模型。凡是“这个模型”，都只对它们成立。
- 设计取舍：
  - **Turn 和 Step 分开命名。** 一个 Turn 里要有总的截止时间和取消，一个 Step 里要有步数上限和“一次模型调用加它的工具”这个单位，两个层次各有各的限制，混在一起会说不清“停在了哪里”。
  - **回滚整个 Turn，不是只丢进行中的 Step。** 备选是保留已经完成的 Step：历史会以工具结果结尾，下一条用户消息接上去，对话不再是问答的记录。代价（有副作用的工具执行过的部分不在历史里）已在 2.4 说明，留给 1.4 回头看。
  - **事件和钩子合成一个概念。** 备选是只读的事件加另一套能改的钩子，两套名字、两套接口。本章的钩子只读，但按真钩子设计（协程、有顺序、出错不影响 Turn），支线 llm-1.1 在它上面加改写和中止，不用换接口。
  - **钩子的方法是协程，上下文是 `const&`。** 备选是 `std::function` 事件：以后有的钩子要等用户批准，那时每个订阅者的签名都要改。只读由编译器保证，不是约定。
  - **一个取消入口，两个触发器。** 备选是命令行专用的 Ctrl+C 处理（Discord 用不上）或者只做脚本测试（命令行里看不到效果）。现在 Ctrl+C 和以后的 `/stop` 都只是调用 `Cancel()`；截止时间不经过它，而是让计时器和 Step 循环并排运行，哪个先到就取消另一个。
  - **steering 放进携带工具结果的那条消息。** 备选是另起一条用户消息：会出现两条连续的用户消息。
  - **工具表手写，接缝窄。** 备选是现在就做完整的运行时，那是 1.4。循环只认识“有哪些工具”和“执行这个调用”，换实现不改循环。
  - **一个 Step 里的多个调用按顺序执行。** 同时执行是 1.4 的并发策略，要先有副作用分类才能决定哪些可以同时跑。
  - **最后一个允许的 Step 里模型要求的工具照样会执行。** 到了步数上限，这个 Turn 作废，结果被丢掉，但工具已经跑过了（`sleep` 最长 60 秒）。有副作用的工具要在 1.4 里想清楚。
  - **没做：** 工具运行时（参数校验、每个工具自己的超时、并发、结果截断、副作用分类）、流式输出（支线 llm-1.2）、改写和中止的钩子、重试与降级、权限确认（支线 llm-1.1）、steering 的真实接入和 Discord 前端（1.7）、持久化。

## 8. 常见问题与坑

下面每一条都写明了核对到哪一步：没有注明的，是在这一章的真实运行或测试里遇到并核对过的；注明的，只在文档里读到或没有试。

- **Chat 和 Responses 的参数是文字，不是对象。** 回答里的 `arguments` 是一段 JSON 文字，官方文档说它不总是合法的 JSON。块里同时存着解析好的和原样的，解析不了时参数是 null，循环给模型一个“参数不是合法 JSON”的错误结果。回放用原样的文字。
- **Responses 里有两个编号。** `call_id` 把调用和结果配对，`id` 是服务给这个项的编号。回放时两个都带着（服务返回 200）；不带 `id` 会怎样没有试。
- **Anthropic 的结果必须排在文字前面，一个 Step 的所有结果在同一条用户消息里。** 这是官方文档的要求（文档里说违反了是 400）；编码测试检查了顺序，真实运行里我们的消息总是这样排的，没有故意违反去试。
- **模型一次可以给好几个调用。** 三种协议在这个问题上第一个 Step 里都给了两个。所以结果要按调用的顺序、放在同一个位置回答，循环不能假设一个 Step 只有一个调用。
- **取消和截止时间一起用时，`||` 会把两个终止一起报告。** 真实的程序总是有截止时间（默认五分钟），所以 Step 循环总是和计时器并排运行。外部取消到来时两边都以“被取消”结束，`||` 抛出的是 `multiple_exceptions`，不是一个取消异常。最初的实现只认单个取消异常，结果是 Turn 被记成 `kFailed`。这是评审时发现的：以前所有取消测试都没有设截止时间。现在 `RunTurn` 认得这种情形，有测试（`CancelWhileADeadlineIsSetStillCancelsAndIsNotATimeout`，以及带截止时间的 Ctrl+C 测试）。
- **取消以后，同一个协程里新的 `co_await` 会被同一个取消打断。** 取消到达时，协程的取消状态被设上，不重置的话，后面钩子里任何要等的操作都会立刻失败，`OnTurnFinished` 也就收不到。实现里在取消处理完以后调用 `reset_cancellation_state()`。验证过：临时去掉这一行，三个取消的测试（`sleep` 中取消、模型请求在途时取消、Ctrl+C）就失败，放回去就通过。
- **`signal_set` 要在 Turn 结束时取消。** 它的等待会让事件循环一直有事可做，Turn 结束以后 `io.run()` 就不会返回。这是从 Asio 的行为推出来的设计，没有故意不取消去试。
- **Ctrl+C 在没有 Turn 运行时是平常的意思。** `signal_set` 只在 Turn 运行期间存在，等你输入时按 Ctrl+C 还是退出程序。（真实控制台里按键没有验证，见第 6 节。）
- **简单的问题模型不一定思考。** 加法这样的小任务，`--llm_reasoning high` 下 Anthropic 也没有返回 thinking 块，只有 `tool_use`；要看到“thinking 块加调用”，要问一道需要推导的题。
- **去掉 thinking 块，这个模型照样回答，改了签名就是 400。** 见第 6 节的实验。结论只对这个模型的自适应模式成立。
- **步数上限是对一个 Turn 说的。** 到了上限 Turn 作废，历史里什么都不留；模型再怎么调用工具，也不会无限循环。
- **失败的工具调用也要有结果。** 三种协议都要求每个调用有对应的结果，所以工具失败、工具名不存在也要回一个 `is_error` 的结果，不能什么都不回。
- **OpenRouter 的 Chat 响应里有额外的 `reasoning`。** 这不是 Chat 的字段，本章不读它也不回放，多步工具调用照样成功。这条在 1.2 里就遇到了，这一章核对的结果是“不回放也能完成这一个任务”。

- **本章的 JSON 列表里键是按字母序排的，缩进也是为了好读。** 程序实际写出的是一行紧凑的 JSON，键的顺序是代码里写入的顺序（见 1.1）。
- **`add` 的整数是精确的，靠 `generic_u64`。** `json::Value` 是 `glz::generic_u64`：非负整数存成 `uint64_t`，负整数存成 `int64_t`。换成默认的 `glz::generic`，大于 2^53 的整数就不准了（1.1 的练习 10 试过这一点）。

1. 在 `AddToyTools` 里再加一个工具 `multiply(a, b)`，写它的测试（`test_tool.cpp`），再用 `--chat --tools` 问一个需要它的问题。
