## 1. 本章目标与成果

这一章第一次让程序真的去问一个大模型，而且从第一章起就是异步的：等模型回答要几秒，机器人在等的时候还要收消息、发消息，所以“发一个请求”不能占住一个线程。做完后你会得到：

- 一个 `http::Transport` 接口，和它用 libcurl 写的实现 `MakeCurlTransport()`。程序里所有要发请求的地方都只认这个接口，不认 libcurl；测试里换成一个假的，以后换成录制好的回放也可以。
- 一套对错误的分类：连不上、超时、连接断了，各是什么意思，哪些可以放心重发。取消一个正在等回答的请求，也在这里定好。
- 日志里不出现密钥：打印请求头的地方，密钥都被换成 `***`。
- 项目里 JSON 的写法：用 Glaze 的 `glz::generic` 表示形状事先不知道的 JSON，`src/json.h` 把它包成几个小函数（解析、写出、查找、读整数）。0.3 里装的 nlohmann/json 到这里换成 Glaze，第 2 节把两个库放在一起比较，说明为什么换。
- 三种请求格式各一份“生成请求”和“读出回答”的代码：OpenAI 的 Chat Completions、OpenAI 的 Responses、Anthropic 的 Messages。三份各写各的，不合并，这样差别一眼就能看出来。
- 命令行上的 `--prompt`（再加可选的 `--system`）：问一次，打印回答，退出。用哪个服务、哪个模型、哪种格式，都由配置决定。
- 一套契约测试：同一组测试既跑在 libcurl 的实现上（对着本机的一个小服务器），也跑在测试用的假实现上，以后任何新的实现都用它来检查。

先看效果（配置文件里已经写好密钥和模型）：

```text
comfystudy --llm_provider openai --openai_api chat --prompt "Say hello in five words." --system "You are terse."
```

```text
Hello, how are you today?
[info] stopped because: stop; tokens in/out: 41/65
```

第一行是模型的回答，第二行是日志：模型为什么停下来，以及输入、输出各用了多少 token。

## 2. 背景与概念

**HTTP 请求与响应。** 调用大模型的接口，就是向一个网址发一次 HTTP 请求。请求由四样东西组成：方法（这里用 `POST`）、网址、请求头（一组“名字: 值”，比如 `Content-Type: application/json`，还有带着密钥的认证头）、请求体（这里是一段 JSON）。服务回来三样东西：状态码（200 表示成功，401 表示认证失败，429 表示请求太多……）、响应头、响应体（又是一段 JSON）。**服务回了一个错误状态码，是服务的答复，不是我们这边出了错**；只有根本没有收到答复（连不上、超时、连接断了），才是传输失败。后面的代码一直把这两种情况分开处理。

**libcurl。** libcurl 是处理 HTTP（以及 TLS、代理、压缩、HTTP/2 等一大堆细节）的 C 库。它有两套常用的接口：easy 是同步的，`curl_easy_perform` 发一个请求，发完才返回，一个线程同一时刻只能做一件事；multi 是把许多个请求交给一个 multi 句柄，在一个线程里同时推进它们。本章用 multi：由一个专门的线程循环运行 `curl_multi_poll` 和 `curl_multi_perform`，所有请求都挂在这一个 multi 句柄上，请求结束时通知等它的协程。为什么不用线程池加 easy，以及三种做法在本机和真实服务上的耗时对比，在支线 [llm-1.2](../../contrib/quest-llm-01-llm-app-engineering/llm-1.2-curl-modes.md) 里有完整的数据；这里只记一个结论：12 个请求，4 个线程的线程池要 3 轮，一个 multi 线程一次发完，在 Anthropic 上是 2.4 秒对 1.2 秒，而且线程池里正在进行的请求没法取消。

**事件循环与协程。** 我们的程序要同时等很多件事：几个模型的回答、Discord 的消息、各种定时器。让每一件事占一个线程，线程数会跟着等待的数量涨，而线程大部分时间只是在睡觉。事件循环换了一种做法：一个线程负责“哪件事有动静了就处理哪件”，等待本身不占线程。本项目用 Boost.Asio 做事件循环（`boost::asio::io_context`），再用 C++20 的协程把“等”写成顺序的代码：

- 一个返回 `boost::asio::awaitable<T>` 的函数是协程。在里面 `co_await` 一个异步操作，函数就暂停，线程回去做别的事，操作完成后函数从暂停的地方继续，`co_return` 返回结果。
- `boost::asio::co_spawn(io, 协程, use_future)` 把协程交给事件循环去跑，返回一个 `std::future`；`io.run()` 运行事件循环，直到再没有事情可做。
- 一个协程可以被取消：取消之后它正在等的那个操作会提前结束，抛出 `operation_aborted`。取消是 Asio 的标准机制，`Transport` 的契约里直接用它。

本章只用这几样。事件循环的原理、`strand`、超时与取消、多线程怎么用，在支线 [llm-1.1](../../contrib/quest-llm-01-llm-app-engineering/llm-1.1-asio-basics.md) 里讲透。

**`Transport`：把“怎么发请求”放在一个接口后面。** 程序里需要发请求的地方（现在是 `Ask`，以后有 Provider、Discord 通知、出图服务）都不直接用 libcurl，而是用一个 `http::Transport` 的引用。这样做有三个好处：测试里可以换成一个不连网络的假实现，速度快、结果确定；以后可以换成“把请求和响应录下来，之后原样回放”的实现，让整个 Agent 循环的测试不花钱、可重复；libcurl 的细节（句柄、线程、回调）全部关在一个源文件里。接口对每个实现提出的要求写在第 4 节，同一组测试（契约测试）检查所有实现是否都做到了。

**错误的分类。** 一个请求没有得到答复，调用者接下来能做什么，取决于是怎么失败的：

| 种类 | 含义 | 例子 | 可以放心重发吗 |
|---|---|---|---|
| `kConnect` | 连接没有建立起来，请求根本没有发出去 | 域名解析失败、连接被拒绝、TLS 握手失败 | 可以（`SafeToRetry()` 为真） |
| `kTimeout` | 在规定的时间内没有收到完整的答复 | 服务太慢 | 不一定：服务也许还在处理，重发会让模型多算一次，多花一次钱 |
| `kLost` | 请求发出去之后连接断了 | 对方关闭连接、HTTP/2 的流出错 | 不一定：服务也许已经处理了 |
| `kOther` | 其他 | 网址不合法、传输被关闭 | 不重发 |

这个分类留给后面的重试（支线 llm-1.7）用：只有 `kConnect` 可以不加思考地重发，其余的要由调用者按“重发会不会做两次”来决定。

**日志里不能有密钥。** 请求头里有 `Authorization: Bearer 密钥` 或 `x-api-key: 密钥`。调试时要看请求头，但日志和错误信息一旦把密钥带出去，就可能出现在截图、录屏、粘贴出去的报错里。所以所有打印请求头的地方都要先过一遍 `http::Redacted`：`Authorization` 保留认证方式（`Bearer ***`），`x-api-key`、`Cookie` 等整个值换成 `***`。

**JSON：用 Glaze，不用 nlohmann/json。** 0.3 为了演示 vcpkg 装了 nlohmann/json，它只用在 `JsonRoundTrip` 这一个函数里。从这一章起 JSON 才是主角：三种请求体、三种回答、工具的参数说明（JSON Schema），以后还有工作流图。这些 JSON 有两种：一种形状事先不知道，要原样保存和回传（模型的推理块、各家服务多出来的字段）；一种形状固定（工具的参数、配置）。项目想用一个库同时管这两种，并且最好能从 C++ 的结构体直接生成 JSON Schema，所以这里换成 Glaze。下面是两个库在这个项目里的实际差别（版本是 vcpkg 基线里的：nlohmann/json 3.12.0，Glaze 9.1.0）：

| | nlohmann/json | Glaze |
|---|---|---|
| 形状不固定的 JSON 值 | `json`，接口像标准容器：`find`、`at`、`push_back`、范围 for | `glz::generic`，接口小一些：`is_*()`、`get<T>()`、`contains`、`[]`、`get_object()`、`get_array()` |
| 结构体和 JSON 互转 | 每个结构体写一个宏，列出字段 | 聚合结构体不写宏就能读写，字段说明和范围另写 |
| 从结构体生成 JSON Schema | 没有，只能手写 | 有：`glz::write_json_schema<T>()`，能写出说明、数值范围、枚举 |
| 整数 | 有符号、无符号、浮点分开存 | `glz::generic` 的数字都是 `double`，2^53 以上的整数不准；`glz::generic_u64` 把非负整数存成 `uint64_t`、负整数存成 `int64_t`，和 nlohmann 一样（本项目用它） |
| 对象里键的顺序 | 排序（字母序） | 保持读入或写入的顺序 |
| 判断两个值相等（`==`） | 有 | 没有（`json.h` 里自己写了一个，测试要用） |
| 写出不合法的 UTF-8 | `dump()` 抛异常 | 原样写出，不检查（1.2 里的 `Utf8()` 检查因此更重要） |
| `dump()` | 返回字符串 | `glz::generic` 的 `dump()` 返回 `std::expected`，不是字符串；`json.h` 的 `json::Dump` 返回字符串 |
| 出错的信息 | 抛异常，带位置 | 返回错误码，`glz::format_error` 给出位置和一个箭头 |
| 一个小程序的编译时间（只编一个源文件，Release，缓存是热的，只测一次，仅作参考） | Windows 3.1 秒，Linux 1.8 秒 | Windows 5.2 秒，Linux 5.4 秒 |
| 同一个小程序的可执行文件大小 | Windows 112 KB，Linux 143 KB | Windows 242 KB，Linux 344 KB |

编译时间和大小来自一次单独的小测量（程序没有放进仓库）：同样的任务（把工具参数读进结构体、报错、动态值来回转换）各写一个小程序，在 MSVC 19.52 和 `g++-16` 上编译。数字只说明 Glaze 的编译更慢、可执行文件更大，不代表这个项目里的差别。

同样一件事，两个库的写法对比，读用量字段：

```cpp
// nlohmann/json
const auto usage = object.find("usage");
if (usage != object.end() && usage->is_object()) {
  reply.input_tokens = Number(*usage, "prompt_tokens");
}
```

```cpp
// json.h（Glaze）
const json::Value* usage = json::Find(object, "usage");
if (usage != nullptr && usage->is_object()) {
  reply.input_tokens = Number(*usage, "prompt_tokens");
}
```

两个库在这个项目里的代价也不同：用 Glaze 要自己补 `json.h` 里的那几个小函数（`Find`、`Items`、`Push`、`AsInt64`、`==`），因为 `glz::generic` 的接口比 nlohmann 的 `json` 少；用 nlohmann 则永远要手写 JSON Schema，并且每个结构体写一次字段列表。

**为什么不是 reflect-cpp。** 它也能从结构体生成 Schema，用起来更顺手（字段说明和类型写在一起，读的时候会检查数值范围）。但在写这一章的时候，它在项目的 vcpkg 基线上是 0.27.1，用 MSVC 19.52 编译，连 `struct S { double a; double b; };` 都会报 `error C3539: a template-argument cannot be a type that contains 'auto'`；我试过 0.23.0、0.24.0、0.25.0 和 0.27.1，都是这样，只有 0.22.0 能编译。项目只能固定在这个旧版本上，所以没有选它。Glaze 在两个平台、C++20 下都直接编译。


**三种请求格式。** 三家的接口做的是同一件事：把一段话发给模型，拿回一段话。但 JSON 的样子各不相同：

| | OpenAI Chat Completions | OpenAI Responses | Anthropic Messages |
|---|---|---|---|
| 路径 | `POST {base}/chat/completions` | `POST {base}/responses` | `POST {base}/v1/messages` |
| 认证 | `Authorization: Bearer 密钥` | `Authorization: Bearer 密钥` | `x-api-key: 密钥`，外加 `anthropic-version` |
| 指令（system prompt） | `messages` 里的一条，角色是 `system` | 单独的字段 `instructions` | 顶层字段 `system` |
| 用户的话 | `messages` 里的一条，角色是 `user` | 字段 `input`（可以是一个字符串） | `messages` 里的一条，角色是 `user` |
| 回答长度上限 | `max_completion_tokens`（可选） | `max_output_tokens`（可选，至少 16） | `max_tokens`（**必填**） |
| 回答在哪里 | `choices[0].message.content` | `output[]` 里 `type` 为 `message` 的项，它的 `content[]` 里 `type` 为 `output_text` 的部分的 `text` | `content[]` 里 `type` 为 `text` 的块的 `text` |
| 为什么停下 | `choices[0].finish_reason` | `status`，没写完时看 `incomplete_details.reason` | `stop_reason` |
| 用量 | `usage.prompt_tokens`、`usage.completion_tokens` | `usage.input_tokens`、`usage.output_tokens` | `usage.input_tokens`、`usage.output_tokens` |

**token 与长度上限。** 模型不是按字而是按 token 读写文本，一个 token 通常是一个词或词的一部分，汉字通常占一个到几个 token，具体取决于模型的分词器。回答长度上限用 token 数表示。需要注意：有“思考”过程的模型，思考用的 token 也算在输出里。本章实测的例子里，回答只有 5 个词，输出 token 却是几十个，多出来的是思考。

**本章的配置项。** 这些设置都可以写在配置文件里，也可以用同名的命令行选项或大写的环境变量：

| 设置 | 作用 |
|---|---|
| `llm_provider` | 用哪家服务：`openai` 或 `anthropic` |
| `openai_api` | OpenAI 用哪种请求格式：`chat` 或 `responses`，不写就是 `chat`（Chat Completions） |
| `openai_model`、`openai_api_key`、`openai_base_url` | OpenAI（或兼容的服务）的模型名、密钥、服务地址 |
| `anthropic_model`、`anthropic_api_key`、`anthropic_base_url` | Anthropic 的模型名、密钥、服务地址 |

两家各有自己的模型名，所以模型名也分开写。`openai_base_url` 可以改成任何兼容 OpenAI 格式的服务（本章的实测就走了这样的一个网关）。

## 4. 关键代码讲解

**请求、答复和错误的类型。** 一个 `PostRequest` 是网址、请求头和请求体；一个 `Response` 是状态码和响应体。错误的种类和 `SafeToRetry()` 在 `http::Error` 里：

<!-- src: src/http_client.h#L12-L17 -->
```cpp
enum class ErrorKind {
  kConnect,  // the connection could not be made (name lookup, TCP, TLS): the request was never sent
  kTimeout,  // no complete answer in time: the server may still be working on the request
  kLost,     // the connection broke after the request was sent: the server may have processed it
  kOther,    // anything else (a bad URL, an option libcurl refused, the transport was shut down)
};
```
<!-- src: src/http_client.h#L21-L35 -->
```cpp
class Error : public std::runtime_error {
 public:
  explicit Error(const std::string& what, ErrorKind kind = ErrorKind::kOther)
      : std::runtime_error(what), kind_(kind) {}

  ErrorKind kind() const { return kind_; }

  // True when sending the request again cannot make anything happen twice, because the first one
  // never left this machine. After a timeout or a lost connection the answer is unknown, and for a
  // request that costs money the caller has to decide.
  bool SafeToRetry() const { return kind_ == ErrorKind::kConnect; }

 private:
  ErrorKind kind_;
};
```

<!-- src: src/http_client.h#L37-L37 -->
```cpp
using Header = std::pair<std::string, std::string>;  // name, value
```
<!-- src: src/http_client.h#L40-L44 -->
```cpp
struct PostRequest {
  std::string url;
  std::vector<Header> headers;
  std::string body;
};
```

<!-- src: src/http_client.h#L46-L49 -->
```cpp
struct Response {
  long status = 0;   // the HTTP status code, e.g. 200 or 401
```

<!-- src: src/http_client.h#L51-L54 -->

`Options` 里的两个超时：`connect_timeout` 是建立连接的时间，`timeout` 是整个请求（包括等回答）的时间。大模型的回答可能要几十秒，所以整个请求的默认值是 120 秒。

**`Transport` 接口。** 只有一个函数，是协程。注释里写的就是契约：每个实现都要做到，契约测试逐条检查。

<!-- src: src/transport.h#L9-L30 -->
```cpp
// How a request gets to a server and the answer comes back. The rest of the program talks to this
// interface, never to libcurl, so a test can put a fake in its place and a recording can be played
// back instead of the real service.
//
//   Post is a coroutine: the caller `co_await`s it, is suspended until the whole answer is there,
//   and resumes on its own executor. Many requests can be under way at the same time.
//
// What every implementation promises:
//   - An answer with an error status (401, 500, ...) is a Response, not an exception.
//   - When no answer arrives, Post throws http::Error. error.kind() says why, and error.SafeToRetry()
//     whether sending the request again cannot make anything happen twice.
//   - When the awaiting coroutine is cancelled, the request is cancelled too, and Post throws
//     boost::system::system_error with boost::asio::error::operation_aborted.
//   - Destroying the transport ends the requests that are still running with an http::Error.
//   - Redirects are not followed: an API key in a header must not be sent to a place the caller did
//     not name.
class Transport {
 public:
  virtual ~Transport() = default;

  virtual boost::asio::awaitable<Response> Post(PostRequest request) = 0;
};
```

**把 libcurl 的错误翻译成种类。** libcurl 用一个枚举 `CURLcode` 报告传输失败。`KindOf` 把它们分到上面的四种里：

**一个请求的所有设置。** 每一个 `setopt` 都是一项设置。请求体、请求头、写回调这几样要在传输期间一直存在，所以它们都放在 `Transfer` 里，和句柄一起活着。`CURLOPT_POSTFIELDS` 加 `CURLOPT_POSTFIELDSIZE_LARGE` 指定请求体和它的长度（不依赖字符串里有没有 `\0`）；`CURLOPT_FOLLOWLOCATION` 设为 0 表示不跟随重定向，因为请求头里有密钥，不能被一个重定向带到调用者没有指定的地方；`CURLOPT_NOSIGNAL` 让 libcurl 在多线程里不用信号处理超时；`CURLOPT_ERRORBUFFER` 让 libcurl 把可读的错误原因写进我们的缓冲区。最后一项 `CURLOPT_PIPEWAIT` 只在 HTTPS 下设：握手之后才知道服务支不支持 HTTP/2，设了它，后面的请求会等第一个请求建好的连接，一起走一条连接，而不是各开一条。

**从协程到回调，再回到协程。** libcurl 是回调风格的：请求结束时它调用我们的函数。协程要的是 `co_await`。`Suspend` 是两者之间的桥：协程调用它时暂停，它把“请求结束时该做什么”（`done`）交给 `start`；等 libcurl 的线程调用 `done`，它再把协程恢复的动作**投递**回协程自己所在的执行器，所以协程总是在它自己的线程上继续，不会在 libcurl 的线程里跑起来。这里一定要 `post` 而不是 `dispatch`：`dispatch` 在同一个线程上会立刻运行，协程就会在 libcurl 的回调里恢复，要是它又发起新请求，就是在 libcurl 的回调里调用 libcurl。`executor_work_guard` 让事件循环在请求没有结束的时候不会以为自己没事做而退出。

<!-- src: src/curl_transport.cpp#L129-L157 -->
```cpp
// What a request calls when it is over: with an error, or with the answer. Can be called from any
// thread, once.
using Done = std::function<void(std::exception_ptr, Response)>;

// Turns "start the request, then call `done`" into something a coroutine can await. `start` receives
// `done` and the cancellation slot of the awaiting coroutine (connected when it can be cancelled).
// `done` resumes the coroutine through its own executor, so it is safe to call from another thread.
template <class Start>
asio::awaitable<Response> Suspend(Start start) {
  co_return co_await asio::async_initiate<decltype(asio::use_awaitable), void(std::exception_ptr, Response)>(
      [start = std::move(start)](auto handler) mutable {
        using Handler = decltype(handler);
        asio::any_io_executor executor = asio::get_associated_executor(handler);
        asio::cancellation_slot slot = asio::get_associated_cancellation_slot(handler);
        auto owner = std::make_shared<Handler>(std::move(handler));
        // While the request is under way the event loop must not think it has nothing to do.
        auto guard = std::make_shared<asio::executor_work_guard<asio::any_io_executor>>(executor);
        Done done = [owner, guard, executor](std::exception_ptr error, Response response) {
          // post, not dispatch: the coroutine must not resume inside libcurl's thread or callback.
          asio::post(executor, [owner, guard, error = std::move(error), response = std::move(response)]() mutable {
            guard->reset();
            Handler resume = std::move(*owner);
            std::move(resume)(error, std::move(response));
          });
        };
        start(std::move(done), slot);
      },
      asio::use_awaitable);
}
```

**`Post`：协程这一侧。** 协程把请求放进一个队列，登记“被取消时该做什么”，然后用 `curl_multi_wakeup` 叫醒 libcurl 的线程。`curl_multi_wakeup` 是 libcurl 里少数明确可以从别的线程调用的函数，所以别的线程只需要加一把保护队列的锁。

```cpp
  asio::awaitable<Response> Post(PostRequest request) override {
    co_return co_await Suspend([this, request = std::move(request)](Done done, asio::cancellation_slot slot) mutable {
      auto job = std::make_unique<Job>();
      job->request = std::move(request);
      job->done = std::move(done);
      std::uint64_t id = 0;
      {
        const std::lock_guard<std::mutex> lock(mutex_);
        id = next_id_++;
        job->id = id;
        incoming_.push_back(std::move(job));
      }
      if (slot.is_connected()) {
        slot.assign([this, id](asio::cancellation_type) {
          {
            const std::lock_guard<std::mutex> lock(mutex_);
            cancels_.push_back(id);
          }
          curl_multi_wakeup(multi_.get());
        });
      }
      curl_multi_wakeup(multi_.get());  // the one call that is meant to be made from other threads
    });
  }
```

**libcurl 的线程。** 它的循环每一轮做四件事：取出新来的请求（加进 multi 句柄）和要取消的请求（从 multi 句柄里摘掉）；推进所有传输；收取已经完成的；最后在 `curl_multi_poll` 里睡觉，直到有传输要处理，或者被 `curl_multi_wakeup` 叫醒。

<!-- src: src/curl_transport.cpp#L247-L290 -->
```cpp
  void Run() {
    for (;;) {
      std::vector<std::unique_ptr<Job>> added;
      std::vector<std::uint64_t> cancelled;
      bool stop = false;
      {
        const std::lock_guard<std::mutex> lock(mutex_);
        added.swap(incoming_);
        cancelled.swap(cancels_);
        stop = stopping_;
      }
      for (auto& job : added) Add(std::move(job));
      for (const std::uint64_t id : cancelled) {
        const auto it = running_.find(id);
        if (it != running_.end()) Finish(it, Cancelled(), std::nullopt);
      }
      if (stop) {
        FailAll("the transport was destroyed while the request was running");
        return;
      }

      int still_running = 0;
      const CURLMcode performed = curl_multi_perform(multi_.get(), &still_running);
      if (performed != CURLM_OK) FailAll(std::string("curl_multi_perform failed: ") + curl_multi_strerror(performed));

      int pending = 0;
      while (CURLMsg* message = curl_multi_info_read(multi_.get(), &pending)) {
        if (message->msg != CURLMSG_DONE) continue;
        Job* job = nullptr;
        curl_easy_getinfo(message->easy_handle, CURLINFO_PRIVATE, &job);
        const auto it = running_.find(job->id);
        if (message->data.result == CURLE_OK) {
          Response response;
          curl_easy_getinfo(job->easy.get(), CURLINFO_RESPONSE_CODE, &response.status);
          response.body = std::move(job->transfer.response_body);
          Finish(it, nullptr, std::move(response));
        } else {
          Finish(it, std::make_exception_ptr(job->transfer.Failure(message->data.result)), std::nullopt);
        }
      }
      // Sleep until a transfer has something to do, or curl_multi_wakeup is called from another thread.
      curl_multi_poll(multi_.get(), nullptr, 0, 1000, nullptr);
    }
  }
```

```cpp
  const json::Value root = ParseJson(body);
  const json::Value& object = Object(root);
  const json::Value* content = json::Find(object, "content");
  if (content == nullptr || !content->is_array()) throw Error("the answer has no \"content\"");

  Reply reply;
  for (const json::Value& block : json::Items(*content)) {  // typed blocks; a "thinking" block may come first
    if (String(block, "type") == "text") reply.text += String(block, "text");
  }
  reply.stop_reason = String(object, "stop_reason");
  const json::Value* usage = json::Find(object, "usage");
  if (usage != nullptr && usage->is_object()) {

    reply.output_tokens = Number(*usage, "output_tokens");
```

```cpp
    const json::Value* error = json::Find(root, "error");
    if (error != nullptr && error->is_object()) {
      std::string type = String(*error, "type");
      if (type.empty()) type = String(*error, "code");
```

`Ask` 把前面的步骤串起来：选格式，按格式取对应的模型名、密钥、地址（缺哪个就报哪个设置的名字），生成请求，通过 `Transport` 发出，状态码不是 2xx 就把服务的错误信息变成异常（`401` 加一句“检查 API 密钥”），否则解析回答。它是协程：发请求那一行 `co_await transport.Post(...)` 的时候，它暂停，线程可以去做别的事。因为它是协程，参数都是引用，调用者要保证这些对象活到协程结束（`main` 里它们都活到 `io.run()` 返回之后）。`-v` 时会打印网址、请求头（密钥被换成 `***`）、请求体和响应体。

```cpp
boost::asio::awaitable<Reply> Ask(http::Transport& transport, const config::Values& settings,
                                  const std::string& prompt, const std::string& system) {
  const Protocol protocol = ChooseProtocol(settings);

  Request request;
  request.system = system;
  request.prompt = prompt;

  Endpoint endpoint;
  HttpRequest (*build)(const Endpoint&, const Request&) = nullptr;
  Reply (*parse)(const std::string&) = nullptr;
  std::string (*error_text)(const std::string&) = nullptr;
  switch (protocol) {
    case Protocol::kOpenAIChat:
    case Protocol::kOpenAIResponses:
      request.model = Required(settings, "openai_model");
      endpoint.base_url = Required(settings, "openai_base_url");
      endpoint.api_key = Required(settings, "openai_api_key");
      if (protocol == Protocol::kOpenAIChat) {
        build = openai_chat::BuildRequest;
        parse = openai_chat::ParseReply;
        error_text = openai_chat::ErrorText;
      } else {
        build = openai_responses::BuildRequest;
        parse = openai_responses::ParseReply;
        error_text = openai_responses::ErrorText;
      }
      break;
    case Protocol::kAnthropic:
      request.model = Required(settings, "anthropic_model");
      endpoint.base_url = Required(settings, "anthropic_base_url");
      endpoint.api_key = Required(settings, "anthropic_api_key");
      build = anthropic::BuildRequest;
      parse = anthropic::ParseReply;
      error_text = anthropic::ErrorText;
      break;
  }

  const HttpRequest http_request = build(endpoint, request);
  // The headers carry the API key: they are logged only with the secrets blanked out. The bodies
  // hold just the question and the answer.
  spdlog::debug("POST {}", http_request.url);
  for (const http::Header& header : http::Redacted(http_request.headers)) {
    spdlog::debug("request header {}: {}", header.first, header.second);
  }
  spdlog::debug("request body: {}", http_request.body);
  const http::Response response =
      co_await transport.Post({http_request.url, http_request.headers, http_request.body});
  spdlog::debug("HTTP {}", response.status);
  spdlog::debug("response body: {}", response.body);

  if (response.status < 200 || response.status >= 300) {
    std::string message = "the service answered HTTP " + std::to_string(response.status) + ": " +
                          error_text(response.body);
    if (response.status == 401) message += " (check the API key)";
    throw Error(message);
  }
  co_return parse(response.body);
}
```

- `OpenAiChat`、`OpenAiResponses`、`Anthropic`（`test_llm_wire`）：用固定的 JSON 样例检查每种格式的请求长什么样、回答怎么读，包括 `content` 为 `null`、带 `reasoning` 块、没有 `message` 项、被截断等情形。
- `TransportContract`（`test_transport`）：同一组测试跑在 libcurl 的实现（对着本机用 cpp-httplib 起的小服务器）和假实现上，检查接口的每一条承诺：请求头和请求体原样发出；错误状态是答复不是异常；20 个请求同时在途、各拿各的答案，总共只比一个请求多一点点；连不上是 `kConnect`，可以放心重发，错误信息里没有密钥；超时是 `kTimeout`，不可以放心重发；一个请求失败不影响别的；取消协程会取消请求，并且很快就结束；协程回到自己的线程；销毁 `Transport` 时在途的请求以错误结束（假实现没有在途的请求可以结束，这一项对它是“跳过”）。
- `CurlTransport` 和 `HttpTypes`（也在 `test_transport`）：重定向不被跟随；中文和 1 MB 的请求体完整到达；只有 `kConnect` 的 `SafeToRetry()` 为真；`Redacted` 藏起密钥、保留其余、不改原件。
- `LlmAsk`（`test_llm_client`）：让假的服务器分别假装三家，检查 `Ask` 选对格式、带对认证头、用对模型名，`401` 变成带提示的错误，缺设置按名字报错，服务不存在时抛 `http::Error`。

`scripts/check-build.ps1` 也要通过：编译 19 条命令（10 个库和程序的源文件加 9 个测试）、链接 10 条。真实服务只用来手动验证（上一节的命令），不进 `ctest`：它需要网络和密钥，而且回答每次都不一样。

## 7. 技术资料

- libcurl 8.23.0（vcpkg 的端口，带 `http2` 特性，nghttp2 1.71.0，Windows 上 TLS 用 Schannel，所以不需要 OpenSSL）；Boost 1.92.0 的 Asio（vcpkg 的 `boost-asio`，头文件库）；测试用 cpp-httplib；JSON 用 Glaze 9.1.0（vcpkg 的 `glaze`，头文件库）；0.3 装的 nlohmann/json 3.12.0 不再用，对比见第 2 节。
- 三种接口的官方文档（字段以实测和文档为准）：OpenAI Chat Completions 的 create 接口、OpenAI Responses 的 create 接口、Anthropic 的 Messages 接口。OpenAI 的两个文档页说的字段名和兼容服务的实际行为有小出入，写代码时以实测为准。
- 设计取舍：
  - **一开始就异步。** 机器人要在等模型回答的时候同时做别的事，把“发请求”做成会阻塞线程的函数，后面所有调用它的地方都得改。所以第一章就让 `Ask` 是协程，`main` 里用事件循环把它跑起来；只问一次的 `--prompt` 看起来多了几行，换来的是后面的章节不用回头改。
  - **JSON 用 Glaze，不用 nlohmann/json。** 项目需要一个库同时管形状不固定的 JSON（推理块、各家多出来的字段）和形状固定的 JSON（工具参数、配置），并且能从结构体生成 Schema，Glaze 满足，nlohmann/json 不能生成 Schema。代价：`glz::generic` 的接口小，要自己补几个函数；编译慢一些；没有 `==`。
  - **用 `generic_u64`，不用默认的 `generic`。** 默认的 `glz::generic` 把所有数字存成 `double`，大整数会变；工具的 `add` 要把两个整数精确相加，所以用 `glz::generic_u64`。
  - **读 JSON 的函数用指针，不用异常。** `json::Find` 找不到返回 `nullptr`，调用方判断；回答里缺字段是常事（见第 8 节），不该靠异常来处理。
  - **请求都经过 `Transport`。** libcurl 的细节关在一个源文件里；测试、录制回放、换一个实现，都不用动调用方。
  - **选 multi 加一个线程。** 数据和理由在支线 llm-1.2：同样的请求量，比线程池快、线程更少，而且能取消。代价是线程里的回调不能做耗时的事（流式输出那一章会遇到）。
  - **错误分类，不只是一条消息。** 重试要不要做，取决于请求有没有发出去、答复知不知道，一条字符串信息里读不出来。
  - **三种格式各写各的。** 它们差别不大，但每一处差别（指令放在哪、上限字段叫什么、回答在哪里）都是实际会踩的坑。写在一起并排对比比一开始就抽象有用。统一的接口留给下一章。
  - **不重试、不流式。** 重试和限流是支线 llm-1.7，流式输出是支线 llm-1.3。
  - **不跟随重定向。** 请求头里有密钥。
  - **HTTP 错误状态不是异常。** 状态码是服务的答复，传输失败才是异常，两者的处理方式本来就不同。
  - **被否决：** 手写 socket 发 HTTP（要自己处理 TLS、分块传输、压缩，还得写证书校验）；用一个封装好的 C++ HTTP 客户端库（本项目的主要目的是弄懂这些东西，而且这些库多半不支持取消和 HTTP/2）；线程池加 easy 接口（见支线 llm-1.2 的对比）。

## 8. 常见问题与坑

- **libcurl 的 POST 默认的 `Content-Type` 是 `application/x-www-form-urlencoded`。** 不写这个头，服务会把请求体当表单看。我们的测试里就踩到了：1 MB 的请求体没有 `Content-Type`，本机的测试服务器直接回 413；契约测试里，一个不带 `Content-Type` 的请求在 libcurl 的实现和假实现上得到的回答也不一样。所以 JSON 请求一定自己带 `Content-Type: application/json`。
- **`Job` 里 `transfer` 要写在 `easy` 前面。** 成员按声明的反序销毁，句柄清理时 libcurl 还会访问它的选项指向的缓冲区（请求体、请求头、错误缓冲区），缓冲区要比句柄晚销毁。声明顺序反了，大约每 4 到 5 次运行崩一次，而且每次崩的位置不一样。
- **协程的参数是引用时，对象要活到协程结束。** `Ask` 的参数都是引用，协程第一次 `co_await` 之后，调用者的栈可能已经变了。`main` 里这些对象都在 `io.run()` 返回之后才销毁；写测试时也一样。
- **协程恢复要回到协程自己的执行器。** libcurl 的线程不能直接恢复协程，否则协程会在 libcurl 的线程里跑。`Suspend` 里用 `post` 把恢复的动作投回去。
- **`401` 的信息各家不同。** Anthropic 的错误体有 `authentication_error` 这样的类型；本章用的兼容网关的错误体里只有一段说明，所以信息里没有类型。错误信息的格式是“类型: 说明”或只有说明，`ErrorFromBody` 两种都认。
- **回答可能是空的。** Chat 里 `content` 可以是 `null`，Responses 里 `output` 可能一个 `message` 都没有，Anthropic 的 `content` 可能只有 `thinking` 块。这通常是因为 `max_tokens` 太小，思考用掉了配额。解析函数在这几种情况下返回空文本和停止原因，而不是抛异常，由调用者决定怎么办。
- **响应体前面可能有空白。** 兼容网关的 Chat 响应在 JSON 之前先发了几行空白（用来保持连接），JSON 解析器本来就忽略空白，所以没有影响；但如果你先 `trim` 再判断“是不是 JSON”就要小心。
- **兼容网关的响应里有额外字段。** 比如 `reasoning`、`reasoning_details`、`provider`、`cost`。代码只读自己要的字段，多出来的忽略，这样换网关不会出错。
- **不要把密钥写进日志。** 打印请求头一律先过 `Redacted`；错误信息里也不含密钥（`TransportContract` 和 `LlmAsk` 的测试检查了这一点）。
- **从项目根目录运行。** 配置文件靠当前目录找（见 0.4）；换个目录运行会找不到配置，错误信息会说缺哪个设置。
- **HTTP/2 下一条连接断了，同一条连接上在途的请求会一起失败。** HTTP/1.1 下每个请求一条连接，互不影响。`kLost` 就是为这种情形准备的，重试时要能一次处理一批请求。

- **`glz::generic` 的 `dump()` 返回的不是字符串。** 它返回 `std::expected<std::string, glz::error_ctx>`，直接拼进字符串会编译失败。用 `json::Dump`。
- **`glz::generic` 没有 `==`。** `EXPECT_EQ` 两个 JSON 值会编译失败。`json.h` 里写了一个，放在 `glz` 命名空间里，GoogleTest 才找得到；数字按写出的文字比较。
- **默认的 `glz::generic` 只有 `double`。** `9007199254740993` 读进来再写出去变成 `9007199254740992`。本项目用 `generic_u64`，整数不会丢；其余仍是 `double`。
- **写出不合法的 UTF-8，Glaze 不报错。** 请求体会带着坏字节发出去，服务那边才报错。所以文字在放进 JSON 之前先过 `Utf8()`（1.2 起）。
- **键的顺序是写入的顺序。** 请求体里键不会自动排序；对服务没有影响，但和 nlohmann/json 的输出比较时要注意。
- **花括号的初始化要小心。** `json::Value{{"a", 1}, {"b", 2}}` 是对象；数组要写 `json::Array({1, 2})`，不要写 `json::Value{1, 2}`。
- **不要在头文件里 `using namespace json;`。** 函数名 `Array`、`Object`、`Parse` 太常见。

## 9. 练习

1. 加上 `-v`，对同一个问题分别用 Chat 和 Responses 各发一次，比较两个响应体里“思考”各出现在哪里、用量字段各叫什么。
2. 把 `--system` 去掉再问一次，看请求体里 `messages`（或 `instructions`、`system`）有什么变化。
3. 在 `llm_wire.h` 里把 `Request` 的 `max_tokens` 默认值改成 16，重新构建，问一个需要长回答的问题，看停止原因是什么，回答是不是空的。
4. 用 `curl.exe` 手写一个等价的请求（密钥放在环境变量里，用 `%OPENAI_API_KEY%` 引用），对比它和程序发出的请求体。
5. 把 `http::Options` 的 `timeout` 改成 200 毫秒，看看会得到什么错误，错误的 `kind()` 是什么。
6. 给 `Transport` 写第三个实现：不连网络、只会回答固定的一段 JSON（比如永远回一个 `finish_reason` 为 `stop` 的 Chat 答复），把它补进契约测试，看哪几条必须改（提示：要不要它认识 `/slow`？）。
7. 想一想：`Redacted` 为什么保留 `Bearer` 这个词，而不是整个值都换成 `***`？又为什么 `x-api-key` 的值整个都换掉？
8. 想一想：为什么 `ErrorFromBody` 在不是 JSON 时只取响应体的前 200 个字符，而不是整个响应体？
9. 把 `anthropic-version` 的值改成一个不存在的版本，看看服务怎么回答，错误信息能不能读出原因。
10. 在 `json.h` 里把 `Value` 改成 `glz::generic`（去掉 `_u64`），写一个小测试：读 `{"n":9007199254740993}` 再写出来，和 `generic_u64` 的结果比较。
11. 把 `json::AsInt64` 改成直接读 `value.get<std::int64_t>()`，看看读一个小数和一个很大的整数时各会怎样。
