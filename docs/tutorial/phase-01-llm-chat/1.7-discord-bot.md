- 一句话目标：把机器人放进 Discord：DPP 在它自己的线程里跑，回调只做最少的事再 `post` 进我们的 `io_context`；收发放在 `Gateway` 接口后面，每个频道一条车道（同一频道一次一个作业、不同频道同时跑，作业进行中来的消息由回合在下一步取走）；长回答按 2000 字拆开、关掉所有提及；出错时只给用户一句话加错误编号；`/status` 和 `/stop`；干净地关闭，连不上而且不会自己好的问题要说清楚；系统提示词里有 Discord 的格式说明

## 1. 本章目标与成果

到 1.6 为止，程序只有命令行：一个人，一行一行地问。这一章把它放进 Discord：很多人在很多频道里同时说话，每个频道一段独立的对话；同一个频道的消息一个一个处理，不同的频道同时处理；机器人忙的时候来的话，能插进正在进行的回答，也能随时停掉；断线重连、出错、关闭，都有交代。做完后你会得到：

- **`Gateway` 接口：** 收消息、发消息、“正在输入”、斜杠命令，都放在一个小接口后面。DPP 是它的一个实现，测试里的假网关是另一个，所以车道、队列、拆分、命令这些逻辑不用连 Discord 就能测。
- **车道：** 每个频道一条，有自己的收件箱、正在进行的作业、自己的工具运行时和已加载的 Skill。同一频道一次一个作业，不同频道同时跑。作业进行中来的消息由回合在下一步取走（steering）；回合结束时还剩的，合成一条作为下一个作业。
- **什么时候回应：** 私信里的每条，服务器频道里提到机器人的，机器人所在线程里的每条。别的都不理。
- **发回去：** 超过 2000 个字符的回答拆成几条（保持代码围栏成对），第一条是对触发消息的回复；所有消息关掉提及，模型输出里的 `@everyone` 不会真的通知任何人。
- **失败时：** 用户只看到一句话加一个错误编号，路径、堆栈、服务端的原文都不会出现；详情和编号一起进日志。
- **`/status` 和 `/stop`：** 两个斜杠命令，回答只有发命令的人看得见。
- **系统提示词里的 Discord 格式说明：** 告诉模型哪些 Markdown 在 Discord 里显示、哪些不显示。
- **干净地关闭：** Ctrl+C、`SIGTERM`、关闭控制台窗口都走同一条路：停止接收、取消并等在途作业、停网关。
- **连不上时说清楚：** 一个没打开的特权开关、被拒绝的令牌，机器人停下来并说明该改什么，而不是让 DPP 无限重试。
- 新选项 `--discord`；DPP 10.1.7 经 vcpkg 引入。62 个新测试，现在一共 434 个。

## 2. 背景与概念

**两个循环。** 到现在为止，程序里只有一个事件循环：我们自己的 `io_context`（协程、定时器、HTTP 请求都在上面）。DPP 是另一个：它自己有一个套接字事件循环线程和一个线程池，消息事件的回调在线程池里执行，REST 请求完成的回调也是。DPP 的协程类型和 Asio 的 `awaitable` 不是一回事，不能互相 `co_await`。所以机器人里有两个互不相干的循环，它们只通过“把活交给对方”来通信：DPP 的回调里只做三件事：把事件转成我们的类型、过滤掉不该看的、`post` 进我们的 `io_context`，然后立刻返回；绝不在回调里跑模型，也不在里面等什么。反过来，我们要发消息时，从自己的协程里调 DPP 的异步接口，它的完成回调（在 DPP 的线程上）再 `post` 回来，我们的协程才继续。

**接口：平台的缝。** 机器人的逻辑不应该知道 DPP。`Gateway` 接口只说：有消息来了（通知谁）、有命令来了、连接不上了（说一句话）、启动、停止、发一条消息（回一个编号）、显示“正在输入”、回答一个命令。DPP 的实现很薄，大部分逻辑在 `Bot` 里；测试里的 `FakeGateway` 记下机器人发了什么，让测试往里塞消息。这样车道、队列、拆分、命令，都能在没有网络的测试里反复跑，还能写出“两个频道同时在跑”这种在真实 Discord 里很难稳定重现的测试。

**车道。** 一个频道（私信、服务器频道、线程，Discord 里每个都有自己的编号）一条车道，里面是：收件箱、当前作业、这个频道自己的 `ToolRuntime` 和 `SkillTools`。工具运行时和已加载的 Skill 是每个频道自己的：一个频道里加载了 `calculator`，另一个频道里并没有。所有车道的状态只在 `io_context` 那一个线程里碰，所以不用加锁。

- **同一频道一次一个作业。** 作业进行中来的消息放进收件箱。
- **steering。** 作业在第 2 步起会问收件箱要新消息（1.3 里就有的 `take_new_messages`），取走的消息跟在上一步的结果后面，开头带一句说明，这样模型在回答的过程中就能看到用户又说了什么。
- **剩下的消息。** 如果回合在一步里就结束了（模型没有调用工具），收件箱里的消息就没人取，这时把它们合成一条（空行隔开）作为下一个作业。用户连发三行，得到的是一个答案，不是三个。
- **不同频道同时跑。** 没有全局的并发上限，也没有收件箱的上限：有多少个频道在说话，就有多少个回合在跑。风险在第 8 节说。
- **车道什么时候删。** 空闲且没有加载任何 Skill 就删；加载了 Skill 就留着，不然这个频道的 Skill 每个回合都丢，模型要多一步重新加载，缓存也要重写。

**历史。** 车道不存历史。每个作业开始时从 `History` 读这个频道的历史，回合以回答结束才写回去，失败、取消、关闭时什么也不写（和 1.3 的回滚是同一个原则）。这一章 `History` 还是内存实现，所以**重启之后历史就没了**，1.9 才用 SQLite 解决。

**什么时候回应，用户的话怎么给模型。** 私信里的每条消息；服务器频道里提到机器人的消息；机器人所在线程里的每条消息。其余的忽略：频道里每条都回的话，机器人会打断人的聊天，也会把别人的话全发给模型。在频道里，用户的话前面写上说话的人：`Mei: 你好`（私信里不写）；这样模型分得出几个人，也满足 steering 里不同的人连发几句的情形。（用户可以在消息里写“Admin: ……”假装别人，这是提示注入的一种，防护是支线 llm-1.1 的事。）

**发回去。** Discord 的一条消息最多 2000 个字符，所以长回答要拆。拆的办法：在空行、行尾、空格里选一个靠近末尾的地方断开，再不行就硬切；每条的长度按字符算不按字节；代码围栏被切开时，上一条末尾补上闭合，下一条开头补上同样的开启（带上语言名），这样每一条里的代码都显示成代码。第一条是对触发消息的回复，后面的不是。所有消息都关掉提及：Discord 的发送接口有一个 `allowed_mentions`，设成什么都不通知，回复也不去 ping 被回复的人；程序自己还把回答里的 `@everyone`、`@here` 和 `<@…>` 都插进一个零宽空格，使它们不再是提及。两道锁出于同一个理由：模型的输出不可信。

**出错时用户看到什么。** 内部的错误（路径、堆栈、密钥的片段、服务端的原始错误文字）不能原样发给用户。用户看到“出错了（错误编号 ABC234），请稍后再试。”这样的一句话，详情和编号一起写进日志，所以用户说“它说了 ABC234”，就能找到那一行。编号是六个字符，字母表里去掉了长得像的（没有 0 和 O，没有 1 和 I）。被 `/stop` 停掉的作业回“已停止”，关闭时被停的回“机器人正在关闭”。

**斜杠命令。** `/status` 说这个频道现在有没有作业、已经几步、收件箱里几条、加载了哪些 Skill；`/stop` 停掉这个频道正在进行的作业（收件箱里的消息保留，成为下一个作业）。命令的回答只有发命令的人看得见。Discord 要求命令在 3 秒内得到回应；我们的命令是立刻回答的，所以直接回一条私密的回复就够了。（第一版我先发了一个“正在思考”，再去编辑它，结果 Discord 报 `Unknown Webhook`：两个请求在 DPP 里的先后不保证。见第 8 节。）

**系统提示词里的 Discord 格式说明。** 机器人的每个请求，系统提示词里多一节 `[discord]`：回答显示在 Discord 里，Discord 渲染 Markdown 的一个子集：粗体、斜体、下划线、删除线、剧透、行内代码、带语言名的代码块、引用（`>` 和 `>>>`）、列表、`#` 标题、`-#` 小字、`[文字](网址)` 链接（网址两边加尖括号可以不生成预览）；表格、图片语法、HTML、水平线、数学公式不显示，用列表代替表格；一条消息最多 2000 个字符；不要写 `@everyone` 这类提及。这一节的内容固定，所以和规则、Skill 目录一样在缓存的稳定前缀里。

**特权开关。** 机器人要读消息的文字，Discord 把这个叫作 Message Content Intent，是特权的：要在开发者后台自己打开。没打开时 DPP 连上以后会收到错误 4014（不被允许的 intent），然后无限地重连。这一章让网关把这种“不会自己好”的问题说出来：机器人停下来，说明要去哪里改。

**关闭。** Ctrl+C 和 `SIGTERM` 用 Asio 的 `signal_set` 接收；Windows 上关闭控制台窗口不是信号，用 `SetConsoleCtrlHandler`，它在另一个线程里被调用，所以先 `post` 回我们的循环，再等最多四五秒（Windows 在处理函数返回后很快就会结束进程）。关闭的顺序：不再接收消息，取消在途的作业并等它们结束（最多几秒），最后停网关。被取消的作业像一个被取消的回合：不留痕迹。

**不做的事。** 用户白名单和全局的并发与用量上限（用量上限是支线 llm-1.1 的事）；流式输出（llm-1.2）；图片（1.8）；SQLite 历史（1.9）；长期记忆（llm-2.4）；Windows 崩溃时写 minidump 并由外部守护重启（运维，不在这一章）；分片；在 Discord 里切换 Provider。

## 4. 关键代码讲解

**平台的缝。** 一条消息和一个命令，各是一个小结构；`Gateway` 的所有函数都在 `io_context` 的线程上被调用（实现自己负责把别的线程上的事件交过来）：

```cpp
class Gateway {
 public:
  virtual ~Gateway() = default;

  // Who is told about messages and commands. Set before Start.
  virtual void OnMessage(std::function<void(IncomingMessage)> handler) = 0;
  virtual void OnCommand(std::function<void(Command)> handler) = 0;

  // Who is told that the connection cannot work and will not by itself: a refused token, an intent that is not
  // switched on. Gets a sentence for the user that says what to do. Set before Start.
  virtual void OnFatal(std::function<void(std::string)> handler) = 0;

  virtual void Start() = 0;                         // connect and begin delivering
  virtual boost::asio::awaitable<void> Stop() = 0;  // stop delivering, disconnect

  // Writes a message in the channel and gives back its id. `reply_to` (may be empty) is the id of the message it
  // answers. A message never notifies anyone by name: whatever the text says (@everyone, a user), nobody is
  // pinged. Throws when the message could not be sent.
  virtual boost::asio::awaitable<std::string> Send(const std::string& channel_id, const std::string& text,
                                                   const std::string& reply_to) = 0;

  // "The bot is typing...", which the platform shows for a few seconds.
  virtual boost::asio::awaitable<void> Typing(const std::string& channel_id) = 0;

  // The answer to a command, shown to the person who used it only.
  virtual boost::asio::awaitable<void> Reply(const Command& command, const std::string& text) = 0;
};
```

  while (true) {
    Lane& lane = *lanes_.at(channel_id);
    if (lane.inbox.empty() || stopping_) break;
    // Everything that is waiting is one message for the model; the answer is a reply to the first of them.
    std::string text;
    const std::string reply_to = lane.inbox.front().id;
    for (const Lane::Pending& pending : lane.inbox) text += (text.empty() ? "" : "\n\n") + pending.text;
    lane.inbox.clear();
    co_await RunJob(lane, std::move(text), reply_to);

  Lane& lane = *lanes_.at(channel_id);

  stop_timer_ = std::make_unique<asio::steady_timer>(executor_, asio::steady_timer::time_point::max());

**拆分。** 每条最多 `limit` 个字符：先留出补围栏要用的位置，在最后四分之三里找空行、行尾、空格，找不到才硬切；如果这一刀落在围栏里面，这一条末尾补闭合，下一条开头补开启：

<!-- src: src/message_split.cpp#L74-L108 -->
```cpp
std::vector<std::string> SplitMessage(const std::string& text, std::size_t limit) {
  std::vector<std::string> messages;
  const std::string closer = "\n```";
  std::string rest = text;
  std::string prefix;  // the fence to open again at the start of this message
  while (true) {
    const std::string whole = prefix + rest;
    if (Chars(whole) <= limit) {
      if (!Blank(whole)) messages.push_back(whole);
      break;
    }
    // Leave room for the fence that is opened again and for the one that may have to be closed.
    const std::size_t reserved = Chars(prefix) + Chars(closer);
    const std::size_t room_chars = limit > reserved + 1 ? limit - reserved : 1;
    const std::size_t room_bytes = ByteOffset(rest, room_chars);
    const std::size_t cut = std::max<std::size_t>(BreakAt(rest, room_bytes), 1);

    std::string head = prefix + TrimmedRight(rest.substr(0, cut));
    std::size_t skip = cut;
    while (skip < rest.size() && (rest[skip] == '\n' || rest[skip] == '\r')) ++skip;  // not the spaces: they may be indentation
    std::string tail = rest.substr(skip);

    std::string language;
    if (FenceOpen(head, language)) {
      head += closer;
      prefix = "```" + language + "\n";
    } else {
      prefix.clear();
    }
    if (!Blank(head)) messages.push_back(head);
    rest = tail;
    if (rest.empty()) break;
  }
  return messages;
}

**`Bot`（假网关加“要等测试放行”的传输）。** `tests/test_bot.cpp` 里的传输 `GatedTransport` 让每个请求都等着，测试用 `Release` 放行第几个，所以能控制“两个频道的请求同时在飞”这类时序。32 个用例：

- 谁被回应：提到机器人的消息有回复，且回复指向它；没提到的频道消息不理；线程和私信里每条都回；机器人（含自己）的消息不理；只有提及没有字的不理；同一个消息 ID 第二次来不再回答。
- 说话的人：频道里模型看到 `Mei: hello`，私信里只有文字。
- 顺序和车道：作业进行中来的消息等着，之后合成一条（`Mei: second` 空一行 `Li: third`），回答是对第一条的回复；作业进行中来的消息在下一步被交给模型（请求里有 steering 的标记），不会再开一个作业；两个频道的请求同时在飞；每个频道自己的历史；空闲且没有 Skill 的车道被删，加载了 Skill 的留着。
- 给模型的内容：系统提示词是指令、规则、Skill 目录、`[discord]` 的顺序；没有 Skill 时没有目录也没有工具；状态里有频道和日期（时钟用固定的）；`[discord]` 一节里有该有的话。
- 发回去：长回答拆成几条，只有第一条是回复，每条不超过 2000 字；回答里的 `@everyone` 和 `<@…>` 被拆开；作业进行时“正在输入”按间隔重复，结束后不再发；一条消息发不出去不影响下一个作业。
- 出错：服务返回 500 时用户的文字里有错误编号，没有路径、没有“secret”、没有状态码；失败的回合历史里什么也没有。
- 命令：`/stop` 取消作业、频道里说已停止、历史不动；停下之后等着的消息成为下一个作业；没有作业时 `/stop` 说没有；`/status` 空闲时、运行时（作业号、步数、收件箱）、加载了 Skill 时各说得对。
- 关闭：关闭时在途的作业被取消、没有半条历史、回一句“机器人正在关闭”；没有作业时关得很快；关闭之后来的消息不理；网关说自己不能用了时机器人停下来并保存原因，普通的停止不是失败。

**DPP 的转换。** `tests/test_dpp_convert.cpp` 用手工造出来的 `dpp::message`：两种写法的提及都被认出并从文字里去掉，别人的提及不动，编号 9999 不会被当成 999；显示名优先于用户名；机器人作者和没有服务器的消息被标出；线程由调用者说；三种线程类型；`FatalGatewayProblem` 对 4014 和 4004 给出说明（里面有“开发者后台”和 `discord_token`），普通的日志行不是致命的。

**其余。** `LoadSkillSetup` 三个用例（目录里的 Skill 和玩具工具；没有可用的 Skill 是指出目录的错误；目录不存在是错误）；`RulesSection` 和 `CatalogSection`；选项 `--discord`。

**改动检验。** 把下面三处各临时改坏一次，对应的测试都会失败，然后改回：

- 不做去重：`Bot.TheSameMessageDeliveredAgainIsNotAnsweredAgain` 失败。
- 不拆开回答里的提及：`Bot.MentionsInTheAnswerAreNotMentions` 失败。
- 所有频道共用一条车道：`Bot.ALaneIsGoneWhenItsWorkIsDoneUnlessASkillIsLoadedInIt`、`AMessageThatArrivesDuringAnAnswerIsGivenToTheModelAtTheNextStep`、`AMessageThatMentionsTheBotIsAnsweredWithAReplyToIt` 等五个用例失败。

**构建。** 清理后重建，`/W4 /WX` 下 0 个警告；`check-dlls` 和 `--dependency-check` 的测试通过（DPP 带来的 DLL 都在清单里）。

**真实运行（Discord）。** 在我的测试服务器里，用 `config.ini` 里的令牌和模型（`deepseek` 经 OpenRouter）跑了两轮，机器人在线，第 1 节里的是第二轮的日志。结果：

- **连接：** 第一次用 DPP 10.1.6，连不上，日志里是 `HTTP(S) error on https connection to GET discord.com:443/api/v10/gateway/bot: Malformed HTTP response`，而同一台机器上的 curl 访问同一个地址正常。DPP 的发布说明里说 10.1.7“修复了 10.1.6 引入的、让 Windows 上的 SSL 连接不能正常工作的问题”；页面没有写这个错误文字，我没有确认两者是同一个问题，但换成 10.1.7 之后连接就好了。

- **DPP 回调所在的线程：** 第一轮的调试日志里，每条消息的回调打印了它所在的线程，一共出现了 11 个不同的线程：回调确实在 DPP 的线程池里，不在我们的循环线程里。
- **令牌：** 用配置里令牌的原文去搜整份日志（包括 `-v` 的调试日志），0 次出现；LLM 的密钥在请求头里显示为 `Bearer ***`。

- **命令：** `/status`（空闲时、作业运行时）和 `/stop` 都有回应，日志如第 1 节。
- **回答和格式：** 在 Discord 里看到：“1 到 400 每个数字一行”的超长回答被拆成几条，接得上，没丢内容；标题、列表、引用、代码块、链接都按预期显示，表格显示成原样的竖线和横线，所以 `[discord]` 一节里“表格不显示”这一条是对的，没有改。

## 7. 技术资料

- **DPP 10.1.7**（vcpkg 基线给的是 10.1.6，用 `vcpkg.json` 的 `overrides` 固定到 10.1.7）。它不用 Asio：自己一个套接字事件循环线程，加一个至少 4 个线程的线程池；消息和 REST 完成的回调都在线程池里；REST 走它自己的 HTTPS 客户端（OpenSSL），不走 libcurl，所以进程里有两套 TLS；它自己处理 Discord 的限流。DPP 的协程（`dpp::task`）和 Asio 的 `awaitable` 不是一个类型，这一章全程不用 DPP 的协程。端口声明 Windows 上不支持静态三元组，所以是动态链接，要带 DLL。
- **Discord 的几个事实：** 一条消息最多 2000 个字符；读消息的文字需要 Message Content Intent，它是特权的，要在开发者后台打开；斜杠命令要在 3 秒内得到回应；发送接口的 `allowed_mentions` 控制谁被通知。Discord 渲染 Markdown 的一个子集：官方帮助页我读不了（返回 403，我没有绕开），所以 `[discord]` 一节里的清单是我按已知的行为写的，并在真实运行里逐项在 Discord 里看过，结果见第 6 节。
- **DPP 的版本与 Windows 的套接字：** 10.1.6 在 Windows 上用 `WSAPoll`，`FD_SETSIZE` 默认 64，超过了会抛异常（这是读源码得出的推断，我没有实测）；一个机器人的分片加并发的 REST 连接远低于这个数。发布说明里说 10.1.7 换了 Windows 的套接字引擎（`WSAAsyncSelect`）；我没有量过两者的差别。
- 设计取舍：
  - **两个循环，只通过 `post` 通信。** 被否决：把我们的作业放进 DPP 的线程池（我们所有的协程和计时器就都不能用了）；自己用 Boost.Beast 写网关（限流、分片、重连都得自己做）。
  - **`Gateway` 接口。** 被否决：车道里直接用 `dpp::message`（测试要么连 Discord，要么 mock DPP 的大类型）。
  - **历史只在 `History`，车道里只有进行中的东西。** 被否决：车道里缓存历史（以后换成 SQLite 就有一致性问题）；每个回合重建工具运行时（加载的 Skill 丢了，缓存也要重写）。
  - **车道在空闲且没有 Skill 时删除。** 被否决：一直保留（频道多了内存不回收）；一空闲就删（Skill 每个回合都丢）。
  - **剩下的消息合成一条。** 被否决：一条一个作业；丢掉。
  - **只回应私信、提到、线程。** 被否决：每条消息都回应；只回应提到的（线程里每句都要再提一次）。
  - **斜杠命令。** 被否决：文字命令（会被当成发给模型的消息，用户也不知道有这些命令）。
  - **不做白名单，不设并发上限。** 骨架里就是这么定的；风险在第 8 节。
  - **命令用一条私密回复，不用“先思考再编辑”。** 我们的命令是马上回答的，延迟回答只会引入先后顺序的问题。

## 8. 常见问题与坑

- **DPP 10.1.6 在 Windows 上连不上。** `Malformed HTTP response`。用 10.1.7（`vcpkg.json` 的 `overrides`）。
- **`4014: Disallowed intent(s)`。** Message Content Intent 没打开。开发者后台，Bot，Privileged Gateway Intents。没打开时 DPP 会一直重连；这一章让机器人停下来并说明。
- **`4004`。** 令牌被拒绝：重新生成并写进 `discord_token`。令牌等于密码。
- **别在 DPP 的回调里 `co_await` 或跑模型。** 它在线程池里，至少只有 4 个线程，占住了会拖住 DPP 自己；而且 DPP 的协程和 Asio 的不是一个类型。
- **DPP 的线程池会吞掉回调里的异常，只记一条警告。** 这条消息就丢了；回调里自己 `try/catch` 并记日志。
- **先“思考”再编辑命令的回复，会碰到 `Unknown Webhook`。** 两个请求在 DPP 里的先后不保证；能马上回答的命令，一次回答完。
- **没有并发上限，也没有白名单。** 很多频道同时说话，就有很多个回合同时请求 LLM 服务，可能碰到服务的速率限制（请求失败，用户看到友好的错误和编号）；令牌被邀请进别人的服务器时，任何成员都能花你的 LLM 额度。这一章不处理，只在自己的服务器里用；限速、重试和用量上限是支线 llm-1.1 的事。
- **重启之后历史没了。** `History` 是内存实现；1.9 才有 SQLite。加载了哪些 Skill 也一样。
- **用户可以在消息里写“Admin: ……”假装别人。** 说话的人是我们写在文字前面的，用户自己也能写。这是提示注入的一种；防护是支线 llm-1.1 的事。
- **回答里的提及要两道锁。** 发送接口的 `allowed_mentions`，和程序自己在 `@everyone` 里插零宽空格；少一道，换一个实现就可能漏。
- **“今天”是服务器所在时区的今天。** 状态里的日期用的是运行机器人的机器的本地时区，不是用户的。
- **关闭控制台窗口的处理函数在另一个线程里。** 不能直接碰 `Bot`，要先 `post` 回 `io_context`；返回之后 Windows 很快就会结束进程，所以处理函数里要等机器人关完（最多四五秒）。
- **两套 TLS 栈并存。** DPP 用 OpenSSL，我们的 HTTP 请求用 libcurl（Windows 上是 Schannel），互不影响，但进程里会有两份证书的设置。
- **试程序时小心 `config.ini` 里的令牌。** 带 `--discord` 的程序一启动就用令牌去连 Discord（`--dependency-check` 这类不联网的选项除外）；只想看错误信息的话，用别的配置文件，不要用写着真令牌的那个。

## 9. 练习

练习：

1. 加一个斜杠命令 `/reset`：清掉这个频道的历史和已加载的 Skill。先写测试（假网关里用 `Use`），再做；想一想：正在进行的作业怎么办？
2. 给 `/status` 加一行“这个频道已经问了几个问题”。要用到 `History` 里的什么？
3. 把 `typing_interval` 设成 100 毫秒，在测试里看“正在输入”的次数；想一想：为什么真实的间隔是 8 秒？
4. 让机器人对一个频道里每一条消息都回应（不用提到）：改哪几处？去掉“只回应提到的”之后，会有什么新问题？
5. 给 `FakeGateway` 加一个“延迟”：`Send` 要 50 毫秒才完成。写一个测试：同一个频道里，第二个作业在第一个作业的回答还没发完时就开始了吗？应该是什么样？
6. 实现一个文本文件的 `Gateway`：从标准输入读“频道 ID: 文字”，把机器人的回答打印出来。用它不连 Discord 就能和机器人聊天。
7. 想一想：为什么车道里的状态只在 `io_context` 一个线程里碰，不加锁，也不会有数据竞争？如果以后让 `io_context` 用多个线程跑，要改哪里？
8. 想一想：`Bot::RunLane` 里 `lanes_.erase(channel_id)` 之后不能再用 `lane`。如果在 `erase` 之后又有一条消息进来，会怎样？
