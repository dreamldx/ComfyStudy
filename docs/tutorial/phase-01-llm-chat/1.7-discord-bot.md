## 2. 背景与概念

待写。（要点：会话是无状态的：每一轮按 `channel_id` 从 SQLite 重新生成历史，跑完写回就丢，不做会话缓存和淘汰；内存里只有每频道一条车道（`strand`、收件箱（不设上限）、当前作业的 ID 和取消信号，不存历史，空了就删），同一频道串行；作业运行时来了新消息，放进车道的收件箱，由 Agent 循环在下一步开始前取走（steering，见 1.3），轮次结束时收件箱里还有剩余，就当成下一轮；`io` 与 `blocking` 两个执行器；DPP 的回调在池线程里执行，只做最少的检查（忽略机器人自己的消息、按消息 ID 去重），然后 `post` 进我们的 `io_context`；简易作业队列（每频道串行，全局有并发上限）；程序入口集中组装依赖，去掉全局取配置；优雅退出（先停接收，再等在途任务，最后停循环）；准入控制：全局限制同时跑 Agent 循环的车道数，收件箱不设上限，不做用户白名单，用量上限见 llm-1.7；失败、取消或进程中途退出的一轮不留任何记录，已经流式发出去的那条消息改成“已中断”；网关重连后事件可能重发，按消息 ID 去重，避免回复两次；密钥管理（Discord 令牌放哪里，不进日志）；Windows 上崩溃时写 minidump，由外部守护重启；Discord 的约束（消息 2000 字要拆分，附件有大小上限，交互令牌有有效期）；面向用户的错误信息：内部错误（路径、堆栈、密钥片段）不原样发给用户，用户看到友好的提示和一个错误编号，详情进日志；作业的可追溯：每个作业有 ID，用 `/status` 查状态、`/cancel` 取消；Windows 上用 `SetConsoleCtrlHandler` 接收 Ctrl+C 和关闭窗口事件，触发优雅退出；斜杠命令与自然语言的分工：`/reset`、`/model`、`/status`、`/cancel` 走命令，其余走对话；产物的投递：出图耗时长，图片一生成就发到 Discord，同时把句柄或缩略图回给模型；失败的一轮不记录，但已经发出的图片和这一点怎么说明，见 10.4；确认与澄清：需要用户确认或模型要提问时，结束这一轮并带上问题，用户的回答作为下一轮，不让一轮挂着等人；Discord 里可以用按钮；Discord 是 Agent 事件流（见 1.3）的一个前端：订阅文本增量做限速编辑，订阅产物事件发图片，订阅错误事件发友好的提示。）
